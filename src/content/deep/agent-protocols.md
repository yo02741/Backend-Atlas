> 本課以 2026 年 11 月的公開資訊為準。這些協定都還在快速變動，治理單位、參與廠商與規格內容都可能改變；這裡只講各自的定位與抽象流程，不寫規格欄位與版本號，實作前請以各協定的官方文件為準。

## 從一個具體問題開始：一個 agent 平台，五個協定名詞

團隊要做一個內部的 agent 平台，需求單上寫著：agent 要能查工單系統與資料庫、要能把「寫測試」這種子任務交給另一個團隊做的 agent、工程師要能在編輯器裡叫用它、未來還想讓它在公司官網上幫客人操作、甚至自動付費呼叫外部的資料 API。

會議上有人說「這些都用 MCP 就好」，另一個人說「agent 之間要用 A2A」，第三個人貼了 ACP、WebMCP、x402、AP2 的連結。最後的決定是「全部都支援」，三個月後平台上有五套半完成的整合，每一套都只有一個人懂。

這些協定其實各自處理不同的「誰跟誰說話」。先把每一個放對位置，多數情況只需要其中一兩個。

## 先分清楚：誰跟誰說話

```text
                          ┌─────────────┐
           ACP            │  編輯器 /    │
   （編輯器 ↔ coding agent）│  IDE        │
                          └──────┬──────┘
                                 │
┌──────────┐     A2A      ┌──────▼──────┐     MCP      ┌─────────────────┐
│ 別的 agent │ ◀──────────▶ │   你的 agent  │ ───────────▶ │ 工具與資料（server）│
└──────────┘ （agent ↔ agent）└──────┬──────┘（agent ↔ 工具）└─────────────────┘
                                 │
                  WebMCP         │        x402 / AP2
           （網頁 → 瀏覽器內的 agent）  （agent 付款與授權）
```

| 關係 | 協定 | 一句話 |
|---|---|---|
| agent ↔ 工具與資料 | MCP | 把工具、資料、提示樣板用統一方式提供給 AI 應用 |
| agent ↔ agent | A2A | 把一個任務委派給另一個（可能是別家的）agent，取回結果 |
| 編輯器 ↔ coding agent | ACP（Agent Client Protocol） | 任何編輯器接任何 coding agent |
| 網站 ↔ 瀏覽器裡的 agent | WebMCP | 網頁主動宣告「這裡有哪些功能可以讓 agent 呼叫」 |
| agent ↔ 收費的服務 | x402 | 用 HTTP 402 回應告訴 agent「要付款才能用」，付完再取 |
| 使用者 ↔ 代為付款的 agent | AP2 | 證明「使用者確實授權了這筆購買」的框架 |

## MCP：工具與資料

**解決什麼**：每個 AI 應用都要接一堆外部工具（工單、資料庫、檔案），沒有標準時每個應用對每個工具都要寫一次整合。MCP 讓工具提供者寫一次 server，任何支援 MCP 的應用都能接。

**誰在推**：Anthropic 在 2024 年發表，現在是開放規格，多家 AI 應用與開發工具都有實作。

**角色**：host（AI 應用本身，例如桌面聊天程式、IDE）裡面有 client，每個 client 連一個 server；server 提供工具（tools）、資源（resources）與提示樣板（prompts）。

**抽象流程**：client 連上 server → 問它有哪些工具 → 把工具清單交給模型 → 模型決定呼叫哪個 → client 轉送呼叫、取回結果放回 context。

細節（訊息格式、兩種傳輸、Python SDK）見 [#/skill/ai-skills-mcp](#/skill/ai-skills-mcp)；遠端 server 的授權見 [#/skill/mcp-authorization](#/skill/mcp-authorization)；安全風險見 [#/skill/owasp-mcp-top10](#/skill/owasp-mcp-top10) 與 [#/skill/tool-poisoning](#/skill/tool-poisoning)。

**和其他協定的關係**：MCP 是其他幾個協定的參照點。它處理的是「agent 使用工具」，工具本身沒有自主性、不會反問、不會花一小時自己規劃。

## A2A：agent 之間委派任務

**解決什麼**：當對方不是一個工具，而是另一個有自己模型、自己工具、會自己規劃的 agent 時，「呼叫工具、立刻拿到結果」的模型不夠用。任務可能要跑很久、中途需要補充資訊、結果可能是一份檔案而不是一行文字。A2A 定義 agent 之間怎麼發現彼此、委派任務、追蹤進度、交換結果。

**誰在推**：Google 在 2025 年發表，之後移交 Linux Foundation 治理，多家企業軟體廠商參與。

**角色**：發出任務的一方是 client agent，接任務的一方是 remote agent。remote agent 對外公布一份描述自己能力的卡片，client 讀了之後決定要不要把任務交給它。

**抽象流程**：發現（讀對方的能力描述）→ 送出任務 → 對方回報狀態（進行中、需要更多輸入、完成、失敗）→ 取回產出物。長任務可以用串流或回呼的方式更新進度。

**和 MCP 的關係**：互補，不是替代。一個 agent 往下用 MCP 接自己的工具，往旁邊用 A2A 和其他 agent 協作。判斷原則：對方是「被呼叫就照做、立即回傳」的功能，用 MCP；對方是「接下任務、自己決定怎麼做、可能需要來回」的 agent，用 A2A。同一個團隊內部的多個 agent，如果都在同一個程式裡，直接用函式呼叫或框架內建的機制就好，不需要協定（多 agent 分工見 [#/skill/ai-multi-agent](#/skill/ai-multi-agent)）。

> IBM 也推過一個縮寫同為 ACP 的 **Agent Communication Protocol**，定位接近 A2A（agent 之間的通訊）；依公開消息，它後來併入 A2A 的發展方向。它和下一節的 Agent Client Protocol 是兩個不同的東西，看到 ACP 時先確認指的是哪一個。

## ACP（Agent Client Protocol）：編輯器接 coding agent

**解決什麼**：coding agent（在終端機裡改程式的那種）越來越多，編輯器也很多。沒有標準時，每個編輯器要為每個 agent 寫一套整合，每個 agent 也要為每個編輯器做外掛。ACP 讓兩邊各實作一次就能互通，概念上類似 LSP（Language Server Protocol）之於程式語言支援。

**誰在推**：Zed 在 2025 年發表，之後有其他編輯器與 agent 陸續支援。

**角色**：client 是編輯器，agent 是 coding agent。通常由編輯器在本機啟動 agent 程序，兩者在本機交換訊息。

**抽象流程**：編輯器把使用者的要求與相關檔案的 context 送給 agent → agent 回報它的計畫、要讀寫的檔案、要執行的指令 → 需要權限的動作由編輯器詢問使用者 → agent 的修改以差異的形式呈現在編輯器裡，讓使用者審。

**和 MCP 的關係**：不同層。ACP 處理「人在編輯器裡怎麼操作 agent」，MCP 處理「agent 怎麼接工具」。一個透過 ACP 接進編輯器的 agent，背後照樣可以用 MCP 接工具。

## WebMCP：網站對瀏覽器裡的 agent 暴露功能

**解決什麼**：瀏覽器裡的 agent 要操作網站時，現在多半是「看畫面、找按鈕、點下去」，又慢又容易壞，網站改版就失效。WebMCP 的想法是讓網頁自己宣告「這裡有哪些功能、要帶什麼參數」，agent 直接呼叫，不用模擬點擊。

**誰在推**：目前是在 W3C 社群小組中孵化的**提案**，還不是正式標準，瀏覽器支援仍屬實驗階段。具體的 API 形狀可能還會大改。

**角色**：網頁（由網站提供）宣告工具；瀏覽器（或瀏覽器裡的 agent）是呼叫方；使用者在場，動作在使用者自己的瀏覽器 session 裡進行。

**抽象流程**：網頁載入時用 JavaScript 註冊一組功能與說明 → 瀏覽器內的 agent 讀到清單 → 依使用者要求呼叫 → 功能在網頁裡執行，沿用使用者已經登入的身分。

**和 MCP 的關係**：名稱與概念借自 MCP（工具清單、描述、參數），但位置不同：MCP server 通常是一個獨立的後端程序；WebMCP 的「server」就是網頁本身，跑在使用者的瀏覽器裡。因為沿用使用者的登入狀態，寫入類的功能更需要明確的使用者確認。

## x402 與 AP2：agent 付款

### x402

**解決什麼**：agent 想用一個收費的 API（例如付一次費查一筆資料），傳統做法要先註冊帳號、綁信用卡、拿 API key，這對自動化的 agent 很不方便。x402 用 HTTP 早就保留、但一直少有人用的狀態碼 **402 Payment Required**：伺服器回 402 並說明要付多少、怎麼付，client 付款後帶著付款證明重送請求。

**誰在推**：Coinbase 在 2025 年發表，付款方式以穩定幣等鏈上支付為主。

**抽象流程**：請求資源 → 收到 402 與付款條件 → client（agent 的錢包）完成付款 → 帶付款證明重送 → 伺服器驗證後回傳資源。

### AP2

**解決什麼**：當 agent 代替使用者購物時，商家、支付業者與使用者都需要一個問題的答案：**這筆交易真的是使用者授權的嗎？授權的範圍是什麼？** AP2（Agent Payments Protocol）處理的就是這件事——用可驗證、有簽章的紀錄，把「使用者的意圖與授權範圍」和「agent 最後送出的購物內容」連起來，出事時能追責。

**誰在推**：Google 在 2025 年發表，有多家支付與商務業者參與。

**和 x402 的關係**：層次不同。x402 處理「怎麼在一次 HTTP 請求裡完成付款」，AP2 處理「這次付款有沒有被授權、授權了多少」。公開資料中 AP2 有提到可以搭配 x402 這類付款方式使用。兩者都和 MCP、A2A 互補：agent 可以透過 MCP 呼叫一個要付費的工具，付費的部分走 x402。

不論用哪一個，讓 agent 能自己花錢都要有上限：單筆金額、每日總額、允許的收款方，超出時由人確認。這和 [#/skill/agent-loop](#/skill/agent-loop) 的 token 預算是同一個思路，只是單位從 token 換成錢。

## 我該用哪個

| 需求 | 用 | 不需要 |
|---|---|---|
| 讓 agent 查工單、讀資料庫、呼叫內部 API | MCP | A2A：對方只是功能，不是 agent |
| 把「寫測試」交給另一個團隊維護的 agent，它要跑二十分鐘 | A2A | 把對方包成 MCP 工具：長任務與來回補充資訊不好處理 |
| 同一個程式裡的 planner 與 worker 兩個 agent | 框架內建機制或函式呼叫 | A2A：沒有跨系統邊界 |
| 讓團隊在自己慣用的編輯器裡用同一個 coding agent | ACP（如果編輯器與 agent 都支援） | 為每個編輯器寫外掛 |
| 讓客人在瀏覽器裡用 agent 操作官網的訂位功能 | WebMCP（實驗中，先評估成熟度） | 要求 agent 模擬點擊 |
| agent 按次付費呼叫外部資料 API | x402 | 先開帳號綁卡、把 API key 給 agent |
| agent 代使用者購物，商家需要確認授權 | AP2 | 只靠 agent 自己聲稱「使用者同意了」 |

判斷時先問兩個問題：

1. **對方是誰？** 工具 → MCP；另一個 agent → A2A；編輯器 → ACP；網頁 → WebMCP；收款方 → x402 / AP2。
2. **有沒有跨系統邊界？** 都在同一個程式、同一個團隊裡，通常不需要任何協定。協定的價值在於讓不同人、不同廠商做的東西互通；沒有互通需求時，它只是多一層要維護的東西。

## 常見錯誤

**所有東西都包成 MCP server。** 把一個會自己規劃、跑很久的 agent 包成一個「工具」，呼叫方只能乾等結果，中途無法補充資訊或取消。對方是 agent 時看 A2A。

**兩個 ACP 混為一談。** 搜尋「ACP protocol」會同時看到編輯器用的 Agent Client Protocol 與 agent 通訊用的 Agent Communication Protocol，文件與 SDK 完全不同。

**把提案當標準。** WebMCP 這類還在社群小組階段的提案，API 可能整個改掉。拿來做原型可以，正式產品要準備好跟著改，或保留傳統的操作路徑。

**付款沒有上限。** agent 能自動付款，就可能在迴圈裡重複付款。金額上限、收款方白名單、異常時由人確認，必須在 agent 之外的層強制執行，不是寫在提示詞裡。

**每加一個協定就多一個攻擊面。** 每個協定都帶來新的身分驗證、授權與輸入來源，要一起納入威脅建模（見 [#/skill/ai-threat-modeling](#/skill/ai-threat-modeling)）。

## 動手

- 拿團隊現在的 agent 需求清單，逐項用上面的兩個問題分類，看真正需要的是哪一兩個協定。
- 讀 MCP 官方文件的架構說明，再讀 A2A 的概念說明，自己寫一段話說明兩者的分界，對照本課的表格。
- 做完選擇題確認分得清楚各協定的定位。
