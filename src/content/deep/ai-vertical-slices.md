## 從一個具體問題開始：四張票都做完了，功能卻不能用

需求是「病患可以取消掛號」。團隊把它拆成四張票，派給四個 agent 平行做：

```text
#1 appointments 表加 cancelled_at 欄位與 migration
#2 POST /appointments/{id}/cancel API
#3 「我的掛號」頁加取消按鈕
#4 補上取消功能的測試
```

四張票都準時完成、各自的 PR 都過了 review。合在一起後才發現：#2 的 API 回傳 `{"status": "canceled"}`，#3 的前端判斷的是 `"cancelled"`；#1 的 migration 把欄位設成 `NOT NULL DEFAULT now()`，所有舊掛號一夕之間都變成「已取消」；#4 的測試是照著票的描述寫的，跟實際的 API 對不上，整批都是紅的。

問題不在任何一個 agent 做錯事，而在拆法。這四張票是**水平切片**：每張只做一層，單獨完成時沒有任何行為可以驗證，層與層之間的約定（欄位名、狀態字串、預設值）要到最後整合才被檢查。平行的 agent 越多，各自猜錯約定的機會越多。

## 垂直切片：tracer bullet

tracer bullet（曳光彈）的比喻是：先打出一發能看到彈道的子彈，確認從頭到尾打得到目標，再補上其他的。換成拆票，就是每張票都**窄窄地貫穿每一層**：

```text
          水平切片：一張票一層              垂直切片：一張票貫穿每一層
        ┌────────────────────┐          ┌────┬────┬────┬────┐
UI      │         #3         │          │    │    │    │    │
        ├────────────────────┤          │    │    │    │    │
API     │         #2         │          │ #1 │ #2 │ #3 │ #4 │
        ├────────────────────┤          │    │    │    │    │
DB      │         #1         │          │    │    │    │    │
        ├────────────────────┤          │    │    │    │    │
測試    │         #4         │          │    │    │    │    │
        └────────────────────┘          └────┴────┴────┴────┘
```

一張好的垂直切片票有四個條件：

- **貫穿每一層**：schema、API、UI、測試都在這張票裡，只做這個行為需要的那一小部分。
- **做完就能單獨展示或驗證**：合併後，可以操作一次給人看，或有一組測試證明這個行為成立。「新增一個欄位」驗證不了任何行為，不是一張完整的票。
- **大小放得進一個 agent 的工作脈絡**：一個從零開始的 agent 能讀完需求、相關程式與測試，並在同一個脈絡裡做完。需要讀十幾個模組才能開始的票，通常還能再切。
- **先做 prefactor**：如果現有程式讓這個改動很難做，先開一張「整理程式、行為不變」的票，讓之後的票變簡單。這個原則常被概括為「先讓改動變容易，再做那個容易的改動」。

每張票寫的是**使用者看得到的行為**，不是逐層的實作清單。mattpocock/skills 的 `engineering/to-tickets` 技能就是這套拆票規則，它也建議票裡不要寫具體的檔案路徑與程式片段，因為很快就會過時。

### 阻擋關係

每張票都要標出 **Blocked by**：哪些票做完它才能開始。沒有阻擋的票可以立刻開工；所有阻擋都完成的票構成**可以開工的前線（frontier）**。阻擋關係只標真正的依賴（需要前一張票建立的資料、介面或行為），不要因為「感覺應該先做」就標。標太多，可以平行的工作被串成一條線；標太少，agent 會在依賴還不存在時自己猜，猜錯就重工。

## 示範：「掛號可以取消」拆成六張票

需求補齊後是這樣的：病患可以取消未來的掛號；看診前 2 小時內不能取消；取消後時段要釋出給其他人預約；後台要看得到取消紀錄；取消後寄通知給病患。現有程式裡，掛號狀態的改變散在三個 handler 各自用字串比對，加一個「已取消」狀態要改三處。

| 票 | 做出來的行為 | Blocked by | 驗收 |
|---|---|---|---|
| P | （prefactor）掛號狀態的轉換集中到一個地方，行為不變 | 無 | 既有測試全綠；新增狀態轉換的單元測試 |
| 1 | 病患能在「我的掛號」取消一筆未來的掛號 | P | 欄位 + API + 按鈕 + 測試：取消後狀態為已取消，列表顯示「已取消」，舊資料不受影響 |
| 2 | 看診前 2 小時內不能取消 | 1 | API 回 409 與原因；按鈕停用並顯示原因；剛好 2 小時的邊界有測試 |
| 3 | 取消的時段可以被其他病患預約 | 1 | 預約查詢與重疊檢查排除已取消的掛號；依 ADR-0005 調整資料庫約束 |
| 4 | 後台能篩選並查看取消紀錄 | 1 | 後台列表可篩選已取消；顯示取消時間與操作者 |
| 5 | 取消後病患收到通知 | 1 | 取消與「待寄通知」在同一個交易寫入；背景工作寄出；寄送失敗會重試 |

幾個值得注意的地方：

- **票 1 就是 tracer bullet**。它是最窄的一條完整路徑：一個欄位、一個 API、一個按鈕、一組測試。做完它，「狀態字串叫什麼」「欄位預設值是什麼」這些約定就固定在 main 上了，後面的票都從這裡開始，不用各自猜。
- **票 2–5 彼此沒有依賴**，票 1 完成後可以同時派給四個 agent。
- **阻擋關係與檔案衝突是兩件事**。票 2 和票 5 都會改到取消的處理邏輯，雖然功能上互不依賴，平行做仍可能在同一個檔案衝突。這屬於排程問題：可以讓票 5 晚一點開始，或在票 1 先留好「取消後」的擴充點。多 agent 如何分配檔案所有權，見[多 agent 協作：分支與工作區隔離](#/skill/ai-multi-agent)。
- **票 3 引用了 ADR**。執行這張票的 agent 需要知道為什麼重疊檢查是資料庫約束，而不是應用程式裡的判斷（見 [ADR：把架構決策寫下來](#/skill/ai-adr)）。

下面這段程式把阻擋關係算成「每一波可以平行開工的票」，順便檢查有沒有循環依賴（循環代表拆錯了，沒有任何一張能先開始）。可以直接執行：

```python run
# 每張票 → 阻擋它的票
blocked_by = {
    "P": [],
    "1": ["P"],
    "2": ["1"],
    "3": ["1"],
    "4": ["1"],
    "5": ["1"],
}


def waves(graph):
    """依阻擋關係分波：同一波的票可以平行做。有循環時丟出錯誤。"""
    done, result = set(), []
    while len(done) < len(graph):
        # 前線：自己還沒做、所有阻擋都已完成
        frontier = sorted(t for t, deps in graph.items() if t not in done and all(d in done for d in deps))
        if not frontier:
            stuck = sorted(set(graph) - done)
            raise ValueError(f"循環依賴，這些票永遠無法開始：{stuck}")
        result.append(frontier)
        done.update(frontier)
    return result


for i, wave in enumerate(waves(blocked_by), 1):
    print(f"第 {i} 波：{', '.join(wave)}")

# 拆錯的例子：2 等 3、3 又等 2
try:
    waves({"1": [], "2": ["1", "3"], "3": ["2"]})
except ValueError as e:
    print("\n" + str(e))
```

把 `"5": ["1"]` 改成 `"5": ["1", "2"]`，再執行一次，可以看到票 5 被推到第 4 波——這就是「為了避免檔案衝突而延後」的代價，整體多了一輪。

### 一張票寫成什麼樣

```markdown
## 1：病患能在「我的掛號」取消一筆未來的掛號

**要做出來的行為**：登入的病患在「我的掛號」看到每筆未來的掛號旁有「取消」，
按下並確認後，那筆掛號顯示為「已取消」，重新整理後仍是已取消。

**Blocked by**：P（掛號狀態轉換集中）

**相關決策**：ADR-0005

- [ ] 已取消的掛號在 API 回傳中狀態為 cancelled，並帶取消時間
- [ ] 既有的掛號資料在 migration 後狀態不變
- [ ] 只能取消自己的掛號（別人的回 404）
- [ ] 測試涵蓋上面三點
```

驗收項目寫成可以檢查的句子，之後可以直接變成測試（見[規範要變成測試](#/skill/ai-spec-to-tests)）。

## 例外：大範圍機械式重構用 expand–contract

有一種改動不適合硬切垂直：**一個機械式的變更，波及整個程式庫**。例如把 `patient_name` 欄位改名成 `display_name`，全專案有上千個地方用到它。改了欄位，上千處同時壞掉；任何一張「只改一部分」的票合進去，CI 都是紅的。

這種改動用 **expand–contract**（也叫 parallel change）分三階段：

| 階段 | 做什麼 | 這時的狀態 |
|---|---|---|
| Expand（擴張） | 加上新形式，與舊形式並存：新增 `display_name` 欄位、寫入時兩個都寫、讀取時優先讀新的、回填舊資料 | 新舊都能用，什麼都沒壞 |
| Migrate（遷移） | 分批把呼叫點改用新形式，每批一張票，大小依影響範圍切（每個套件、每個目錄） | 每批合併後 CI 都是綠的，因為舊形式還在 |
| Contract（收縮） | 確認已經沒有呼叫點使用舊形式後，刪除舊欄位與相容程式碼 | 只剩新形式 |

阻擋關係是固定的形狀：每一張遷移票都被 Expand 阻擋；Contract 被**所有**遷移票阻擋。遷移票之間通常互不依賴，可以平行派給多個 agent。

```text
            ┌──> M1（scheduling 套件）──┐
Expand ─────┼──> M2（billing 套件）─────┼──> Contract
            └──> M3（admin 套件）───────┘
```

資料庫欄位的 expand–contract 也是零停機部署的基本做法：新舊版本的程式在部署期間同時在跑，schema 必須同時相容兩者（見[部署策略與資料庫遷移](#/skill/cd-strategies)）。

如果連分批都沒辦法各自保持綠燈，例如型別改變會讓編譯整個失敗，仍然維持同樣的順序，但讓各批改動先合進一條共用的整合分支，最後由一張「整合並驗證」的票合回 main。綠燈只在那一張保證。

## 常見錯誤

| 狀況 | 症狀 | 修法 |
|---|---|---|
| 依層切票（schema 一張、API 一張、UI 一張） | 每張都完成，整合時約定對不上 | 改成垂直切片，第一張做最窄的完整路徑 |
| 第一張票就想做完整功能 | 票太大，agent 的脈絡塞不下，做到一半開始自相矛盾 | 第一張只做 happy path，例外情況各自一張 |
| 驗收寫「API 完成」「頁面完成」 | 無法判斷到底做完沒有 | 寫使用者看得到的行為，每條都能變成測試 |
| 阻擋關係憑感覺標 | 能平行的被串成一條線，或依賴不存在時 agent 自己猜 | 只標「需要前一張建立的東西」；用上面的程式檢查波數 |
| 循環依賴 | 沒有任何票能開始 | 通常是兩張票各做了對方需要的一半，重新切 |
| 大範圍改名硬切垂直 | 每張票合進去 CI 都紅 | expand–contract |
| 跳過 prefactor 直接做功能 | 每張票都在跟同一段難改的程式搏鬥 | 先開一張行為不變的整理票 |

## 動手

1. 在 Playground 執行上面的分波程式，試著加一張「6：取消原因統計報表」，想想它該被哪些票阻擋，看它落在第幾波。
2. 刻意製造一個循環（讓票 1 也被票 4 阻擋），確認程式會報錯並列出卡住的票。
3. 挑一個需求（例如「醫師可以設定休診日」），寫出 4–6 張垂直切片票：每張要有行為描述、Blocked by、可以檢查的驗收項目，第一張要是最窄的完整路徑。
4. 為一個大範圍改名（例如 `amount` 改成 `amount_cents`）寫出 expand、各批遷移、contract 的票與阻擋關係。
