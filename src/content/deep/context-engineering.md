## 從一個具體問題開始：規範檔有九百行，agent 還是跑錯指令

掛號系統的 repo 根目錄有一份給 coding agent 讀的專案規範檔，兩年來每次 agent 做錯事，就有人往裡面加一段。現在它有九百多行。這個月發生了三件事：

- agent 每次改完程式都先跑 `make test`，失敗，再去翻 `pyproject.toml` 找到真正的指令。規範檔第 40 行寫的是 `make test`，但 Makefile 半年前就刪了。
- agent 直接修改了一支已經上線的 migration。「已合併的 migration 不得修改」寫在規範檔第 612 行，夾在一段講舊報表系統歷史的文字中間。
- 一段很長的對話裡，開頭交代過「這次不要動 `billing/`」。四十輪之後，agent 改了 `billing/` 裡的檔案。

第一件是內容過期，第二件是重點被稀釋，第三件是限制只存在於會被壓縮掉的對話裡。共同原因是：沒有人把「模型這一刻看得到什麼」當成要設計與維護的事。

## 模型只知道 context 裡的東西

模型對這個 repo 沒有記憶。每一次呼叫，它能依據的只有這次送進去的內容，也就是 **context**。走廊上講過的、上週另一段對話裡交代的、資深同事都知道的慣例，只要沒有出現在這次的 context 裡，對模型來說就不存在。

一個 coding agent 的 context 大致由這幾種東西組成：

| 組成 | 誰寫的 | 什麼時候進來 | 會一直留著嗎 |
|---|---|---|---|
| 系統指示 | 工具的開發者 | 每次呼叫 | 會 |
| 工具與 skill 的清單（名稱與說明） | 工具、團隊 | 每次呼叫 | 會 |
| 專案規範檔 | 團隊 | 依工具而定，通常在一開始 | 通常會 |
| 對話 | 使用者與模型 | 逐輪累積 | 太長時舊的會被摘要或截掉 |
| 工具結果（指令輸出、搜尋結果） | 執行環境 | 每次工具呼叫之後 | 同上，而且常常是最佔空間的 |
| 讀進來的檔案、skill 全文、文件 | repo、團隊 | 用到才讀 | 同上 |

兩個推論：

- **context 有上限，也有成本**。每一輪都把前面的內容重送一次（見 [Agent 的執行迴圈](#/skill/agent-loop)），放進去的每一段文字，之後每一輪都要再付一次。
- **放什麼、不放什麼、什麼時候放，是可以設計的**。這件事有人稱為 context engineering，對象是整個 context 的內容與來源，不只是 prompt 的措辭。

## 專案規範檔：該寫什麼、不該寫什麼

專案規範檔是放在 repo 裡、由 agent 工具自動讀進 context 的文字檔，例如 `CLAUDE.md`、`AGENTS.md`。**檔名只是例子**：每個工具讀哪些檔名、從哪些目錄讀、什麼時候讀、多份之間怎麼合併，規則都不同，要以所用工具的文件為準。下面講的是不分工具都成立的原則。

規範檔的特性是**常駐**：不管這次的任務是什麼，它都在。所以判斷一段內容該不該寫進去，只問一個問題：幾乎每個任務都需要它嗎？

該寫的：

| 內容 | 例子 | 理由 |
|---|---|---|
| 怎麼建置、怎麼測試 | 安裝依賴、跑單一測試、跑全部測試、跑 lint 的確切指令 | agent 每次改完都要驗證；指令猜錯就是浪費好幾輪 |
| 目錄結構的要點 | 哪個目錄放什麼、哪些檔案是產生出來的不要手改 | 省掉每次重新探索 |
| 不能做的事 | 不修改已合併的 migration、不改測試的期望值來讓測試通過、不碰某個目錄 | 這些從程式碼看不出來，做錯的代價高 |
| 決策去哪裡找 | ADR 的位置與索引、API 規格的位置 | 寫位置，不寫內容；見 [ADR](#/skill/ai-adr) |
| 完成的定義 | 回報完成之前要跑過哪些指令 | 讓「做完了」有可檢查的標準 |

不該寫的：

| 內容 | 問題 | 放哪裡 |
|---|---|---|
| 會過期的細節：版本號、目前的衝刺目標、負責人姓名 | 沒人會回來改，幾個月後就是錯的 | 不放，或放在本來就會更新的地方 |
| 長篇的背景與歷史 | 佔空間，把規則淹沒 | ADR 或文件，規範檔只留一行指過去 |
| 能從程式碼看出來的東西：函式清單、路由表、資料表欄位 | 和程式碼重複，程式一改就不同步 | 不放；agent 需要時自己讀程式碼 |
| 工具能機械檢查的規則：排版、import 順序、分層 | 寫成文字只是請求，不是約束 | formatter、linter、[架構測試](#/skill/architecture-tests) |
| 只有某類任務才需要的詳細步驟 | 其他任務白白帶著它 | skill 或文件，用到才載入 |
| 金鑰、密碼、內部網址的憑證 | 規範檔會進版控，也會被送進模型 | secret 管理工具 |

一份精簡的規範檔大概長這樣：

```markdown
# 掛號系統 API

## 指令
- 安裝依賴：`uv sync`
- 跑單一測試：`uv run pytest tests/test_x.py::test_name`
- 回報完成前：`uv run pytest` 與 `uv run ruff check .` 都要通過

## 目錄
- `src/appointments/`：掛號的領域邏輯，不直接 import web 框架
- `migrations/`：資料庫變更。已合併的檔案不得修改，要改就新增一支
- `src/generated/`：由 OpenAPI 規格產生，不要手改

## 規則
- 不修改既有測試的期望值；規範有變時先停下來說明
- 架構決策在 `docs/adr/`，索引是 `docs/adr/README.md`；改動相關模組前先讀
- 寫 migration 的詳細規則在 `docs/migrations.md`，寫 migration 時才讀
```

每一行不是指令，就是從程式碼看不出來的限制，或是指到別處的位置。

## 常駐與用到才載入

context 裡的東西可以分成兩種載入方式：

| | 常駐 | 用到才載入 |
|---|---|---|
| 例子 | 規範檔、工具與 skill 的清單 | skill 的全文、文件、ADR、原始碼 |
| 成本 | 每一次呼叫都付 | 只有用到的那幾次付 |
| 風險 | 寫太多會稀釋重點 | 該讀的時候沒讀 |
| 適合 | 短、穩定、幾乎每個任務都需要 | 長、只有特定任務需要 |

用到才載入的內容要靠**一行指標**讓 agent 知道它存在：規範檔寫「寫 migration 的規則在 `docs/migrations.md`」，或是 skill 的說明寫清楚「什麼時候用」。指標本身是常駐的，指過去的內容不是。這是 [Skill 與 MCP](#/skill/ai-skills-mcp) 那一課講的漸進載入：清單只佔一兩行，全文在任務相符時才進來。

指標太模糊，該讀的時候不會去讀。「相關文件在 docs/」沒有用；「改動付款流程前先讀 `docs/adr/0007-…`」才有用。

## 太長與過期的代價

**太長會稀釋重點**。規範檔越長，其中任何一條被遵守的把握越低，重要的規則夾在不重要的段落之間時尤其明顯。這沒有固定的門檻，不同模型與工具的表現也不一樣，但方向一致：每加一段，其他段落的份量就被分掉一些。開頭那條埋在第 612 行的 migration 規則就是這樣被忽略的。

**太長會比較貴**。常駐的內容每一輪都重送。一份 4,000 token 的規範檔，在一個跑 30 輪的任務裡是 12 萬 token 的輸入。供應商的前綴快取可以降低這部分的單價，但不會讓它消失，計費方式見 [FinOps](#/skill/finops)。

**過期的內容比沒有更糟**。這一點最容易被低估：

| 規範檔的狀態 | agent 的行為 |
|---|---|
| 沒寫測試指令 | 去讀 `pyproject.toml`、CI 設定，自己找出來。慢一點，但會對 |
| 寫了正確的指令 | 直接用 |
| 寫了過期的指令 | 照著跑、失敗、再想辦法；更糟的情況是舊指令還能跑，但跑的是不完整的測試 |

沒有資訊時，agent 會去查；有錯誤資訊時，它有憑有據地照著做。兩條互相矛盾的規則效果相同：模型會挑一條，而且不會說它挑了哪一條。

:::stop 讀到這裡可以先停：會判斷一段內容該不該進規範檔、用一行指標讓 skill 或文件用到才載入，也知道過期內容的代價。後面的目錄層級規範、子 agent 隔離與 context 組裝程式，在 repo 變大或長對話常被壓縮時再回來讀。

## 目錄層級的規範與繼承

大一點的 repo 裡，不同目錄的規則不一樣：前端目錄用的指令和後端不同，`migrations/` 有自己的限制。不少工具支援在子目錄放另一份規範檔，適用範圍是那個目錄底下的檔案；它什麼時候被讀進 context，依工具而定。

原則是：

- **根目錄放全專案都適用的**，子目錄只寫那個目錄的差異，不重複根目錄的內容。
- **越靠近程式碼的規則越具體**。「`migrations/` 的檔案合併後不得修改」放在 `migrations/` 的規範檔裡，比放在根目錄第 612 行有用。
- **不要寫互相矛盾的規則**然後指望優先順序來解決。上下層衝突時誰優先、子目錄的規範何時載入，各工具的規則不同，要查文件；最保險的做法是讓它們不衝突。

## 隔離與壓縮：子 agent 與摘要

context 快滿的時候，有兩種處理方式。

**用子 agent 隔離**。有些工作要讀很多東西，但最後只需要一個結論：在整個 repo 裡找某個函式的所有呼叫點、讀一份三千行的 log 找出第一個錯誤。把這種工作交給子 agent：它有自己獨立的 context，讀完之後只把結論交回來。主 agent 的 context 裡只多了幾行結論，而不是三千行 log。

代價有兩個：子 agent 看不到主對話，交辦時要把它需要知道的事（包括限制）寫完整；它交回來的是摘要，需要原文時要再去讀。多個 agent 同時改檔案的隔離是另一個問題，見 [多 agent 協作](#/skill/ai-multi-agent)。

**壓縮與摘要**。對話太長時，工具會把較舊的內容換成一段摘要（[Agent 的記憶](#/skill/agent-memory) 裡的滾動摘要）。摘要一定會丟東西，而且丟什麼不是你決定的。開頭第三件事就是這樣發生的：「不要動 `billing/`」在摘要裡消失了。

所以**不能丟的限制不要只放在對話裡**：

- 長期有效的，寫進規範檔。
- 只對這次任務有效的，寫進一個檔案（計畫、待辦、筆記），需要時重讀；檔案不會被摘要掉。
- 能機械檢查的，變成測試或 CI 檢查，讓違反時有東西會失敗。

## 規範檔是程式碼：版控、審查、清理、驗證

規範檔改變的是 agent 的行為，影響範圍是之後每一次在這個 repo 裡的工作。它應該得到和程式碼一樣的對待：

- **版控與審查**。規範檔的修改走 merge request，有人看過才合併。一行「測試失敗時可以跳過」的影響，比大多數程式碼的改動都大。從資安的角度，它也是行為層供應鏈的一部分，見 [行為層的供應鏈管理](#/skill/agent-supply-chain)。
- **每條規則要有來歷**。為什麼有這條、對應哪一份 ADR 或哪一次事故。沒有來歷的規則沒有人敢刪，規範檔就只會變長。
- **定期清理，並設觸發點**。排一個固定的週期檢查一次；另外，改了建置指令、搬了目錄、淘汰了某個模組的那一個 merge request，就要同時改規範檔。
- **機械檢查**。規範檔裡提到的路徑是否存在、有沒有驗證指令、長度有沒有超過團隊訂的上限、有沒有重複的段落，這些可以寫成腳本放進 CI。本課的程式題寫的是這個檢查。
- **改完要驗證**。改規範檔和改 prompt 是同一件事：行為可能變好，也可能在別的地方變壞。準備幾個固定的代表性任務，改動前後各跑一次比對結果，做法見 [Harness Engineering](#/skill/harness-engineering) 的評測集與回歸比對。

最後一個提醒：規範檔對 agent 是輸入，不是約束。它讀到了，大多數時候會照做，但沒有任何機制保證每一次都照做。真正不能違反的規則，要有測試或權限擋著。

## 實際程式：在預算內組裝 context

下面把一次呼叫前手上的片段列出來，依優先序在預算內放入，印出哪些被擠掉、哪些因為過期而不該放。真實的工具各有自己的組裝與壓縮方式，這段程式只是把「預算有限，所以要排優先序」這件事算出來。token 數都是示意。

```python run
# 一次呼叫前手上有這些片段。tokens 是估計值（示意）；stale 表示內容已經和現況不符。
FRAGMENTS = [
    {"name": "系統指示（工具內建）",        "kind": "system", "tokens": 1200},
    {"name": "專案規範檔",                  "kind": "rules",  "tokens": 3800},
    {"name": "規範檔裡的舊部署流程",        "kind": "rules",  "tokens": 900,  "stale": True},
    {"name": "這次的任務：取消掛號要寫稽核紀錄", "kind": "task", "tokens": 300},
    {"name": "skill：資料庫 migration 規則", "kind": "skill",  "tokens": 1500},
    {"name": "檔案 appointments/service.py", "kind": "file",   "tokens": 2600},
    {"name": "檔案 appointments/models.py",  "kind": "file",   "tokens": 1800},
    {"name": "工具結果：測試輸出（全文）",   "kind": "tool",   "tokens": 5200},
    {"name": "較早的對話（40 則）",          "kind": "history", "tokens": 6400},
    {"name": "最近的對話（6 則）",           "kind": "history_recent", "tokens": 1400},
]
# 優先序：數字小的先放。常駐的（system、rules）與這次的任務一定要在；舊對話最後才放。
PRIORITY = {"system": 0, "rules": 1, "task": 2, "history_recent": 3, "skill": 4, "file": 5, "tool": 6, "history": 7}

def assemble(fragments, budget):
    kept, dropped, stale, used = [], [], [], 0
    for f in sorted(fragments, key=lambda f: PRIORITY[f["kind"]]):   # sorted 是穩定排序，同類維持原順序
        if f.get("stale"):
            stale.append(f)            # 過期的不放：放進去模型會照著做
            continue
        if used + f["tokens"] <= budget:
            kept.append(f)
            used += f["tokens"]
        else:
            dropped.append(f)
    return kept, dropped, stale, used

def report(title, fragments, budget):
    kept, dropped, stale, used = assemble(fragments, budget)
    print(f"{title}（預算 {budget:,} token）")
    for f in kept:
        print(f"  放入  {f['tokens']:>5,}  {f['name']}")
    for f in dropped:
        print(f"  擠掉  {f['tokens']:>5,}  {f['name']}")
    for f in stale:
        print(f"  過期  {f['tokens']:>5,}  {f['name']}  ← 該從來源刪掉，不是每次組裝時跳過")
    always = sum(f["tokens"] for f in kept if f["kind"] in ("system", "rules"))
    print(f"  用掉 {used:,} / {budget:,}；其中常駐 {always:,}（{always / budget:.0%}），每一次呼叫都要付\n")

report("現況", FRAGMENTS, budget=16000)

# 整理之後：規範檔刪掉過期與重複的段落、把 migration 細節移到 skill；測試輸出只留失敗的那幾行
slim = [dict(f) for f in FRAGMENTS if not f.get("stale")]
for f in slim:
    if f["name"] == "專案規範檔":
        f["tokens"] = 900
    if f["kind"] == "tool":
        f["name"], f["tokens"] = "工具結果：測試輸出（只留失敗的 3 個案例）", 600
report("整理之後", slim, budget=16000)
```

「現況」那一輪被擠掉的是測試輸出，剛好是這次任務最需要的東西；常駐內容佔了預算的三成。整理之後常駐降到一成多，測試輸出放得進去。沒有換模型、沒有加大預算，只是決定了什麼東西值得佔位置。

## 常見錯誤

| 錯誤做法 | 會發生什麼 | 修正 |
|---|---|---|
| agent 每做錯一次就往規範檔加一段 | 檔案只會變長，重要的規則被淹沒 | 先問這條能不能變成測試或 lint；加一段時順手刪一段 |
| 把整份架構文件、API 清單貼進規範檔 | 每次呼叫都付費，而且和程式碼不同步 | 只留位置，內容用到才讀 |
| 改了建置指令，沒改規範檔 | agent 照舊指令跑，失敗或跑到不完整的檢查 | 指令和規範檔在同一個 merge request 裡改；CI 檢查規範檔裡的路徑與指令 |
| 重要的限制只在對話裡講一次 | 對話被摘要後限制消失 | 寫進規範檔、任務檔案，或變成測試 |
| 規則只寫「不要做 X」，不寫理由與替代做法 | agent 遇到非做不可的情況時自己找路 | 寫出理由與「需要例外時先停下來說明」 |
| 根目錄與子目錄的規範互相矛盾 | 行為取決於工具的合併規則，沒人預期得到 | 子目錄只寫差異；矛盾在審查時擋下 |
| 把規範檔當成安全邊界 | 規則被忽略時沒有任何東西失敗 | 不能違反的事用測試、權限、CI 擋 |

## 動手

1. 執行上面的程式，把 `budget` 改成 12000，看「現況」還有哪些被擠掉；再把規範檔的 token 改回 3800、只精簡測試輸出，比較兩種整理各自的效果。
2. 在 [Playground](#/playground?lang=python) 改 `PRIORITY`，讓工具結果的優先序高於檔案，觀察哪個檔案被擠掉，想一想這對「取消掛號要寫稽核紀錄」這個任務是好是壞。
3. 打開手邊一個專案的規範檔，逐段問三個問題：幾乎每個任務都需要嗎？現在還是對的嗎？能不能改成測試或 lint？
4. 做本課的程式題：寫一個規範檔的 lint。接著讀 [Harness Engineering](#/skill/harness-engineering)，把「改規範檔之後行為有沒有變壞」變成可以重跑的評測。
