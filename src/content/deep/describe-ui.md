## 從一個具體問題開始：「做一個今日門診的頁面」

給 AI 的需求只有一句：「用 Vue 做一個今日門診的頁面，列出預約，可以報到。」產出能跑，畫面也不難看，接上實際的後端之後問題一個個出現：

- 表格用的欄位是 `patient.fullName`、`doctor.name`，後端實際回的是 `patientName`，畫面一整欄空白。
- 沒有載入中、沒有資料、載入失敗的畫面。網路慢的時候白一片，失敗的時候也白一片。
- 「報到」按下去跳出一個用 `<div>` 疊出來的確認框，按 Esc 關不掉，Tab 會跑到後面的表格。
- 手機上表格比螢幕寬，整頁可以左右滑。
- 錯誤訊息是英文的「Something went wrong」。

這些都不是寫錯，是描述裡沒寫。沒寫到的部分，模型只能自己決定。把畫面拆成固定的幾段來描述，每一段都寫到能拿來驗收，產出才有東西可以對照。

## 運作原理：五段加兩項

| 段落 | 寫什麼 | 沒寫時常見的產出 |
|---|---|---|
| 版面 | 畫面分成哪些區域、彼此的位置 | 版面隨機，每次重新產生都不一樣 |
| 元件 | 每個區域用哪個元件 | 用 `<div>` 自己拼出 Dialog、Tabs，沒有鍵盤操作 |
| 狀態 | loading、empty、error、disabled、selected | 只有成功的畫面 |
| 資料 | API 路徑、欄位、範例值、顯示格式 | 自己編欄位名稱 |
| 互動 | 操作之後畫面怎麼變、送什麼請求、焦點去哪 | 點了有反應，但網址、焦點、錯誤處理不一定 |
| 斷點 | 390、768、1280 時版面怎麼變 | 只有桌機版 |
| 文案 | 按鈕、標題、空狀態、錯誤訊息的實際文字 | Lorem ipsum 或英文的預設訊息 |

### 版面：用文字畫出區域

不需要設計稿，用幾行文字或 ASCII 就能表達區域與相對位置：

```text
┌──────────────────────────────────────────────┐
│ 頁首：今日門診　11/20（四）　［前一天］［後一天］ │
├──────────────────────────────────────────────┤
│ Tabs：101 內科　102 小兒科　103 骨科            │
├──────────────────────────────────────────────┤
│ Data table：時間　病患　狀態　操作              │
│ 09:00　王○明　［候診］　［報到］               │
│ 09:15　陳○華　［已報到］                       │
└──────────────────────────────────────────────┘
```

寫出區域的名字（頁首、Tabs、Data table），之後描述狀態與互動時可以直接指名「Data table 載入中時……」。

### 元件：用名字取代形容

| 口語的說法 | 元件名稱 |
|---|---|
| 一排可以切換的標籤 | Tabs |
| 跳出來要你按確定的框 | 確認 Dialog（modal） |
| 角落跳出來、幾秒後消失的訊息 | Toast |
| 打字時下面跳出建議的輸入框 | Combobox（Autocomplete） |
| 小小的彩色狀態標籤 | Badge |
| 載入時灰色的方塊 | Skeleton |
| 滑鼠移上去出現的說明 | Tooltip |
| 從側邊滑出來的面板 | Drawer |
| 可以排序、勾選的表格 | Data table |
| 換頁的頁碼 | Pagination |

名字帶著一整套慣例。說「確認 Dialog」，產出比較可能用原生 `<dialog>` 的 `showModal()`、按 Esc 關閉、焦點留在對話框裡；說「跳出一個框」，產出可能只是一個絕對定位的 `<div>`。各元件的鍵盤操作慣例，可以查 WAI-ARIA Authoring Practices 的 Patterns。

### 狀態：每個區塊一張小表

| 區塊 | loading | empty | error | 其他 |
|---|---|---|---|---|
| Data table | 5 列 Skeleton，列高與資料相同 | 「這個診間今天沒有預約」 | inline Alert「預約清單暫時無法載入」＋重試 | 報到中的那列按鈕停用、顯示「報到中…」 |
| Tabs | 顯示診間名稱，數字先不顯示 | 沒有診間時整個 Tabs 隱藏 | 同 Data table | 目前的 Tab 用 `aria-selected="true"` |

狀態寫成表，漏掉的格子一眼看得出來；細節見 [互動狀態](#/skill/ui-states) 與 [API 的四種狀態](#/skill/api-states)。

### 資料：附一筆實際的回應

```text
GET /api/appointments?date=2026-11-20&clinic=101

[
  { "id": 501, "time": "09:00", "patientName": "王○明", "status": "booked" },
  { "id": 502, "time": "09:15", "patientName": "陳○華", "status": "checked_in" }
]
```

再寫出顯示規則：時間用 24 小時制、`status` 對應的中文與 Badge 顏色（`booked` 候診、`checked_in` 已報到、`cancelled` 已取消）、姓名已由後端遮罩、前端不再處理。有 OpenAPI 規格時直接附上對應的 schema。

### 互動：寫成「按下……之後……」

- 按下 Tab：網址的 `clinic` 改成該診間（`?clinic=102`），重新抓清單；重新整理後停在同一個 Tab。
- 按下「報到」：按鈕停用並顯示「報到中…」，送 `POST /api/appointments/{id}/check-in`；成功後該列變成「已報到」，顯示 Toast「王○明 已報到」；失敗時在該列下方顯示原因。
- 按下「前一天」：日期減一天，清單回到 loading。
- 只用鍵盤時：Tab 能走到每個按鈕，焦點看得見；Tabs 用左右鍵切換。

### 斷點與文案

斷點寫三個寬度就夠用：390（手機）、768（平板直放）、1280（筆電）。每個寬度寫出會變的東西，例如「390 時 Data table 改成卡片清單，一張卡片一筆預約；Tabs 可以橫向捲動」。

文案寫實際的字，包含空狀態與錯誤。「顯示適當的錯誤訊息」不能驗收，「預約清單暫時無法載入」可以。

### 驗收條件：每段一條以上

| 段落 | 驗收條件 |
|---|---|
| 版面 | 1280 時頁首、Tabs、Data table 由上而下排列 |
| 元件 | 確認報到用 `<dialog>`，按 Esc 會關閉，焦點回到原本的按鈕 |
| 狀態 | 封鎖清單 API 後顯示錯誤與重試，不是「沒有預約」 |
| 資料 | Network 分頁的回應欄位與程式使用的欄位一致 |
| 互動 | 切 Tab 後重新整理，停在同一個 Tab |
| 斷點 | 390 時沒有水平捲軸 |
| 文案 | 畫面上沒有英文的預設訊息或 Lorem ipsum |

## 實際範例：一份完整的描述

```text
頁面：今日門診（路由 /today，Vue 3.5、<script setup>、專案的元件庫 token）

版面：上方頁首（標題「今日門診」、日期、前一天／後一天按鈕），下面是診間 Tabs，Tabs 下面是預約 Data table。

元件：Tabs、Data table（欄位：時間、病患、狀態 Badge、操作）、確認 Dialog（原生 <dialog>）、Toast、Skeleton。

資料：GET /api/appointments?date=YYYY-MM-DD&clinic=<id>，回傳
[{ "id": 501, "time": "09:00", "patientName": "王○明", "status": "booked" }]
status 對應：booked 候診（灰）、checked_in 已報到（綠）、cancelled 已取消（刪除線）。

狀態：
- 載入中：5 列 Skeleton，列高與資料列相同。
- 沒有資料：「這個診間今天沒有預約」。
- 失敗：表格位置顯示「預約清單暫時無法載入」與「重試」；403 時顯示後端回的 title，不給重試。
- 報到中：該列的「報到」按鈕停用、文字「報到中…」。

互動：
- 切 Tab：網址 ?clinic= 跟著變，重新抓清單。
- 報到：按鈕 → 確認 Dialog「確定為 王○明 報到？」→ POST /api/appointments/{id}/check-in → 成功後該列狀態改為已報到、Toast「王○明 已報到」；失敗時在該列下方顯示原因。
- Dialog 開啟時焦點在「確定」，Esc 關閉，關閉後焦點回到原本的按鈕。

斷點：390 時表格改成卡片清單，Tabs 可以橫向捲動；768 以上用表格。

驗收：390／768／1280 都沒有水平捲軸；只用鍵盤能完成報到；封鎖 API 時顯示錯誤不是空狀態；Console 沒有 [Vue warn]。
```

一次給全部，產出容易變成一個很長的單一元件。可以分次給：先版面與元件（用寫死的假資料），再接資料與狀態，最後互動與斷點；每一次都對照驗收條件看過再進下一步。

## 常見錯誤

- **用形容詞代替規格**：「簡潔」「現代感」「好用」無法驗收。改寫成元件、間距 token、字級。
- **只描述成功的畫面**：沒寫 loading、empty、error，產出就沒有。每個會呼叫 API 的區塊都要有狀態表。
- **沒給資料形狀**：模型會自己編欄位，畫面上出現空白或 `undefined`。附一筆實際的回應。
- **只想到桌機**：沒寫斷點，產出多半只照桌機寬度排；390 時表格撐出水平捲軸。
- **文案留空**：產出用英文預設文字或 Lorem ipsum。空狀態與錯誤訊息最常被漏掉。
- **一次要整個系統**：描述越長，產出的單一檔案越大，越難驗收。一次一個畫面，一個畫面分幾步。
- **和專案規範衝突**：描述說「用 Tailwind」，專案用的是元件庫與 CSS 變數。共通的規範（框架版本、元件庫、token、禁止事項）放在專案規範檔，畫面描述只寫這個畫面。

## 動手

1. 挑一個自己常用的網頁（訂票、網路銀行、電商的訂單頁），照五段加兩項寫成描述，再對照實際畫面檢查漏了什麼，最常漏的是狀態與斷點。
2. 把同一個需求用一句話與完整描述各給 AI 一次，用上面的驗收條件表逐條比對兩份產出。
3. 把 [API 的四種狀態](#/skill/api-states) 實驗室裡每個狀態的驗收條件，改寫成自己畫面的版本。
4. 接著讀 [AI 寫前端的常見錯誤](#/skill/ai-common-mistakes)：描述寫清楚之後，產出還是會有固定幾類錯，要用工具抓。
