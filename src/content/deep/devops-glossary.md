## 從一個具體問題開始：一場聽得懂每個字、卻抓不到重點的會議

一家醫院的資訊部開週會，議程上有三件事：

1. 「掛號系統下週二晚上的 change window 要上新版，pipeline 已經綠了，artifact 會先晉升到 staging 驗一天。」
2. 「上次檢驗報告系統的事故 RCA 還沒結案，postmortem 裡有三個 action item 沒人認領。」
3. 「明年要上 Kubernetes，廠商報價的叢集是三台 master、六台 worker，說可以做到 HA，但 DR 要另外報。」

每個字都聽過，但如果不知道這些詞背後在**決定什麼**，就沒辦法判斷這三件事有沒有問題。例如第 1 項沒有提到 rollback 要怎麼做；第 2 項的 action item 沒人認領，代表同樣的事故會再發生；第 3 項「HA 有、DR 另外報」的意思是：同一個機房裡壞一台機器沒事，整個機房斷電就全停。

這一課把維運會議的常見詞分成六組。每個詞給三件事：**意思**、**會議上通常在決定什麼**、**可以追問的問題**。

## 交付：程式碼怎麼變成線上服務

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| pipeline（管線） | push 程式碼後自動執行的一串 job：lint、測試、build、部署 | 哪些檢查是必過的、哪些步驟要人工按 | 「pipeline 綠了」包含哪些測試？有沒有整合測試？ |
| job / stage | job 是一個執行單位；stage 是一組可以平行跑的 job | 哪些步驟可以平行以縮短時間 | 一次 pipeline 要跑多久？最慢的是哪一步？ |
| artifact | job 產出、後續要用的東西：container image、安裝包、測試報告 | artifact 存哪裡、保留多久、用什麼版本號 | 正式環境跑的是哪一個 artifact？能對回哪一個 commit？ |
| container registry | 存放 container image 的倉庫（GitLab Container Registry、Harbor、雲端廠商的 registry） | 用哪一個、要不要放內網、誰能推誰能拉 | image 有沒有掃描弱點？舊 image 保留多久？ |
| environment（環境） | 同一套系統的不同部署：dev、test、staging、prod | 要有幾個環境、各自的資料從哪來 | staging 的資料跟正式環境像不像？有沒有用到真實個資？ |
| 環境晉升（promotion） | **同一個** artifact 依序部署到 staging、再到 prod，只換設定不重 build | 晉升條件：測過什麼、誰核准 | prod 的 image 和 staging 驗過的是不是同一個 digest？ |
| rollback（回滾） | 出問題時退回上一版 | 退版要多久、誰能決定退 | 這次有資料庫 migration 嗎？新版寫入的資料，舊版讀得懂嗎？ |
| roll forward | 不退版，直接修好再上一版 | 問題小、修得快時，比回滾安全 | 修一版要多久？期間影響多大？ |
| 藍綠部署 / canary | 藍綠：新舊兩套並存、一次切流量；canary：先給少量流量試 | 要不要多花資源換取快速切換 | 切換是改 DNS 還是改負載平衡？DNS 的 TTL 多長？ |

「環境晉升」是最常被誤解的詞。如果每個環境各自從原始碼重新 build，staging 測過的東西和上線的東西就不是同一個——相依套件可能在兩次 build 之間更新了。站上 [環境、secrets 與 artifact](#/skill/environments-secrets) 有更完整的說明。

## 基礎建設：機器、網路、設定怎麼管

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| IaC（Infrastructure as Code） | 用檔案描述基礎建設（主機、網路、DNS、權限），交給工具建立與修改，例如 Terraform / OpenTofu、Ansible | 哪些資源要納管、手動改過的怎麼處理 | 現在的環境能從檔案重建出來嗎？有人手動改過嗎？ |
| GitOps | 把「叢集應該長怎樣」放在 git，由工具（例如 Argo CD、Flux）持續比對並套用到叢集 | 部署權限從「人有叢集帳號」變成「人能合併 MR」 | 誰能核准合併？緊急時怎麼繞過、繞過之後怎麼補回 git？ |
| 設定漂移（drift） | 實際環境和檔案描述的不一致 | 要不要定期偵測、發現時以誰為準 | 上一次偵測漂移是什麼時候？ |
| VM / 容器 | VM 有自己的作業系統核心；容器共用主機核心、用 namespace 與 cgroup 隔離 | 新系統用 VM 還是容器部署 | 這個系統有沒有容器化？image 誰維護？ |
| 資源配額（quota） | 限制一個專案或 namespace 最多能用多少 CPU、記憶體、儲存 | 各單位分到多少資源、超用怎麼辦 | 配額是依據什麼估的？尖峰時夠不夠？ |
| requests / limits | Kubernetes 裡，requests 是排程時保留的資源，limits 是上限 | 每個服務要保留多少 | 記憶體超過 limit 會被 OOMKilled，這個數字怎麼來的？ |

IaC 和 GitOps 都在解決同一個問題：**沒人說得清楚現在的環境長什麼樣**。手動改過幾次之後，正式環境就成了沒有人敢動、也沒有人能重建的東西。追問「能不能重建」是檢驗這件事最快的方法。

## 網路：封包怎麼走到服務

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| DNS 記錄 | 名字對應到位址的設定：A（IPv4）、AAAA（IPv6）、CNAME（別名）、PTR（反查）、TXT（驗證用） | 新系統用什麼網域名稱、內外網是否不同 | TTL 設多少？改記錄後多久生效？ |
| split-horizon DNS | 同一個名字在內網、外網解析到不同位址 | 內網使用者連內部 IP、外部使用者走公開入口 | 從外網和內網各查一次，結果一樣嗎？ |
| VLAN | 在同一組實體交換器上切出邏輯上隔離的網段 | 新主機放在哪個網段（例如伺服器區、DMZ、醫療設備區） | 這個網段和資料庫網段之間的規則誰管？ |
| 防火牆規則 | 「來源、目的、port、協定、允許或拒絕」的一條規則 | 開哪些 port 給誰 | 是開特定來源還是 any？有到期日嗎？誰申請的？ |
| DMZ | 放對外服務的隔離網段，外網能進、內網要再經過一道防火牆 | 對外系統放 DMZ 還是走反向代理 | DMZ 的主機能主動連到內網哪些地方？ |
| proxy / 反向代理 | 正向 proxy 代表用戶端連外；反向代理代表伺服器接請求，例如 [nginx](#/skill/nginx) | 對外入口統一由誰處理 TLS 與路由 | 伺服器連外（例如下載套件）要不要經過 proxy？ |
| 負載平衡（LB） | 把流量分給多台後端，剔除健康檢查失敗的 | L4（看 IP 與 port）還是 L7（看 HTTP 路徑與 Host） | 健康檢查打哪個網址？後端全掛時回什麼？ |
| 憑證（certificate） | 證明「這個網域是這台伺服器」的文件，由 CA 簽發 | 買哪種、誰負責續約 | 到期日在哪裡監控？過期時誰會收到通知？ |

會議上講「網域不通」時，可能是 DNS 沒建、防火牆沒開、憑證過期或後端掛了，處理的人完全不同。[網路通不通](#/skill/network-troubleshooting) 那一課把每一層壞掉時的錯誤長相列出來；憑證的細節在 [HTTPS 憑證](#/skill/https-certificates)。

## 可靠度：多可靠才算夠、壞了能多快好

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| SLI | 服務水準指標：實際量到的數字，例如成功請求比例、延遲 | 量什麼才代表使用者體驗 | 這個數字是從使用者端量還是從主機量？ |
| SLO | 服務水準目標：內部訂的目標，例如「30 天內 99.9% 請求成功」 | 目標訂多高、達不到時怎麼辦 | 過去三個月實際是多少？ |
| SLA | 服務水準協議：寫進合約、達不到有罰則的承諾 | 跟廠商簽多少、對使用單位承諾多少 | 罰則是什麼？量測方式由誰決定？計畫性停機算不算？ |
| 錯誤預算 | 1 − SLO，例如 99.9% 一個月約 43 分鐘 | 預算用完時要不要暫停新功能上線 | 預算用完由誰決定凍結？ |
| HA（高可用） | 同一地點內消除單點故障：多台、多副本、自動切換 | 哪些元件要做備援 | 資料庫有備援嗎？切換要手動還是自動、要多久？ |
| DR（災難復原） | 整個站點失效時，在另一個地點恢復 | 要不要有異地機房或雲端備援 | 上次 DR 演練是什麼時候？實際花了多久？ |
| RPO | 最多能遺失多長時間的資料 | 備份與複寫的頻率 | 每天備份一次，代表最多可能遺失一天的資料，可以接受嗎？ |
| RTO | 從失效到恢復服務最多多久 | 備援架構與演練方式 | 這個數字有演練驗證過，還是估的？ |

SLA、SLO、SLI 的關係：SLI 是溫度計的讀數，SLO 是自己訂的體溫目標，SLA 是跟別人簽的保證。SLO 通常訂得比 SLA 嚴，留一段緩衝。

HA 和 DR 最常被混用。三台機器放在同一個機房叫 HA，機房停電時三台一起停；DR 要回答的是「這個機房整個不能用時怎麼辦」。**備份也不等於 DR**：備份檔還在，但沒有可以還原的機器、沒演練過還原流程，RTO 就是未知數。另外，複寫（replication）不能取代備份：誤刪的資料會被忠實地複寫到備援端。

## 事故與變更：出事時誰做什麼、上線前誰核准

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| on-call | 輪值待命，告警時負責第一時間處理 | 輪班表、升級路徑、補休 | 告警來了，on-call 有 runbook 可以照著做嗎？ |
| runbook | 特定告警或作業的處理步驟 | 哪些告警需要先寫好 runbook | 最近一次照 runbook 處理，步驟還正確嗎？ |
| 事故分級（SEV） | 依影響範圍與嚴重度分級，決定動員多少人 | 這次算幾級、要通知到誰 | 分級標準是書面的嗎？ |
| RCA | 根本原因分析：找出「為什麼會發生」而不只是「哪裡壞了」 | 原因找到哪一層才算完 | 是「某人操作錯誤」就結案，還是追到為什麼系統允許這個錯誤？ |
| postmortem | 事故檢討文件：時間線、影響、原因、改善項目 | 改善項目誰負責、何時完成 | 上一次 postmortem 的改善項目都完成了嗎？ |
| 變更申請 / CAB | 上線前的申請與審核；CAB 是變更諮詢委員會 | 這個變更的風險等級、要誰核准 | 回復計畫是什麼？誰有權決定回復？ |
| change window | 允許做變更的時段，通常在離峰 | 什麼時候上線、多長 | 時段內做不完怎麼辦？超時算失敗還是延長？ |
| 凍結期（freeze） | 一段不允許一般變更的期間 | 哪些日子凍結、例外怎麼核准 | 緊急修補在凍結期怎麼走流程？ |

「不咎責」（blameless）是 postmortem 的核心原則：寫的是系統哪裡允許錯誤發生，不是誰犯了錯。如果檢討會變成追究個人，下一次就沒有人會說實話。細節在 [事故處理、on-call 與 postmortem](#/skill/incident-response) 與 [受監管環境的變更管理](#/skill/change-management)。

## 資料平台：數據中台會議上的詞

| 詞 | 意思 | 會議上在決定什麼 | 可以追問 |
|---|---|---|---|
| 數據中台 | 把各系統的資料集中、整理成共用的資料服務與指標 | 先接哪些系統、做哪些報表 | 指標定義由誰訂？各系統的代碼對得起來嗎？ |
| ETL / ELT | 抽取、轉換、載入；ELT 是先載入再在目的地轉換 | 多久同步一次、在哪裡轉換 | 來源系統改欄位時，誰會知道？ |
| 資料倉儲 / 資料湖 | 倉儲放整理過、結構化的資料；湖放原始格式的大量資料 | 要整理到什麼程度才放進去 | 放進去之後誰負責品質？ |
| 主資料（master data） | 全組織共用的核心資料：病人、員工、科別、代碼表 | 哪一個系統是「正本」 | 同一個病人在兩個系統的資料不一致時，以誰為準？ |
| 資料擁有者 / 資料管理員 | 擁有者決定定義與存取，管理員負責日常品質 | 每份資料歸誰 | 這張表的擁有者是誰？ |
| 去識別化 | 移除或替換能識別個人的欄位 | 分析環境能看到什麼 | 去識別化之後還能不能回推？對照表誰保管？ |

這組詞的共同問題是「**誰負責**」。數據中台在技術上不難，難的是每個指標、每張表都要有人能說明定義、能為數字負責。[數據中台之前：資料治理](#/skill/data-governance) 有更完整的說明。

## 常見的誤用與該警覺的說法

| 會議上的說法 | 問題在哪 | 可以怎麼回應 |
|---|---|---|
| 「有備份，所以有 DR」 | 備份只是資料；DR 還需要能還原的機器、流程與演練 | 「上次從備份還原整套系統花了多久？」 |
| 「三台主機，所以是 HA」 | 三台都依賴同一個資料庫、同一台儲存或同一條網路，仍是單點 | 「這三台共用哪些東西？那些東西壞了會怎樣？」 |
| 「SLA 99.9%」 | 沒說量測方式、期間、計畫性停機算不算，數字沒有意義 | 「怎麼量？多長期間？達不到時的罰則是什麼？」 |
| 「出問題就 rollback」 | 有資料庫 schema 變更時，程式退版不一定能退資料 | 「這次的 migration 能不能退？新舊版能不能同時跑？」 |
| 「pipeline 綠了就能上」 | 綠燈只代表有寫的測試通過，沒寫的部分沒驗 | 「這次改的地方有測試覆蓋嗎？」 |
| 「防火牆開 any 比較方便」 | 任何來源都能連，一台主機被入侵就能橫向移動 | 「來源能縮到哪幾個網段？規則有沒有到期日？」 |
| 「憑證快到期，到時候再換」 | 到期日當天才處理，任何一步卡住就是事故 | 「續約有自動化嗎？到期前多久會告警？」 |

## 動手

1. 拿最近一次會議的紀錄，把裡面的詞標出來，對照上面的表，替每個詞寫下一個還沒被回答的追問。
2. 替一個熟悉的系統寫下三個數字：SLO、RPO、RTO。寫不出來，或寫出來之後發現沒人量過，就是下一次會議可以提的議題。
3. 接著讀 [網路通不通](#/skill/network-troubleshooting)，把「網域不通」拆成可以逐層檢查的問題。
