## 從一個具體問題開始：付款成功了，訂單卻顯示失敗

訂單服務呼叫付款服務扣款，設定 3 秒逾時。某次付款服務剛好變慢，第 3.2 秒才扣款成功並回應，但訂單服務在第 3 秒已經放棄：把訂單標成「付款失敗」，畫面請使用者重試。使用者再按一次，又扣了一次款。

從訂單服務的角度，「逾時」可能代表三種完全不同的狀況：

| 狀況 | 付款服務做了沒 | 訂單服務看到的 |
|---|---|---|
| 請求在網路上遺失 | 沒做 | 逾時 |
| 付款服務做完了，回應在路上遺失 | 做了 | 逾時 |
| 付款服務還在做，只是很慢 | 還不知道，可能等一下就做完 | 逾時 |

三種狀況看起來一模一樣。單機程式呼叫一個函式，要嘛回傳、要嘛丟例外；跨過網路，多了第三種結果：**不知道**。分散式系統的大部分困難，都從這裡開始：部分失敗、無法區分慢與死、各主機對「現在幾點」沒有共識。

這一課整理幾個基礎概念：網路分區與 CAP、一致性模型、時鐘、訊息傳遞的語意，以及跨服務的交易。

## 網路分區與部分失敗

單機系統的失敗通常是全有全無：程序當掉，一切都停。分散式系統則是**部分失敗**：某台主機慢了、某條網路斷了、某個服務回錯誤，其他部分照常運作。

**網路分區**（network partition）是部分失敗的一種：主機都還活著，但一部分主機和另一部分之間無法通訊。例如兩個機房之間的線路中斷，兩邊各自正常，但互相看不到。從任一邊看，對面「沒有回應」，無法知道對面是掛了，還是只是連不到。

處理部分失敗的基本工具：

- **每個跨網路的呼叫都要有逾時**。沒有逾時，一個慢的依賴會把呼叫端的 worker 全部卡住。
- **逾時之後不能假設「沒做」**。要嘛去查對方的狀態（「這筆付款的結果是什麼」），要嘛用同一個冪等鍵重試，讓對方自己判斷是不是重複。
- **重試要退避、要有上限**，避免在對方已經過載時加倍施壓（見 [錯誤處理與韌性](#/skill/resilience)）。

## CAP 的正確理解

CAP 定理常被簡化成「一致性、可用性、分區容忍，三個只能選兩個」。這個說法容易誤導。比較精確的版本：

- **C（Consistency）**：這裡指的是**線性一致性**（linearizability），所有讀取都像只有一份資料一樣，讀得到最新一次成功的寫入。跟 ACID 裡的 C（約束成立）不是同一件事。
- **A（Availability）**：每個送到「沒有故障的節點」的請求，都會得到非錯誤的回應。
- **P（Partition tolerance）**：網路分區發生時，系統還能繼續運作。

在多台主機透過網路溝通的系統裡，分區**一定會發生**，P 不是可以選擇放棄的選項。所以 CAP 真正說的是：**分區發生時，只能在 C 與 A 之間取捨**。

用一個例子說明。資料在兩個機房各有一份，機房之間斷線，一個使用者在機房 1 更新了資料：

- **選 C**：機房 2 無法確認自己的資料是不是最新的，所以拒絕讀寫（或只允許多數派那一邊寫入）。資料不會不一致，但部分使用者會收到錯誤。
- **選 A**：兩邊都照常接受讀寫。機房 2 的使用者讀到舊資料，甚至兩邊各自寫入了不同的值，分區恢復後要合併或解決衝突。

沒有分區的時候，C 與 A 可以同時擁有。這時的取捨變成**延遲與一致性**：要等所有副本都確認寫入（慢但一致），還是寫到一份就回應（快但副本可能落後）。PACELC 這個延伸的說法就是在描述這件事：分區時（P）在 A 與 C 之間選，否則（E）在延遲（L）與一致性（C）之間選。

所以「三選二」錯在兩個地方：P 不是選項；而且這個取捨只在分區時才存在。另外，把整個資料庫貼上「CP」或「AP」的標籤也過於粗略：同一個資料庫，讀主庫還是讀副本、寫入要幾個節點確認，都會改變它在分區時的行為。

## 一致性模型：強一致、最終一致與中間的選項

| 模型 | 保證什麼 | 例子 | 代價 |
|---|---|---|---|
| 強一致（線性一致） | 任何讀取都看得到最新一次成功的寫入，像只有一份資料 | 單一 PostgreSQL 主庫；Raft 共識系統（etcd 等）的線性一致讀取 | 每次寫入要等多數節點確認；分區時少數派那一邊無法服務 |
| 讀己所寫（read-your-writes） | 自己寫入的東西，自己之後一定讀得到；別人的寫入不保證 | 寫入後一段時間讀主庫；帶版本讀 | 要記住每個使用者的寫入位置或時間 |
| 單調讀（monotonic reads） | 不會先讀到新值、之後又讀到舊值 | 同一個使用者固定讀同一個副本 | 副本掛掉時要處理切換 |
| 最終一致 | 沒有新的寫入時，所有副本**最終**會一樣；過程中可能讀到舊值 | 非同步複製的副本、DNS、CDN 快取 | 應用程式要能接受短暫的舊資料 |

PostgreSQL 的串流複製預設是**非同步**的：主庫 commit 後就回應，副本稍後才套用。所以副本有延遲（replication lag），平常幾毫秒，主庫忙碌或網路不穩時可能好幾秒。可以設定同步複製（`synchronous_standby_names` 搭配 `synchronous_commit`），讓主庫等副本確認後才回應 commit，代價是每次寫入都變慢，而且同步副本不可用時寫入會卡住。

下面模擬一主一副本、延遲 3 個時間單位的情況，以及「帶版本讀」怎麼做到讀己所寫：

```python run
# 一主一副本、非同步複製：主庫的每次寫入要過 lag 個時間單位才會出現在副本
class Cluster:
    def __init__(self, lag: int):
        self.lag = lag
        self.log = []                 # 主庫的寫入紀錄：(版本, 寫入時間, key, value)
        self.version = 0

    def write(self, now, key, value) -> int:
        self.version += 1
        self.log.append((self.version, now, key, value))
        return self.version           # 像 PostgreSQL 的 LSN：這次寫入的位置

    def replica_version(self, now) -> int:
        applied = [v for v, t, _, _ in self.log if t + self.lag <= now]
        return max(applied, default=0)

    def read(self, now, key, node):
        upto = self.version if node == "primary" else self.replica_version(now)
        rows = [val for v, _, k, val in self.log if k == key and v <= upto]
        return rows[-1] if rows else None

c = Cluster(lag=3)
c.write(0, "nickname", "old")
c.write(10, "nickname", "Ann")       # 使用者在 t=10 改暱稱
for t in (10, 11, 13):
    print(f"t={t:2}  讀副本：{c.read(t, 'nickname', 'replica'):4}  讀主庫：{c.read(t, 'nickname', 'primary')}")

# 讀己所寫：帶著「我上次寫入的版本」讀；副本還沒追上就改讀主庫
def read_your_writes(c, now, key, min_version):
    node = "replica" if c.replica_version(now) >= min_version else "primary"
    return c.read(now, key, node), node

my_version = c.write(20, "nickname", "Annie")
for t in (20, 21, 23):
    print(f"t={t}  帶版本 {my_version} 讀：", read_your_writes(c, t, "nickname", my_version))
```

第一段的 t=10 與 t=11 就是「我剛存的怎麼不見了」：使用者改完暱稱，頁面重新載入時讀副本，看到的還是舊的。第二段帶著寫入時拿到的版本去讀，副本還沒追上時改讀主庫，副本追上後就能回到副本。PostgreSQL 裡對應的是 WAL 的位置（LSN）：寫入後取得 `pg_current_wal_lsn()`，讀取前比對副本的 `pg_last_wal_replay_lsn()`。各種做法的取捨，見設計情境 [讀寫分離後的「我剛存的怎麼不見了」](#/scenario/replica-consistency)。

## 時間：多台主機的時鐘不可信

每台主機的時鐘都會漂移，靠 NTP 定期校正。校正時時間可能**往回跳**；虛擬機暫停、主機負載過重時，程序也可能突然「失去」好幾秒。結果是：

- 兩台主機在「同一時刻」讀到的時間可能差幾毫秒到幾秒，設定錯誤時差更多。
- 同一台主機上，後讀到的時間不一定比先讀到的大。

所以有幾件事不能依賴牆上時鐘（wall clock）：

- **量時間間隔**：用 `time.monotonic()`，不要用 `time.time()` 相減。monotonic clock 保證不會往回走，但只在同一台主機、同一次開機內有意義。
- **決定事件的先後**：不同主機產生的時間戳不能拿來排序。
- **最後寫入者勝**（last write wins，LWW）：用時間戳決定哪個寫入留下來，時鐘慢的主機的寫入會被誤判成「比較舊」而丟掉。

需要排序或判斷先後時，改用：

- **單一來源產生的序號**：資料庫的自增 id、序列（sequence）、或由資料庫產生的 `now()`（同一台資料庫主機的時鐘）。
- **版本號**：每次更新加一，寫入時帶上「我讀到的版本」，不符就拒絕（樂觀鎖，compare-and-set）。
- **邏輯時鐘**：Lamport clock 讓每個節點維護一個計數器，送訊息時附上、收到時取 `max(自己, 收到的) + 1`。它能保證「有因果關係的事件順序正確」，但不代表真實時間。

下面這段比較 LWW 在時鐘偏差下會發生什麼，以及版本號怎麼避免：

```python run
# 兩台主機各自用自己的時鐘幫寫入蓋時間戳，「時間戳大的贏」（last write wins）
skew = {"host-a": 0.0, "host-b": -3.0}      # host-b 的時鐘慢 3 秒

def lww_write(store, host, real_time, value):
    ts = real_time + skew[host]              # 主機以為的現在
    if store.get("ts", float("-inf")) < ts:
        store.update(value=value, ts=ts)

store = {}
lww_write(store, "host-a", 100.0, "地址：台北市")     # 真實時間 100 秒
lww_write(store, "host-b", 101.0, "地址：新竹市")     # 1 秒後的新地址，經過 host-b
print("最後寫入者勝：", store["value"], "← 新地址被吃掉了")

# 改用版本號：寫入時帶上「我讀到的版本」，版本不符就拒絕（compare-and-set）
def cas_write(store, expected_version, value):
    if store["version"] != expected_version:
        return f"衝突：目前是版本 {store['version']}，你讀到的是 {expected_version}，請重讀再改"
    store.update(value=value, version=expected_version + 1)
    return f"成功，版本 {store['version']}"

store = {"value": "地址：台北市", "version": 7}
print("先讀到版本 7，改成新竹：", cas_write(store, 7, "地址：新竹市"))
print("另一個請求也以版本 7 為基礎改：", cas_write(store, 7, "地址：台中市"))
print("結果：", store)
```

時鐘也影響到「有到期時間的東西」：鎖的租約（lease）、token 的有效期限。持有分散式鎖的程序如果暫停了一陣子，醒來時以為自己還持有鎖，其實早已到期、被別人拿走。這是 [並發問題](#/skill/concurrency-bugs) 裡提到 fencing token 的原因。驗證 JWT 這類帶時間的 token 時，通常也會允許幾秒到幾十秒的誤差（leeway）。

## 訊息傳遞：至多一次、至少一次、恰好一次

服務之間傳遞訊息（HTTP 呼叫、佇列）時，依「失敗了會不會重送」分成三種語意：

| 語意 | 做法 | 結果 |
|---|---|---|
| 至多一次（at-most-once） | 送出去就不管，不重送 | 不會重複，但可能遺失 |
| 至少一次（at-least-once） | 沒收到確認就重送 | 不會遺失，但可能重複 |
| 恰好一次（exactly-once） | 網路層做不到，要靠接收端配合 | 端到端來說，靠「至少一次 + 接收端去重」達成 |

網路無法保證「恰好送達一次」：送出後沒收到確認，發送端無法知道是訊息遺失還是確認遺失，只能選擇重送（可能重複）或不重送（可能遺失）。大多數佇列系統提供的是至少一次。有些系統宣稱支援 exactly-once，但通常有適用範圍（例如只在該系統內部的「讀取 → 處理 → 寫回」）；一旦處理過程包含外部的副作用（寄信、扣款、呼叫第三方 API），仍然要靠接收端的冪等。

實務上的組合是：**至少一次傳遞 + 冪等的處理**。開頭的付款例子：訂單服務為每筆訂單產生一個冪等鍵，逾時後用同一個鍵重試；付款服務看到同一個鍵，不再扣款，直接回傳第一次的結果。做法見 [訊息佇列與背景工作](#/skill/queues-workers) 與設計情境 [付款請求的冪等與重試](#/scenario/idempotency)。

## 為什麼分散式交易很難

單一資料庫的交易保證原子性：全部成功或全部不算。當一個操作要同時改兩個資料庫，或一個資料庫加一個外部服務時，就沒有這個保證了。

### 兩階段提交（2PC）

兩階段提交由一個協調者（coordinator）主導：

1. **準備階段**：協調者問每個參與者「你能 commit 嗎」。參與者把交易準備好、寫進持久的紀錄、握著鎖，回答「可以」或「不行」。
2. **提交階段**：全部回答可以，協調者通知所有人 commit；任何一個說不行，通知所有人 rollback。

問題出在兩個階段之間：

- **協調者在準備之後掛掉**：參與者已經答應了「可以」，不能自己決定 commit 或 rollback（別的參與者可能已經收到相反的指令），只能**握著鎖一直等**協調者回來。這段時間內，被鎖住的資料誰都不能動。
- **可用性變成乘積**：每個參與者都必須在線才能完成交易，參與者越多，整體越容易失敗。
- **延遲**：至少多兩次網路往返，鎖握得更久。
- **支援有限**：大多數訊息系統、外部 API、許多 NoSQL 資料庫都不支援參與 2PC。

PostgreSQL 支援作為參與者的 `PREPARE TRANSACTION`，但預設是關閉的（`max_prepared_transactions` 預設為 0）。沒有被收尾的 prepared transaction 會一直握著鎖，並阻止 `VACUUM` 清理舊資料，要有機制監控與處理。

### Saga：本地交易加上補償

saga 把一個跨服務的操作拆成一串**本地交易**，每一步都在自己的資料庫裡獨立 commit。某一步失敗時，不是 rollback，而是依反向順序執行前面每一步的**補償動作**：

| 步驟 | 動作（本地交易） | 補償動作 |
|---|---|---|
| 1 | 訂單服務：建立訂單，狀態 `PENDING` | 把訂單改成 `CANCELLED` |
| 2 | 庫存服務：保留庫存 | 釋放保留的庫存 |
| 3 | 付款服務：扣款 | 退款 |
| 4 | 訂單服務：狀態改成 `CONFIRMED` | （最後一步，不需要） |

假設第 3 步扣款失敗（卡片被拒），saga 依序執行：釋放庫存（補償第 2 步）→ 訂單改成 `CANCELLED`（補償第 1 步）。

saga 的特性與要注意的地方：

- **補償不是 rollback**。第 1 步建立的訂單已經 commit，別人可能已經看到它。補償是一個新的動作，把狀態改成「取消」，資料上會留下痕跡。已經寄出的通知信收不回來，只能再寄一封「訂單已取消」。
- **中間狀態看得見**。所以要有明確的狀態欄位（`PENDING`、`CONFIRMED`、`CANCELLED`），畫面與其他流程要能處理「還在進行中」的訂單。
- **每一步與每個補償都要冪等**。它們是透過訊息或呼叫觸發的，一樣會重送。
- **補償也可能失敗**，要能重試，最後還失敗就需要人工處理。
- **編排方式**有兩種：由一個協調者依序呼叫每一步（orchestration，流程集中、容易追蹤），或每個服務完成後發出事件、下一個服務聽事件接著做（choreography，耦合少，但流程分散在各服務裡）。

每一步「改自己的資料庫並通知下一步」本身也是兩件事，要靠 **outbox 模式** 保證原子性：在同一個本地交易裡寫入業務資料與一筆「待發送的事件」，再由另一個程序把事件送出去。

## 常見錯誤與錯誤訊息

| 錯誤 / 現象 | 意思 | 怎麼處理 |
|---|---|---|
| `ReadTimeout`、`context deadline exceeded`、`504 Gateway Timeout` | 呼叫逾時，**結果未知** | 不要直接當作失敗；查詢對方的狀態，或用同一個冪等鍵重試 |
| PostgreSQL 副本上：`canceling statement due to conflict with recovery` | 在副本上執行的查詢，與主庫送來的變更（例如 VACUUM 清掉的列）衝突，被取消 | 重試；長查詢考慮 `hot_standby_feedback` 或調整 `max_standby_streaming_delay`，各有代價 |
| `cannot execute INSERT in a read-only transaction` | 寫入被送到了副本 | 檢查讀寫分流的設定：寫入與「寫完立刻讀」要走主庫 |
| `prepared transactions are disabled` | 使用 `PREPARE TRANSACTION`，但 `max_prepared_transactions` 是 0 | 確認真的需要 2PC；需要的話調整設定並監控未收尾的 prepared transaction |
| 「我剛存的怎麼不見了」 | 寫主庫、讀副本，副本還沒追上 | 讀己所寫的做法；監控複製延遲 |
| 資料被較舊的值蓋掉 | 用不同主機的時間戳做最後寫入者勝 | 改用版本號或資料庫產生的序號 |
| 故障切換後出現兩個主庫（split brain） | 舊主庫其實沒死，只是暫時連不到，兩邊都在接受寫入 | 故障切換要有隔離機制（fencing），確保舊主庫無法再寫入；使用經過驗證的高可用方案，不要自己寫切換腳本 |
| 帶時間的 token 被判定無效或「還沒生效」 | 簽發者與驗證者的時鐘有偏差 | 校正 NTP；驗證時允許小幅度的誤差 |

## 動手

1. 執行複製延遲那段，把 `lag` 改成 0 與 10，看副本什麼時候追上；把 `read_your_writes` 的判斷拿掉、一律讀副本，看 t=20 讀到什麼。
2. 執行時鐘那段，把 `host-b` 的偏差改成 `+3.0`，看看這次換成哪個寫入被吃掉。
3. 程式題「saga 的補償」：實作一個依序執行步驟、失敗時反向執行補償的函式。
4. 到設計情境 [讀寫分離後的「我剛存的怎麼不見了」](#/scenario/replica-consistency) 比較讀主庫、帶版本讀與接受最終一致的取捨。
