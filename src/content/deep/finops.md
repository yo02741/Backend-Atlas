## 從一個具體問題開始：帳單比預估多了三倍

一個團隊把三個內部服務搬上雲，又導入一個 agent 每天自動整理工單。上線前估的月費是根據「三台機器 × 一個月」算的。第一個月的帳單出來，總額是預估的三倍，拆開來看：

- 機器費用和預估差不多。
- 多出一大筆「資料傳輸」：服務每天把報表匯出給機房裡的舊系統，走的是公網出站流量。
- 有兩顆磁碟和一堆快照還在計費，對應的機器早在測試完就刪了。
- 測試環境的資料庫一整個月沒關，週末也在跑。
- agent 的 API 費用遠高於試用時的估計：試用時每次只跑兩三輪，正式上線後一次工作跑十幾輪，每一輪都把前面的對話歷史全部重送。

沒有一項是「被收了不該收的錢」，每一項都是照計費規則算出來的。問題在於估算時只看了最顯眼的那一項，而且帳單只有一個總額，看不出哪個服務、哪個團隊花了多少。

FinOps 處理的就是這件事：先搞清楚計費結構，讓每一筆花費看得見、對得到人，再談怎麼省。本課不寫任何具體價格——價格因供應商、地區、方案而異，也經常調整，估算時一律以官方價目表為準。

## 雲端帳單的計費項目

雲端大部分服務是**用量計費**：用多少、用多久、搬多少。主要的計費項目可以歸成幾類：

| 類別 | 怎麼計 | 容易漏掉的地方 |
|---|---|---|
| 運算 | 機器規格 × 開機時間；容器或函式服務按 vCPU 與記憶體的秒數、或按呼叫次數 | 機器「停止」與「刪除」不一樣：有些服務停止後不收運算費，但掛載的磁碟照收 |
| 儲存 | 容量 × 時間；不同儲存等級單價不同 | 物件儲存另外按請求次數收費；快照、備份、舊版本物件都佔容量 |
| 流量 | 依方向與目的地計費 | **出站流量**（從雲端到網際網路、或跨地區）通常要錢，入站多半免費；跨可用區也可能收費 |
| 請求數與單位 | 託管服務按請求、讀寫單位、訊息數計費 | 小程式迴圈裡每秒呼叫一次，累積起來可觀 |
| 託管服務的固定費用 | 負載平衡器、NAT gateway、託管資料庫依時數計 | 就算沒有流量，開著就有基本費 |

流量值得多說一句。很多架構圖只畫出元件，沒畫出資料往哪裡流。服務放在 A 地區、資料庫在 B 地區，或每天把大量資料從雲端拉回機房，這些在架構圖上看不出來，在帳單上會很明顯。估算時要問的是：每天有多少資料離開這個地區、離開這個雲？

### 折扣：用承諾換價格

各家雲端都有「承諾用量換折扣」的機制，名稱不同（保留執行個體、承諾使用折扣、節省方案之類），概念相近：

- 你承諾一段期間（常見是一年或三年）至少用某個量，換取比隨用隨付低的單價。
- 用不到承諾的量，差額照付。
- 另一類是**可中斷的機器**（spot / preemptible）：價格低，但雲端隨時可以收回，只適合可以重做的批次工作。

這些機制適合**穩定的基礎負載**：二十四小時都在跑的資料庫、固定的幾台應用伺服器。用量還在變、或還不確定架構會不會改時，先不要承諾。各家的規則、可轉換性、適用範圍差異很大，簽之前要讀清楚條款。[部署模式的成本比較](#/skill/hosting-models) 討論了用量曲線與自建、託管之間的取捨，這裡不重複。

## AI 工具與 API 的計費

模型 API 的計費單位是 **token**（模型切分文字的單位；中文一個字常常不只一個 token，實際切法依模型而定）。主要的計費項目：

| 項目 | 說明 |
|---|---|
| 輸入 token | 每次呼叫送出去的所有內容：系統提示、工具定義、對話歷史、檢索回來的文件、這次的問題 |
| 輸出 token | 模型產生的內容；單價通常比輸入高 |
| context 長度 | 不是單獨的計費項，但決定每次輸入有多少 token；有些模型在超過某個長度後單價不同 |
| prompt 快取 | 多次呼叫共用的前綴（系統提示、工具定義、固定文件）被快取後，命中的部分以較低單價計算；寫入快取可能另有價格，快取有存活時間 |
| 批次處理 | 不需要即時回應的工作可以用批次介面，通常比較便宜，但要等 |
| 座位制 | IDE 外掛、聊天工具多半按使用者人數月費計，附用量上限或公平使用規則；超過上限可能降速或另計 |

### agent 為什麼特別貴

一般的聊天是一問一答。agent 是一個迴圈：模型決定呼叫工具 → 工具結果加進對話 → 再送一次給模型 → 再決定下一步。[Agent 的執行迴圈](#/skill/agent-loop) 有完整說明。從計費的角度看，關鍵在於**每一輪都重送前面所有內容**：

| 輪次 | 固定前綴 | 累積歷史 | 這輪的輸入 |
|---|---|---|---|
| 1 | 6,000 | 0 | 6,000 |
| 2 | 6,000 | 2,500 | 8,500 |
| 3 | 6,000 | 5,000 | 11,000 |
| 6 | 6,000 | 12,500 | 18,500 |

六輪加起來，輸入是每一輪的總和，而不是最後一輪的大小。歷史的部分是等差級數，輪數加倍時，歷史佔的 token 大約變成四倍；以這張表的數字，從 6 輪變 12 輪，總輸入約是原來的 3 倍多。所以 agent 成本的兩個槓桿是：

- **固定前綴走快取**：系統提示與工具定義每一輪都一樣，放在最前面、保持不變，才能命中快取。前綴裡只要有一個字變了（例如把目前時間寫進系統提示），後面就都不命中。
- **限制 context 長度**：超過上限就摘要或截掉舊的工具結果。代價是模型看不到完整歷史，可能重做已經做過的事，要觀察品質有沒有下降。

注意這裡說的 prompt 快取是**模型供應商端**的前綴快取，和 [AI Gateway](#/skill/ai-gateway) 的回應快取（同樣請求直接回上次的結果）是兩件事，兩者可以同時用。

## 實際程式：估一個 agent 工作流的月成本

下面的程式用變數表示單價，請換成實際方案的數字（範例裡的數字只是為了讓程式能跑，不是任何供應商的價格）。比較四種組合：有無快取、有無 context 上限。

```python run
# 單價是變數：換成實際方案的數字（每百萬 token 的價格；幣別自訂）。下面的值只是示範用。
PRICE_INPUT = 1.0          # 一般輸入 token
PRICE_CACHED_INPUT = 0.1   # 命中 prompt 快取的輸入 token
PRICE_OUTPUT = 5.0         # 輸出 token
DAYS = 30

# 工作流：一天跑 200 次，每次 6 輪；每輪都送固定前綴（系統提示 + 工具定義）與累積的歷史
runs_per_day = 200
turns = 6
prefix_tokens = 6_000        # 每一輪都一樣的前綴
history_per_turn = 2_500     # 每一輪新增的歷史（工具結果、模型回覆）
output_per_turn = 400


def monthly_cost(cache_prefix, max_context):
    """cache_prefix：前綴是否命中快取；max_context：單次輸入的上限（None 表示不限）"""
    inp = cached = out = 0
    for t in range(turns):
        total_in = prefix_tokens + history_per_turn * t      # 第 t 輪帶著前面 t 輪的歷史
        if max_context is not None:
            total_in = min(total_in, max_context)            # 超過上限就截掉最舊的歷史
        hit = min(prefix_tokens, total_in) if cache_prefix else 0
        cached += hit
        inp += total_in - hit
        out += output_per_turn
    per_run = (inp * PRICE_INPUT + cached * PRICE_CACHED_INPUT + out * PRICE_OUTPUT) / 1_000_000
    return inp, cached, out, per_run * runs_per_day * DAYS


base = None
for name, cache, cap in [
    ("不快取、不限 context", False, None),
    ("快取前綴、不限 context", True, None),
    ("不快取、上限 12k", False, 12_000),
    ("快取前綴、上限 12k", True, 12_000),
]:
    inp, cached, out, month = monthly_cost(cache, cap)
    base = base or month
    print(f"{name:<14} 每次：一般輸入 {inp:>6,} 快取 {cached:>6,} 輸出 {out:>5,}"
          f" ｜ 月成本 {month:>8,.2f}（比基準少 {(1 - month / base) * 100:.0f}%）")
```

改這些參數觀察結構：

- 把 `turns` 從 6 改成 12：基準成本不是變兩倍，而是更多，因為歷史累積是二次成長。
- 把 `PRICE_CACHED_INPUT` 改成和 `PRICE_INPUT` 一樣：快取的效果消失，這時只剩 context 上限有用。
- 把 `prefix_tokens` 調小、`history_per_turn` 調大：快取的效果變小，context 上限變得更重要。

估出來的是**區間**，不是預言。實際的輪數、工具結果長度、重試次數都會浮動；上線後要用真實的用量紀錄回頭校正。

## FinOps 三步：看得見 → 分攤 → 優化

FinOps 這個詞來自 FinOps Foundation 整理的實務框架。它強調的是流程而不是工具：工程、財務、業務一起看成本，讓花錢的人看得到自己花了多少。可以簡化成三步，順序不能倒：

### 1. 看得見

- **標籤（tag / label）**：每個資源都標上 `team`、`service`、`env`（prod / staging / dev）。沒有標籤的資源，帳單上就是一筆對不到人的錢。用政策或 IaC 檢查強制要求，事後補標很痛苦。
- **帳單匯出與報表**：把帳單明細匯出到資料倉儲或試算表，依標籤彙總。雲端主控台的圖表適合看趨勢，細查要靠明細。
- **預算與告警**：依帳號、專案或標籤設預算，用量到某個比例（例如 50%、80%、100%）就通知。預算告警多半是**通知**，不會自動停掉服務，而且帳單資料有延遲，告警不是即時的。
- **AI 工具的用量**：API 用量依金鑰或專案分開；透過 gateway 集中呼叫時，每筆紀錄帶團隊與用途。座位制的工具看的是實際使用人數與活躍度。

### 2. 分攤

把成本歸到團隊與服務。直接標得到的照標籤算；共用的部分（網路、共用叢集、監控平台）要約定分攤規則，例如依 CPU 用量比例或依請求數。規則不必完美，但要公開、一致，大家才會信。分攤的目的是讓擁有者看到自己的數字，不是處罰。

### 3. 優化

有了前兩步，才知道錢花在哪裡、誰能決定。常見的優化：

- 關掉或縮小閒置資源（CPU 長期很低的機器、沒人連的資料庫）
- 非上班時間關掉測試環境
- 穩定負載改用承諾折扣
- 物件儲存設生命週期規則，舊資料轉冷儲存或刪除
- agent 工作流：固定前綴走快取、限制 context、限制最大輪數、便宜的工作用較小的模型、不需即時的改批次

[容量規劃](#/skill/capacity-planning) 講的是規格該給多少；FinOps 是規格決定後，持續看實際用量有沒有偏離。

## 常見的浪費與錯誤

| 現象 | 原因 | 怎麼處理 |
|---|---|---|
| 刪了機器，帳單沒有降 | 磁碟、快照、固定 IP、負載平衡器沒一起刪 | 用 IaC 管理整組資源一起建、一起刪；定期列出未掛載的磁碟 |
| 流量費用突然很高 | 跨地區或出站流量；服務與資料庫不在同一區 | 畫出資料流向；同區部署；大量資料傳輸用專線或壓縮 |
| 測試環境的費用和正式環境差不多 | 二十四小時開著、規格照抄正式環境 | 排程開關、縮小規格 |
| 一筆帳對不到任何團隊 | 沒有標籤 | 建資源時強制標籤；定期列出無標籤資源 |
| agent 成本隨使用時間暴增 | 對話歷史無上限累積；前綴每次都變，快取不命中 | 固定前綴放最前面、不放時間戳；設 context 與輪數上限 |
| 重試迴圈把費用灌爆 | 模型回錯格式就無限重試 | 重試有上限；記錄每次工作的 token 總量並設告警 |
| 承諾折扣用不完 | 架構還在變就簽了長約 | 先觀察幾個月的穩定用量，只承諾底線 |
| 預算告警響了才發現超支一大截 | 帳單資料有延遲、只設了 100% 一個門檻 | 多設幾個門檻；搭配每日的用量報表 |

> 優化前先問「這筆錢是誰的、他知道嗎」。看不見的成本沒有人會去省。
