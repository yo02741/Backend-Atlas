## 從一個具體問題開始：同一個 prompt，昨天對、今天錯

客服系統用模型把來信分類成 `billing`、`account`、`technical` 三類，再派給不同的組。工程師在本機試了十封信，十封都對，就上線了。一週後帳務組抱怨收到一堆技術問題。拿一封被分錯的信回本機重試：這次分對了。再試一次：又錯了。

團隊的第一個反應是「模型不穩定」。這句話沒錯，但沒有用：它沒說是哪裡不穩定、不穩定到什麼程度、改了 prompt 之後有沒有變好。真正的問題有三個：

- 上線前只**各跑一次**，看不出單次正確率是 95% 還是 70%。
- 本機的輸入和線上不同：線上的 context 多了客戶的歷史訂單（由檢索取回，每次筆數與順序不同），本機測試沒有。
- 沒有一組固定的案例可以在改 prompt 前後比對，每次調整都是憑印象。

模型本身換不了，但包在模型外面那一層——怎麼準備輸入、怎麼評分、怎麼比對、失敗時怎麼處理——是自己可以設計的。這一層叫做 **harness**。

## 運作原理：非確定性從哪裡來

「同一個 prompt」通常不是真的同一個輸入。從送出請求到拿到結果，會改變輸出的來源：

| 來源 | 怎麼影響輸出 | 能不能固定 |
|---|---|---|
| 取樣參數（溫度、top-p） | 模型對每個 token 給出機率分布，取樣時溫度越高越常選到機率較低的 token | 可以調低；但溫度 0 也**不保證**每次相同（伺服器端的批次處理、浮點運算順序都可能造成差異），部分模型或 API 也不開放調整 |
| context 的內容 | 檢索取回的文件、對話歷史、系統提示的版本 | 可以：log 實際送出的完整內容，評測時用固定的快照 |
| context 的順序 | 同樣的文件換個順序，結果可能不同；太長時被截斷的部分也不同 | 可以：排序規則固定、截斷規則固定 |
| 工具的回傳 | agent 呼叫的 API、資料庫、搜尋結果會隨時間變化 | 評測時換成固定的假資料（fixture） |
| 模型版本 | 別名（例如「最新版」）背後的模型會更新；不同版本對同一個 prompt 的反應不同 | 可以：指定明確的模型版本，換版本視同一次改動 |
| 時間與環境 | prompt 裡帶了「今天日期」、使用者時區、語系 | 可以：當成參數傳入，評測時固定 |

能固定的全部固定之後，剩下的才是模型本身的隨機性。這時「不穩定」才有意義，而且可以量：同一個輸入跑 N 次，正確幾次。

## harness 的組成

harness 是包在模型呼叫外面的程式，負責五件事：

### 1. 固定輸入

每一次評測都記錄並固定：prompt 的版本（放在 repo 裡、有版本號）、模型版本、取樣參數、context 的快照、工具的假資料。目的是讓「結果變了」只能歸因到一個改動。

### 2. 評測集（golden set）

一組有期望結果的案例，每個案例包含輸入、期望輸出（或判定規則）、標籤（屬於哪一類情境）。來源：

- 代表性的正常案例（各分類都要有）
- 邊界案例（空輸入、超長輸入、混合語言）
- **出過事的案例**：每次線上出錯，把那個輸入加進評測集。這和「每個 bug 留一個測試」是同一個原則
- 應該拒絕的案例（含個資、超出範圍的請求）

評測集本身要版本化，案例的期望值有爭議時由人決定，不由模型決定。

### 3. 評分器

| 評分器 | 適合 | 例子 | 注意 |
|---|---|---|---|
| 精確比對 | 輸出有唯一正解 | 分類標籤、抽取的日期、計算結果 | 比對前做好正規化（去空白、統一大小寫、去千分位） |
| 規則 | 正解不唯一但有可檢查的條件 | regex、JSON schema、必含或禁止的字串、長度上限 | 規則只保證格式或必要條件，不保證內容正確 |
| 模型評分 | 開放式的輸出 | 摘要是否涵蓋重點、回覆語氣 | 評分模型本身也是非確定的；要有評分標準、要抽樣人工複核 |

原則是**能用前兩種就不用第三種**。把開放式的任務拆成可以精確比對或用規則判定的部分（例如要求模型輸出 JSON，再逐欄比對），評測會便宜很多、也穩定很多。

### 4. 回歸比對

改 prompt、換模型、調整檢索之後，用同一份評測集跑一次，和上一版的結果並排比對：哪些案例從過變成不過、哪些從不過變成過、整體通過率變多少。單看整體通過率會漏掉「修好五個、弄壞三個」的情況，所以要看**逐案例的差異**。這份比對可以放進 CI，跟程式碼的 diff 一起被 review。

### 5. 重試與攔截

上線時，harness 在模型輸出交出去之前檢查它：格式不合法就重試，重試幾次還不行就攔下（回傳預設值、轉人工、回報錯誤）。這一步只能用**不需要正確答案**的檢查——上線時沒有期望值可以比對。

## 實際程式：多次取樣、重試與多數決

下面用固定種子的亂數模擬一個「模型」：每個案例有固定的單次正確率，答錯時從幾種常見錯法挑一個。有些錯法格式就不對（`2026-3-14`、`NT$1480`），有些格式對但內容錯（`2026-03-15`、`1470`）。比較三種策略：

- **single**：呼叫一次
- **retry**：格式檢查不過就重試，最多三次；三次都不合法就攔下
- **vote**：呼叫五次取多數

```python run
import random
import re
from collections import Counter

# ── 一個會隨機出錯的「模型」：每個案例有固定的單次正確率，答錯時從常見錯法裡挑一個 ──
CASES = [
    # id,            期望答案,     單次正確率, 錯誤答案（有些格式就不對，有些格式對但內容錯）
    ("extract-date", "2026-03-14", 0.90, ["2026-3-14", "14/03/2026", "2026-03-15"]),
    ("classify",     "billing",    0.70, ["payment", "Billing.", "account"]),
    ("sum-items",    "1480",       0.60, ["1480.0", "NT$1480", "1470"]),
    ("refuse-pii",   "REFUSE",     0.40, ["ANSWER"]),
]

# 規則評分器：不知道正確答案，只檢查「格式是否合法」——重試時唯一能用的訊號
FORMAT = {
    "extract-date": r"\d{4}-\d{2}-\d{2}",
    "classify":     r"billing|account|technical",
    "sum-items":    r"\d+",
    "refuse-pii":   r"REFUSE|ANSWER",
}

def model(case, rng):
    cid, answer, p, wrongs = case
    return answer if rng.random() < p else rng.choice(wrongs)

def valid(case, out):
    return re.fullmatch(FORMAT[case[0]], out) is not None

def correct(case, out):                       # 精確比對：評測時才用得到期望答案
    return out == case[1]

# ── 三種策略。calls 記錄每種策略呼叫了模型幾次（成本） ──
def single(case, rng, calls):
    calls[0] += 1
    return model(case, rng)

def retry(case, rng, calls, attempts=3):
    for _ in range(attempts):
        calls[0] += 1
        out = model(case, rng)
        if valid(case, out):                  # 格式對就收下；格式對但內容錯，重試救不了
            return out
    return None                               # 三次都不合法：攔下，不交出去

def vote(case, rng, calls, k=5):
    outs = []
    for _ in range(k):
        calls[0] += 1
        outs.append(model(case, rng))
    return Counter(outs).most_common(1)[0][0]

TRIALS = 300
rng = random.Random(7)                        # 固定種子：每次執行的數字都一樣
print(f"{'case':14s}{'single':>9s}{'retry<=3':>10s}{'vote of 5':>11s}")
cost = {"single": [0], "retry": [0], "vote": [0]}
for case in CASES:
    row = []
    for name, fn in (("single", single), ("retry", retry), ("vote", vote)):
        ok = sum(correct(case, fn(case, rng, cost[name]) or "") for _ in range(TRIALS))
        row.append(ok / TRIALS)
    print(f"{case[0]:14s}{row[0]:9.0%}{row[1]:10.0%}{row[2]:11.0%}")
n = TRIALS * len(CASES)
print(f"{'calls/case':14s}{cost['single'][0]/n:9.2f}{cost['retry'][0]/n:10.2f}{cost['vote'][0]/n:11.2f}")
```

讀這張表：

- **重試只救得了「格式錯」**。`extract-date` 從 90% 升到 96%：格式錯的答案被擋下重來；但 `2026-03-15` 格式正確，評分器分不出來，重試不會發生。`refuse-pii` 的錯誤答案 `ANSWER` 格式完全合法，重試前後一樣是 37%。重試的效果取決於驗證器能抓到多少種錯。
- **多數決的前提是「正確答案是最常出現的那個」**。前三個案例正確率高於任何一種錯法，取多數會更準；`refuse-pii` 只有一種錯法、而且出現機率（60%）比正確答案高，取五次多數反而更常錯（30%）。
- **成本**：retry 平均每個案例呼叫 1.17 次（大多一次就過），vote 固定 5 次。延遲也跟著呼叫次數走。
- 這張表也說明了為什麼評測要跑多次：`classify` 單次 73%，任何一次單獨的嘗試都可能讓人誤以為它「沒問題」或「完全不行」。

`refuse-pii` 這種情況，harness 的正確做法不是加重試，而是**把問題移到模型外面**：用規則先偵測個資、直接拒絕，不讓模型判斷。

## 同一個 prompt 差很多：排查順序

遇到「結果不一樣」時，照這個順序排除，先排除便宜、確定的：

1. **確認真的是同一個輸入**。從 log 取出兩次實際送出的完整請求（系統提示、對話歷史、檢索結果、工具定義、參數），做 diff。大多數時候差異在這裡。
2. **模型版本**。是否用了會自動更新的別名；兩次請求是否打到不同的模型或不同的供應商。
3. **context 的內容與順序**。檢索結果的筆數、排序、截斷位置；歷史訊息被裁掉了哪些。
4. **工具結果與時間**。agent 呼叫的工具回傳是否不同；prompt 裡的日期、時區是否不同。
5. **取樣參數**。溫度、top-p、最大長度（輸出被截斷也會讓結果看起來不同）。
6. **固定以上全部，跑 N 次**。如果通過率本來就只有七成，那不是「這次壞了」，是「它一直都這樣」——要改的是 prompt、任務拆法或 harness，不是重跑。
7. **評分器本身**。正規化有沒有做、模型評分的標準是否模糊、評分模型自己的版本是否變了。

## 用現成工具：promptfoo

自己寫評測跑器不難（程式題就是在做這件事），團隊規模大了可以用現成工具。**promptfoo** 用 YAML 描述 prompt、要測的模型（provider）與測試案例，每個案例可以掛多個斷言（例如 `equals`、`contains`、`regex`、`is-json`、用模型評分的 `llm-rubric`），執行後產出逐案例的比對表。示意（欄位與指令以所用版本的文件為準，不能在瀏覽器執行）：

```yaml
prompts:
  - file://prompts/classify_v3.txt
providers:
  - id: <指定版本的模型>
    config:
      temperature: 0
tests:
  - vars:
      email: "上個月被重複扣款兩次，請退款"
    assert:
      - type: equals
        value: billing
  - vars:
      email: "登入時一直顯示驗證碼錯誤"
    assert:
      - type: regex
        value: "^(account|technical)$"
```

```bash
npx promptfoo@latest eval      # 跑評測，輸出逐案例結果
npx promptfoo@latest view      # 在瀏覽器檢視結果與前後比對
```

不論用工具還是自建，重點相同：評測集與 prompt 都在 repo 裡、每次改動都跑、結果可以和上一版比對。把 agent 當成軟體來交付（版本、金絲雀、回滾）的完整流程，見 [把 agent 當軟體交付](#/skill/agent-delivery)。

## 常見錯誤與錯誤訊息

| 現象 | 原因 | 處理 |
|---|---|---|
| 評測每次跑的通過率差很多 | 每個案例只跑一次，抽樣誤差大 | 每個案例跑多次，看通過率與不穩定案例清單 |
| 本機評測全過，上線出錯 | 評測的輸入沒有包含線上的 context（檢索結果、歷史） | 從線上 log 取樣真實請求，脫敏後加入評測集 |
| 改了 prompt，整體通過率不變，但有使用者抱怨 | 修好幾個、弄壞幾個，總數抵銷 | 看逐案例的差異，而不是只看總數 |
| 精確比對大量失敗，人工看卻都對 | 沒做正規化：多了空白、句點、大小寫不同 | 評分前正規化；或要求模型輸出結構化格式 |
| `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)` | 模型在 JSON 前面加了說明文字或 markdown 圍欄 | 規則評分器先檢查格式；harness 重試或攔下；使用 API 提供的結構化輸出功能（若有） |
| 重試三次後成功率幾乎沒變 | 錯誤答案的格式是合法的，驗證器擋不下 | 加強驗證器（例如對照資料庫確認值存在），或把判斷移出模型 |
| 換了評分模型後分數大幅變動 | 模型評分本身非確定、且依賴評分模型的版本 | 固定評分模型版本；標準寫具體；定期人工抽查 |

## 動手

1. 在 Playground 執行上面那段，把 `classify` 的錯誤答案改成只有 `["account"]`、正確率改成 0.45，看多數決的結果如何變化。
2. 把 `FORMAT["sum-items"]` 改成 `r"1480"`（等於把正確答案寫進驗證器），重跑，看重試的通過率——再想想為什麼上線時通常拿不到這種驗證器。
3. 把 `random.Random(7)` 換成 `random.Random()`（不給種子），連續執行兩次，比較數字差異；再把 `TRIALS` 改成 30 看差異變大多少。
4. 做程式題 `harness-engineering-1`：實作評測跑器，跑 N 次、算通過率、列出不穩定的案例。
5. 延伸：模型的輸出怎麼驗收，和程式碼的驗收是同一套想法，見 [驗收設計](#/skill/acceptance-design)。
