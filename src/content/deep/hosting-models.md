## 從一個具體問題開始：同一套系統，三種放法

一家醫院要把掛號、檢驗報告查詢、院內排班這幾個服務搬上 Kubernetes。需求本身很清楚：三個 API、一個 PostgreSQL、一套監控，尖峰在早上八點到十點的門診掛號。真正卡住的是「放在哪裡」，會議上通常出現三個提案：

- **A：院內機房**。買三到四台伺服器、一組儲存設備，自己裝 Kubernetes。
- **B：託管機房（colocation）**。機器自己買，放進專業機房，電力、冷氣、實體門禁由機房業者負責。
- **C：公有雲**。用雲端業者的受管 Kubernetes 與受管資料庫，按用量付費。

接著每個提案都會被問同一組問題：五年下來誰比較便宜？硬碟半夜壞掉誰去換？病歷資料可不可以離開院區？對外網路斷了，院內還能不能掛號？這些問題沒有通用答案，但有固定的拆法：**責任邊界、成本結構、維運人力、彈性、合規、網路條件**。把這六項逐一攤開，結論通常會自己浮現。

## 幾種放法差在哪：誰負責哪一層

最容易混淆的是「上雲」這兩個字，它可能指很不一樣的東西。用「誰負責哪一層」來區分最清楚：

| 層 | 自有機房 | 託管機房 | 公有雲 IaaS（虛擬機） | 公有雲 PaaS／受管服務 |
|---|---|---|---|---|
| 建築、電力、冷氣、實體安全 | 自己 | 機房業者 | 雲端業者 | 雲端業者 |
| 伺服器、儲存、網路設備 | 自己 | 自己 | 雲端業者 | 雲端業者 |
| 虛擬化／實體主機維護 | 自己 | 自己 | 雲端業者 | 雲端業者 |
| 作業系統修補 | 自己 | 自己 | **自己** | 雲端業者 |
| Kubernetes 控制平面、資料庫引擎升級 | 自己 | 自己 | 自己 | 雲端業者（版本升級時機多半仍要自己決定） |
| 應用程式、資料、帳號權限 | 自己 | 自己 | 自己 | **自己** |

最後一列永遠是自己的。這就是雲端業者常說的**共同責任模型**（shared responsibility model）：業者負責「雲本身」的安全，你負責「放在雲裡的東西」——帳號權限設錯、儲存桶公開、資料庫沒加密，都不是業者的責任。

另外兩個常被混用的詞：

- **混合雲（hybrid cloud）**：地端與公有雲同時使用，而且兩邊有連線（VPN 或專線）、有分工。常見的分法是核心系統與敏感資料留在地端，對外網站、需要彈性擴充的運算、異地備份放雲端。
- **多雲（multi-cloud）**：同時用兩家以上的公有雲。理由通常是避免綁定單一業者、或某些服務只有某家有。代價是每一家的帳號、網路、權限、監控都要會，自己寫的抽象層只能用到各家的「最小公倍數」功能。團隊規模小的時候，多雲帶來的維運負擔常常大於它解決的風險。

## 成本模型：不要只比硬體報價

### CapEx 與 OpEx

- **CapEx（資本支出）**：一次買斷的硬體、機櫃、授權，依會計政策分年折舊。預算要提前編列，買了就是沉沒成本。
- **OpEx（營運支出）**：每月、每年持續付的費用，例如雲端用量、機房租金、維護合約。彈性大，但沒有上限的帳單也可能讓人驚嚇。

地端不是「買完就免費」，雲端也不是「只付用多少」。兩邊各有容易漏算的項目：

| 地端容易漏算 | 雲端容易漏算 |
|---|---|
| 電力與冷氣（伺服器的耗電還要再加上冷卻） | **閒置成本**：機器開著沒在用也照樣計費 |
| 機櫃空間、UPS、發電機、消防 | **流量費**：多數業者對流出雲端的流量（egress）收費，流入多半不收 |
| 維護合約、備品、硬體汰換週期 | 快照、備份、跨可用區或跨區的資料傳輸 |
| 虛擬化、作業系統、資料庫授權 | 受管服務的溢價（比自己架貴，換到的是少一份維運） |
| 為了尖峰預留的容量，平常大半閒置 | 監控、日誌儲存的量會隨時間長大 |
| **維運人力**：硬體、網路、儲存、平台升級 | 承諾用量折扣綁約後，用不到也要付 |

### 用量曲線決定誰比較划算

地端要依**尖峰**採購，再加上備援（N+1）。雲端如果真的有做自動擴縮，費用跟著**平均**用量走；沒做擴縮，費用其實跟著「開了多少」走，和地端一樣是依尖峰付錢，而且每個月都在付。所以：

- 負載平穩、長期滿載、資料大量進出：地端或託管機房常常比較划算。
- 尖峰與離峰差很多、短期專案、需要快速試錯：雲端比較划算。
- 大量資料要從雲端傳出（例如影像檔每天下載回院內）：流量費可能超過運算費，要先估。

下面的試算只示範「要算哪些項目」，**所有單價都是虛構的**，實際數字請用業者報價與院內的電費、人力成本替換：

```python run
# 5 年總持有成本（TCO）粗估：所有單價都是虛構的，只示範要算哪些項目
YEARS = 5
STAFF_COST = 1_500_000            # 一個維運人力一年的成本（虛構）

def on_prem(peak_vcpu):
    servers = -(-peak_vcpu // 64) + 1          # 每台 64 vCPU，依尖峰採購，再加一台備援（N+1）
    hardware = servers * 600_000               # 一次性採購（CapEx）；5 年後還要汰換
    yearly = servers * 60_000 + 300_000        # 每年：電力冷氣機櫃 + 維護合約與授權
    staff = 0.5 * STAFF_COST                   # 硬體、網路、儲存、平台升級要投入的人力
    return hardware + YEARS * (yearly + staff)

def cloud(provisioned_vcpu, egress_tb_per_month):
    compute = provisioned_vcpu * 1_000 * 12    # 依「開著的」vCPU 計費，不是依實際使用率
    egress = egress_tb_per_month * 3_000 * 12  # 流出流量每 TB 的費用
    managed = 150_000                          # 受管控制平面、備份、監控的年費
    staff = 0.25 * STAFF_COST                  # 平台維運仍然需要人，只是少一些
    return YEARS * (compute + egress + managed + staff)

PEAK = 128
cases = [
    ("負載平穩，沒做擴縮（雲端也開到尖峰）", PEAK, 2),
    ("尖峰集中在上午，有做自動擴縮（平均約 35%）", int(PEAK * 0.35), 2),
    ("有做擴縮，但每月要傳出 40 TB 影像", int(PEAK * 0.35), 40),
]
print(f"地端（依尖峰 {PEAK} vCPU 採購）：{on_prem(PEAK):>12,.0f}")
for name, vcpu, egress in cases:
    print(f"雲端：{name}：{cloud(vcpu, egress):>12,.0f}")
```

試著把 `PEAK` 調大、把擴縮比例從 0.35 改成 0.8，或把流量從 40 改成 100，觀察哪一個項目主導總額。重點不是哪個答案比較小，而是**哪個假設一改，結論就翻過來**——那個假設就是要先去查證的數字。

## 維運人力與彈性

### 人力：誰會被半夜叫醒

地端與託管機房除了應用程式，還要有人負責：硬體故障叫修與備品、韌體與儲存設備更新、網路設備與防火牆、備份系統、Kubernetes 本身的安裝與升級。Kubernetes 上游大約每年發行三個 minor 版本、只維護最近的幾個版本，自建叢集等於要有人固定排時間升級，跳過太多版本會讓升級變得很痛。

受管服務把其中一部分責任移給業者，但不是全部：版本升級的時機、節點的作業系統映像、叢集裡的網路政策與權限，多半仍然要自己顧。評估時把「現在有幾個人、各自會什麼」寫下來，比任何技術比較都重要。只有一兩位維運人員的團隊，自建全套平台的風險在於**人的單點故障**：那個人請假，叢集就沒人會修。

### 彈性：擴充要多久

- **地端**：擴充 = 採購。從編預算、招標到上架，常常是數週到數月。所以容量規劃要提前做，平常留足餘裕。
- **雲端**：擴充以分鐘計，但有帳號配額（quota）上限，特殊規格的機器在某些區域可能缺貨。彈性要靠架構配合：無狀態服務容易擴，資料庫不容易。

## 合規與資料落地

醫療資料是最敏感的個人資料類別之一。資料能不能放到院外、能不能放到境外、委外給雲端業者時要符合哪些條件，要**依個人資料保護法、主管機關（衛生福利部）的相關規範與院內資安政策**辦理；部分醫院還可能有資通安全相關法規的責任等級要求。這些規範會修訂，條文的具體要求不在本課範圍內，**做決定之前一定要與院內法遵、資安單位確認**，必要時請主管機關或法律顧問釐清。

技術上可以先準備好這份清單，帶去和法遵討論：

| 問題 | 為什麼要問 |
|---|---|
| 資料實際存放在哪個國家、哪個區域？備份與災難復原副本在哪？ | **資料落地**（data residency）：主資料在國內，備份卻自動複製到國外區域，是常見的疏漏 |
| 誰持有加密金鑰？業者能否在技術上讀取明文？ | 用業者管理的金鑰還是自管金鑰（KMS／HSM），決定了「業者看不看得到」 |
| 存取紀錄保存多久？能否匯出給稽核？ | 稽核與事故調查都需要 |
| 委外契約有沒有稽核權、事故通報時限、再委外限制？ | 業者的資安事故也是你的事故 |
| 終止合約時資料如何返還與刪除？ | **退場計畫**：沒寫進契約的事，到時候很難談 |
| 業者的認證（例如 ISO/IEC 27001）涵蓋哪些服務、哪些區域？ | 業者有認證不等於你的系統合規；認證範圍也未必包含你用的服務 |

常見的折衷是**依資料分級決定位置**：可識別個人的病歷與檢驗資料留在地端；去識別化後的統計資料、對外的衛教網站、不含個資的工具服務放雲端。資料分級本身是資料治理的工作，見 [數據中台之前：資料治理](#/skill/data-governance)。

## 斷網或受限網路環境的部署要點

醫院、工廠、金融業的內網常常不能直接連網際網路，或只開放少數白名單。Kubernetes 與現代的建置流程預設「隨時可以下載東西」：拉容器映像、裝 Python／npm 套件、更新作業系統、下載弱點資料庫。在受限環境要事先準備好每一個「下載來源」的內部替代品：

| 外部來源 | 內部替代 | 備註 |
|---|---|---|
| Docker Hub 等公開映像倉庫 | 私有映像倉庫（GitLab Container Registry、Harbor 等） | 基底映像先鏡像進來，Dockerfile 的 `FROM` 指向內部倉庫；用 digest 釘版本 |
| PyPI、npm registry | 內部套件來源（GitLab Package Registry、或其他套件鏡像工具） | `pip`、`uv`、`npm` 的設定改指向內部來源 |
| 作業系統套件庫（apt、dnf） | 內部鏡像 | 修補要能進得來，否則弱點會一直累積 |
| Kubernetes 元件與 Helm chart | 離線安裝包、內部 chart 倉庫 | 叢集元件本身的映像也要先放進私有倉庫 |
| 弱點掃描的資料庫、憑證撤銷資訊 | 定期同步 | 斷網的掃描器若不更新，會一直回報「沒有弱點」 |
| 公開 NTP、DNS、憑證機構 | 內部 NTP、內部 DNS、內部 CA | 時間不同步會讓憑證驗證與日誌時間線全部出問題 |

搬運流程通常是：在可連外的區域下載 → 掃描與核可 → 經由受控管道搬進內網 → 推進內部倉庫。下面是常見的指令與設定（需要真實環境，不能在瀏覽器執行）：

```bash
# 把公開映像複製到內部倉庫（可連外、也能連內部倉庫的跳板機上執行）
skopeo copy docker://docker.io/library/python:3.12-slim \
  docker://registry.example.internal/mirror/python:3.12-slim

# 完全隔離的網路：先存成檔案，經核可的管道搬進去後再推送
skopeo copy docker://docker.io/library/python:3.12-slim oci-archive:python-3.12-slim.tar
```

```ini
# pip.conf：套件一律從內部來源安裝
[global]
index-url = https://pypi.example.internal/simple/
```

```dockerfile
# 基底映像來自內部倉庫，並用 digest 釘住版本（digest 請換成實際值）
FROM registry.example.internal/mirror/python:3.12-slim@sha256:<digest>
```

還有兩件事在斷網環境特別容易忘：**授權驗證**（有些商業軟體要連線啟用）與**時間**（所有機器要同一個時間來源，事故時間線才對得起來）。

## 決策表與常見錯誤

| 條件 | 傾向 |
|---|---|
| 資料依規範不能離開院區，或法遵尚未確認 | 地端／託管機房；雲端只放不含個資的服務 |
| 負載平穩、可預測、長期使用 | 地端或託管機房的成本通常有優勢 |
| 尖峰離峰差距大、短期專案、需要快速試錯 | 公有雲 |
| 維運人力很少，沒有人懂硬體與儲存 | 受管服務（雲端 PaaS），或託管機房加上外包維護 |
| 院內機房的電力、冷氣、實體安全不足 | 託管機房或雲端 |
| 對外網路不穩、要求斷網也能運作 | 核心服務留地端；雲端當備援或對外服務 |
| 有大量資料要頻繁傳出 | 先估流量費，常常讓雲端方案變貴 |
| 想用多雲「避免綁定」，但團隊只有少數人 | 先把一家用好，把可攜性放在容器映像、基礎設施即程式碼、資料匯出能力 |

常見錯誤：

- **只比硬體報價**：漏掉人力、電力、授權、汰換，或漏掉雲端的流量費與閒置成本。
- **原封不動搬上雲（lift-and-shift）就期待省錢**：沒有自動擴縮、不關閉閒置環境，雲端帳單通常比地端高。
- **把業者的認證當成自己的合規**：共同責任模型裡，帳號、權限、資料加密都還是自己的。
- **沒有退場計畫**：資料怎麼匯出、要多久、格式是什麼，在簽約前就要確定。
- **地端沒規劃升級**：叢集裝好之後就不動，兩年後落後太多版本，升級變成大工程。

## 動手

1. 執行上面的 TCO 試算，把三個情境的參數各改一次，找出最影響結論的那個假設。
2. 列出一套目前系統的所有「下載來源」（映像、套件、作業系統、弱點資料庫），逐一寫下斷網時的內部替代品，缺的就是導入前要補的。
3. 把「合規與資料落地」那張表當成會議議程，帶去和法遵、資安確認，答案寫進決策紀錄。
4. 雲端的基本概念見 [雲端與主機基礎](#/skill/cloud-basics)；尖峰要買多少機器見 [硬體資源與容量規劃](#/skill/capacity-planning)；選好位置之後，SLO 怎麼訂見 [SLI、SLO 與錯誤預算](#/skill/slo-error-budget)，上線變更怎麼管見 [受監管環境的變更管理](#/skill/change-management)。
