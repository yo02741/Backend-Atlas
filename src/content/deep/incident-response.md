## 從一個具體問題開始：週一早上八點，掛號頁面一直轉圈

週一 08:05，一家醫院的線上掛號頁面開始逾時。接下來一小時發生的事很典型：

- 08:07 告警寄到一個共用信箱，沒有人看到。
- 08:15 門診櫃台打電話到資訊部，三個人同時開始查：一個看應用程式日誌，一個登入資料庫，一個重開了 API 的 Pod。
- 08:20 有人重啟資料庫，連線恢復了兩分鐘又塞住；重啟也把當下的慢查詢紀錄清掉了。
- 08:30 院長室來電問狀況，接電話的人正在查問題，回答「快好了」。
- 08:50 有人發現是早上 07:50 上線的報表功能，在尖峰時段跑了一支沒有索引的查詢，把資料庫連線占滿。把那個功能關掉，服務恢復。
- 隔週檢討會上，沒有人說得出完整的時間順序，最後結論是「下次部署要小心」。

技術問題本身 10 分鐘就能解決（關掉新功能），真正拖長事故的是：**沒人知道事故已經發生、沒人負責指揮、多人同時改東西互相干擾、對外說法不一致、事後沒有可追蹤的改善**。事故處理要解決的就是這些。告警怎麼設、備份怎麼做、runbook 怎麼寫，分別在 [可觀測性](#/skill/observability) 與 [健康檢查、備份與事故處理](#/skill/reliability) 談；本課講的是「出事之後，人怎麼分工與協作」。

## 事故分級

分級的目的是讓所有人對「要動員多少人、多快回應、通知到哪一層」有共識，不必每次臨場討論。名稱與級數各組織不同（SEV1–SEV4、P1–P4 都常見），重點是**依影響判斷，而且事先寫好**：

| 等級 | 判斷依據（示意） | 例子 | 回應 |
|---|---|---|---|
| SEV1 | 核心服務全面中斷、影響病人安全或照護流程、有資料外洩疑慮 | 掛號與看診系統全部無法使用；疑似病歷資料外洩 | 立即動員，指定事故指揮官，通知主管與相關單位，啟動替代作業流程 |
| SEV2 | 核心功能部分中斷或嚴重變慢，有替代方式 | 線上掛號掛了，但櫃台與電話掛號正常 | 立即處理，指定事故指揮官，定時更新狀態 |
| SEV3 | 次要功能故障，影響有限 | 報表匯出失敗、某個內部工具無法登入 | 上班時間處理，開工單追蹤 |
| SEV4 | 幾乎沒有影響，或已有暫時解法 | 介面錯字、非必要的排程延遲 | 排進一般工作 |

幾個原則：

- **寧可先高估再降級**。宣告 SEV2 之後發現影響很小，降成 SEV3 沒有成本；低估而延誤動員，代價很高。
- **分級看影響，不看原因**。「資料庫掛了」本身不是等級；「因此沒人能掛號」才是。
- **醫療場域要把病人安全與替代作業放進判斷**。系統停擺時是否有紙本或離線的替代流程、能撐多久，會直接影響等級與通知範圍。
- **資安事件另有流程**。疑似入侵、資料外洩時，除了技術處理，通常還有院內資安通報程序與對外通報的要求，具體時限與對象依相關法規與院內政策而定，要事先和資安單位確認並寫進 runbook。保全證據（日誌、映像快照）在這類事件裡特別重要。

## on-call 與輪值

**on-call** 是在約定時段內，負責接收告警並在約定時間內回應的人。要讓 on-call 可以長期運作，幾件事要先準備好：

| 項目 | 內容 |
|---|---|
| 班表 | 主要（primary）與次要（secondary）各一人；主要沒在時限內確認，自動升級給次要，再升級給主管 |
| 交接 | 換班時交接進行中的問題、近期的變更、已知的不穩定點；寫在固定位置，不只用口頭 |
| 回應時限 | 依等級定：例如會呼叫人的告警要在幾分鐘內確認；工單類告警下個上班日處理 |
| 存取權限 | on-call 的人在家裡也要能連上：VPN、跳板機、監控、部署工具的權限**事先測過** |
| runbook | 每一個會呼叫人的告警，都連到一份「收到後先做什麼」的 runbook |
| 告警品質 | 定期檢視：哪些告警響了卻不需要處理？刪掉或降級成工單 |
| 負擔與補償 | 被叫醒的次數要統計；依組織規定給予補休或津貼。長期過勞的 on-call 一定會出錯 |

團隊只有兩三個人時，24 小時輪值很難持續。這時要誠實地決定：哪些服務需要 24 小時回應（通常與病人照護直接相關），哪些只需要上班時間回應，再把這個決定反映在 [SLO](#/skill/slo-error-budget) 上——夜間沒人回應的服務，不應該承諾每月只停機 4 分鐘。

## 事故中的角色

事故規模一大，最常見的失敗是「每個人都在修，沒有人在指揮」。事故管理的做法是把角色分開：

| 角色 | 職責 | 不做的事 |
|---|---|---|
| **事故指揮官** Incident Commander（IC） | 宣告事故與等級、分派工作、決定下一步（例如要不要回滾）、決定何時結束 | 不親自動手修。IC 一旦埋頭查日誌，就沒人看全局 |
| **溝通窗口** Communications lead | 對內（主管、門診、護理站、客服）、對外更新狀態；整理統一說法 | 不猜測原因、不承諾修好時間 |
| **處理人員** Operations／領域專家 | 實際排查與執行修復；**每個動作先告知 IC 再做** | 不各自為政地改設定 |
| **紀錄員** Scribe | 記錄時間線：觀察到什麼、做了什麼、為什麼這樣決定 | — |

小團隊可以一人兼兩個角色（例如 IC 兼紀錄員），但盡量不要讓 IC 同時是主要處理人員。角色要**明確宣告**：在事故頻道裡寫「我是 IC」「我負責溝通」，人員換手時也要宣告。

## 處理流程：先止血，再找根本原因

```text
偵測 → 宣告 → 評估影響 → 止血（mitigate）→ 恢復（resolve）→ 結案 → postmortem → 追蹤行動項目
```

**止血**的目標是讓使用者盡快恢復服務，而不是找出根本原因。常見的止血手段：

- **回滾**最近的變更（程式、設定、資料庫遷移）。出事時第一個問題永遠是「最近改了什麼」，所以部署紀錄要好查，見 [受監管環境的變更管理](#/skill/change-management)。
- **關閉功能**：用 feature flag 關掉剛上線的功能。
- **切換**到備援、擴充容量、把有問題的節點移出服務。
- **降級**：暫停非核心功能（報表、批次），保住核心路徑（掛號、看診）。
- **擋流量**：封鎖異常的來源或啟用限流。

根本原因可以等服務恢復之後再查。但止血時要注意**保全證據**：重啟服務、重建 Pod、清除快取之前，先把日誌、錯誤訊息、慢查詢清單、記憶體與連線數的狀態保存下來，否則事後無從分析。

## 時間線紀錄

時間線是 postmortem 的骨幹，也是事故中交接的依據。在事故頻道或共用文件裡，**當下就寫**，不要事後回憶：

```text
時區：UTC+8
08:05  告警：掛號 API p95 延遲 > 3 秒（監控系統）
08:15  門診櫃台回報線上掛號無法使用；宣告 SEV2，IC：值班工程師 A
08:18  觀察：資料庫連線數達上限 200；API Pod 正常
08:22  決定：先不重啟資料庫，保存 pg_stat_activity 快照（B 執行）
08:26  觀察：大量相同的報表查詢，執行時間 > 60 秒，來源是 07:50 上線的報表功能
08:28  決定：關閉報表功能的 feature flag（理由：最近變更 + 查詢來源吻合）
08:30  執行：feature flag 關閉（B）；溝通窗口 C 通知門診與主管
08:34  觀察：連線數降到 40，延遲恢復正常
08:50  持續觀察 15 分鐘無異常，宣告服務恢復；事故轉為追蹤狀態
```

好的時間線記錄的是**觀察、決定、執行**，以及決定的理由。「08:28 關閉 flag」不如「08:28 決定關閉 flag，因為查詢來源吻合且這是最近的變更」有用。

## 溝通

狀態更新要固定格式、固定頻率（例如 SEV1 每 30 分鐘一次，就算沒有進展也要更新「仍在處理」）：

```text
【SEV2｜線上掛號異常｜08:40 更新】
影響：線上掛號頁面無法使用，櫃台與電話掛號正常
目前狀況：已找到可能原因並採取措施，服務正在恢復，持續觀察中
建議作法：請櫃台持續協助現場與電話掛號
下次更新：09:10 前
```

幾個原則：說事實，不猜原因；不承諾修好的時間，只承諾下次更新的時間；對非技術單位講影響與替代作法，不講技術細節。

## Postmortem：不究責

事故結束後幾天內寫 **postmortem**（事後檢討）。**不究責**（blameless）不是沒有責任，而是承認：在複雜系統裡，人會犯錯是常態，事故的原因是「系統讓這個錯誤有機會造成影響」。把焦點放在某個人身上，下一次大家只會隱瞞資訊，真正的系統問題永遠找不到。

一份 postmortem 的骨架：

```markdown
## 摘要
一句話：發生什麼事、影響多大、持續多久。

## 影響
- 受影響的服務與使用者範圍；持續時間（從開始到恢復）
- 耗用的錯誤預算（若有 SLO）

## 時間線
（從事故頻道整理，含偵測、宣告、止血、恢復的時間點）

## 原因與促成因素
- 直接原因：報表查詢沒有索引，在尖峰時段占滿資料庫連線
- 促成因素：新功能在尖峰前 15 分鐘上線；報表與線上交易共用同一個連線池；
  告警寄到沒人看的信箱；測試環境的資料量遠小於正式環境

## 做得好的地方 / 運氣好的地方

## 行動項目
| 項目 | 類型 | 負責人 | 期限 | 工單 |
```

寫原因時常用「五個為什麼」往下追，但要小心只追出一條線：事故通常有好幾個**促成因素**同時存在，每一個都是可以改善的點。「工程師沒注意」不是原因，要繼續問「為什麼系統允許沒注意也能上線」。

## 行動項目追蹤

postmortem 最常見的失敗是：行動項目寫得很好，然後沒有人做。每一個行動項目都要有**負責人、期限、工單**，並在固定的會議上追蹤。行動項目可以分成三類，確保不是只有「預防」：

| 類型 | 例子 |
|---|---|
| 預防 prevent | 報表查詢改用唯讀副本；遷移前在接近正式資料量的環境測試 |
| 偵測 detect | 資料庫連線數告警；告警改送到 on-call 的呼叫系統 |
| 緩解 mitigate | 新功能預設加 feature flag；報表與交易使用不同連線池 |

下面這段程式從時間線算出幾個常用的時間指標，並檢查行動項目的狀態。各組織對「偵測時間」「恢復時間」的起訖定義不同，**比較數字前要先統一定義**：

```python run
from datetime import datetime, date

def t(s):
    return datetime.strptime("2026-03-02 " + s, "%Y-%m-%d %H:%M")

timeline = {
    "started":      t("07:50"),   # 事後回推：問題實際開始（變更上線）
    "detected":     t("08:05"),   # 第一個告警
    "acknowledged": t("08:15"),   # 有人確認並開始處理
    "mitigated":    t("08:34"),   # 使用者恢復服務
    "resolved":     t("08:50"),   # 宣告事故結束
}

def minutes(a, b):
    return int((timeline[b] - timeline[a]).total_seconds() // 60)

print("偵測耗時（開始 → 告警）：", minutes("started", "detected"), "分鐘")
print("確認耗時（告警 → 有人處理）：", minutes("detected", "acknowledged"), "分鐘")
print("止血耗時（開始 → 恢復服務）：", minutes("started", "mitigated"), "分鐘")

actions = [
    {"item": "報表查詢改走唯讀副本", "type": "prevent", "owner": "A", "due": date(2026, 3, 20), "done": True},
    {"item": "資料庫連線數告警",     "type": "detect",  "owner": "B", "due": date(2026, 3, 9),  "done": False},
    {"item": "告警改送 on-call 呼叫", "type": "detect",  "owner": "",  "due": date(2026, 3, 9),  "done": False},
    {"item": "新功能預設加 flag",    "type": "mitigate", "owner": "C", "due": date(2026, 4, 1),  "done": False},
]

today = date(2026, 3, 16)
for a in actions:
    problems = []
    if not a["owner"]:
        problems.append("沒有負責人")
    if not a["done"] and a["due"] < today:
        problems.append(f"逾期 {(today - a['due']).days} 天")
    status = "完成" if a["done"] else "進行中"
    print(f"[{a['type']:8}] {a['item']}（{status}）", "；".join(problems))

types = {a["type"] for a in actions}
missing = {"prevent", "detect", "mitigate"} - types
print("缺少的類型：", missing or "無")
```

這個例子裡，問題從 07:50 就開始了，但 08:15 才有人處理：真正的改善空間在「偵測」與「確認」，不在修復本身。這也是為什麼行動項目要有偵測類。

## 常見錯誤

| 錯誤 | 後果 | 改法 |
|---|---|---|
| 告警寄到共用信箱 | 沒人看到，靠使用者打電話才知道 | 會呼叫人的告警送到 on-call 系統，有確認與升級機制 |
| 沒有宣告事故 | 大家以為別人在處理，或多人同時改東西 | 有疑慮就宣告，指定 IC；降級沒有成本 |
| IC 自己下去修 | 沒人看全局、沒人回答主管、沒人記錄 | IC 只指揮；人手不足時先找人支援 |
| 先重啟再說 | 證據消失，事後找不到原因，同樣的事再發生 | 先保存日誌與狀態，再重啟 |
| 一邊止血一邊追根因 | 恢復時間被拉長 | 先止血；根因在服務恢復後查 |
| 對外說「快好了」 | 一再跳票，失去信任 | 只承諾下次更新的時間 |
| postmortem 寫成檢討書 | 下次大家隱瞞資訊 | 不究責；寫系統的促成因素，不寫人 |
| 行動項目沒負責人或期限 | 半年後同樣的事故再發生 | 每項都有負責人、期限、工單，定期追蹤 |

## 動手

1. 執行上面的 Python，假設告警設對了：把 `detected` 改成 07:52、`acknowledged` 改成 07:55、`mitigated` 改成 08:14（處理本身同樣花 19 分鐘），比較止血耗時從 44 分鐘變成多少；再補上缺少負責人的行動項目。
2. 為一個熟悉的服務寫一張分級表：每一級各舉一個具體情境，並寫下要通知誰。
3. 找一次過去的事故，依本課的骨架補寫一份 postmortem：先整理時間線，再列至少三個促成因素，每個因素對應一個行動項目。
4. 做一次桌上演練（tabletop exercise）：一人扮演 IC，一人負責溝通，照著時間線推演，看看哪個環節卡住——常見的是權限、聯絡方式、runbook 找不到。
5. 相關課程：[健康檢查、備份與事故處理](#/skill/reliability)（備份、還原與 runbook）、[可觀測性：log、metrics、trace](#/skill/observability)（告警的來源）、[SLI、SLO 與錯誤預算](#/skill/slo-error-budget)（用預算決定事故的嚴重程度與後續）。
