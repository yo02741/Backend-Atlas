## 從一個具體問題開始：一間診所的三種問題

一間診所想讓員工用 LLM 查內部知識。整理需求時，發現大家要問的其實是三種很不一樣的東西：

1. **SOP 與制度**：「針扎事件怎麼通報？」「特休怎麼算？」——文件幾十份，一年改幾次，每個人都能看，答錯會出事
2. **大量的往來文件**：歷年的會議紀錄、公告、廠商合約、設備手冊——幾千份，持續增加，大多數很少被問到
3. **病歷**：「病人 1043 上次用藥調整是什麼時候？」——每天都在變，只有負責的醫療人員能看，屬於高度敏感的個人資料

如果三種都用同一套做法，一定有一種會出問題：SOP 用 RAG，可能撈到舊版或撈不到例外條款；幾千份往來文件做成 wiki，整理成本高到做不完；病歷不管放進哪一種，只要權限沒做在對的地方，就可能被不該看的人問出來。

選擇的重點不是「哪個技術比較新」，而是**資料的性質**：多少、多常變、誰能看、答錯的代價多大。

## 三種做法各是什麼

| 做法 | 一句話 | 細節 |
|---|---|---|
| RAG | 原始文件切段建索引，每次提問檢索幾段放進 prompt | [RAG 怎麼運作，以及它的限制](#/skill/rag-basics) |
| LLM Wiki | LLM 把原始資料編成一份 markdown wiki 並持續維護，提問時讀 wiki | [LLM Wiki](#/skill/llm-wiki) |
| 知識圖譜 | 把概念與關係存成圖：可以是 wiki 的 `[[連結]]`，也可以像 GraphRAG 由 LLM 自動抽取 | [知識圖譜](#/skill/knowledge-graph) |

知識圖譜通常不是單獨的選項，而是疊在另外兩者上面：wiki 的連結本身就是一張圖；GraphRAG 是 RAG 的一種延伸。

## 比較

| 面向 | RAG | LLM Wiki | 自動抽取的知識圖譜（GraphRAG 類） |
|---|---|---|---|
| 資料量 | 大量也能處理，成本主要在索引 | 前提是 wiki 放得進長上下文；適合單一主題、上百份文件的量級 | 可以處理大量，但建圖要大量 LLM 呼叫 |
| 更新頻率 | 新文件建索引後就查得到；適合常更新 | 每份新資料要 ingest 再審核，有延遲 | 新資料要重新抽取、更新社群摘要 |
| 權限控管 | 每段帶權限 metadata，檢索時過濾，做法成熟 | 一頁可能整合多個來源，權限要跟著最嚴格的來源；細緻權限不好做 | 實體與摘要混合了多份文件的內容，細緻權限更難 |
| 可追溯性 | 回答可以指回具體段落 | 回答指回 wiki 頁，wiki 再指回原始資料；兩層 | 指回實體、關係與它們的來源文件；取決於實作 |
| 建置成本 | 低到中：切段、embedding、索引 | 中到高：寫規範文件、每次 ingest 的審核 | 高：抽取與摘要的 LLM 呼叫、調整抽取品質 |
| 答案品質的穩定度 | 隨檢索結果浮動；問法一變，撈到的段落就變 | 穩定：讀的是整理過的同一份內容；但錯誤也會穩定地重複 | 對「全貌」類問題較好；細節問題仍要回原文 |
| 擅長的問題 | 「某條規定寫什麼」「某份文件的細節」 | 「A 和 B 差在哪」「這個主題目前的共識與爭議」 | 「整批文件裡有哪些主題、彼此怎麼關聯」 |

「答案品質的穩定度」那一列值得多看一眼：LLM Wiki 穩定是因為內容固定，這是優點也是風險。RAG 答錯通常是某次檢索沒撈到；wiki 答錯常常是 wiki 本身寫錯，而它會一直錯下去，直到有人修正。這也是 wiki 一定要有審核流程的原因（見 [原始資料下毒與間接提示注入](#/skill/knowledge-poisoning)）。

## 判斷順序

依序問下面這幾題，前面的答案會排除後面的選項：

1. **誰能看？** 不同人能看的範圍不同（病歷、人事、合約），權限就必須做在檢索層：每份文件或每段帶權限，查詢時依使用者身分過濾。這類資料不適合合併進一份共用的 wiki
2. **能不能送到外部模型？** 含個資、病歷、營業秘密的資料，先確認組織政策與適用的法規允不允許送到外部服務。不允許就不要送：改用組織可控的部署環境、去識別化後再處理，或者這部分不做
3. **多常變？** 每天變的資料（庫存、排班、病歷）不要做成 wiki；直接查資料庫或用 RAG
4. **多少？** 一個主題整理後放得進長上下文，wiki 可行；幾千份以上的長尾文件，用 RAG
5. **答錯的代價？** 代價高、問題又集中（SOP、制度），值得花人力做成審核過的 wiki 頁

## 組合做法：wiki 當摘要層，RAG 處理長尾

實務上常見的答案是兩者都用，各管一段：

```text
                       ┌──────────────────────────────┐
問題 ──▶ 先查 wiki ────▶│ wiki：審核過的 SOP、制度摘要 │──▶ 夠回答？──是──▶ 回答（引用 wiki 頁）
                       └──────────────────────────────┘        │
                                                               否
                                                               ▼
                       ┌──────────────────────────────┐
                       │ RAG：全部原始文件（依權限過濾）│──▶ 回答（引用原始段落）
                       └──────────────────────────────┘
```

- **wiki 收高頻、高代價、相對穩定的知識**：例如前 50 個最常被問的問題所涉及的 SOP 與制度，整理成頁、經過審核
- **RAG 收其他所有原始文件**：會議紀錄、公告、手冊，很少被問到，不值得整理，但需要時要查得到
- **wiki 頁連回原始文件**：wiki 回答不夠細時，可以順著引用找到原文，原文也在 RAG 索引裡
- **兩邊都帶版本**：SOP 改版時，wiki 頁跟著 ingest 更新；舊版原始文件在索引裡標成失效或移除

要不要先查 wiki 再查 RAG、還是同時查再合併，取決於延遲與成本，兩種都可行。關鍵是回答時標清楚來源是哪一層。

## 組織內部知識怎麼起步

以 SOP、制度文件為例，不需要一開始就決定整套架構：

1. **盤點**：列出文件、負責人、最後修訂日期、誰能看。沒有負責人、版本不明的文件，先處理文件本身，不要直接餵給模型
2. **收集真實問題**：問幾個單位最常被問什麼，整理成 30～50 題，附上標準答案與出處。這就是之後的評估集
3. **先做最小可用的 RAG**：所有文件依結構切段、帶上文件名稱、章節、版本、權限 metadata。用評估集量檢索命中率
4. **把高頻題做成 wiki 頁**：評估集裡最常見、最容易答錯的題目，整理成審核過的頁面，例如「針扎事件通報」「請假與特休」
5. **定期 lint 與更新**：文件改版時更新 wiki；評估集每次改動都重跑

這個順序的好處是每一步都有東西可以量：先有評估集，才知道加 wiki 頁之後到底有沒有變好。

## 個資、病歷與權限

### 權限要在檢索層做，不是靠提示詞

最常見的錯誤，是把所有文件都放進同一個索引，再在 prompt 裡寫「使用者不是醫師時不得透露病歷」。問題是：檢索時病歷已經被撈出來放進 context，模型能不能守住，取決於模型當下的判斷，而且有心人可以換各種問法試探。

正確的做法是**檢索時先過濾**：沒有權限的文件根本不會進到 prompt。下面用一段純 Python 對照兩種做法：

```python run
# 權限在檢索層做：先依使用者的角色過濾，再排序；沒權限的文件根本不會進到 prompt
DOCS = [  # 虛構的診所內部文件
    {"id": "sop-07", "roles": {"nurse", "doctor"}, "text": "針扎事件通報流程：依 SOP 第 3 節處理傷口後，盡快通報感染管制單位。"},
    {"id": "hr-02", "roles": {"staff"}, "text": "特休計算：依年資給假，詳見人事規章第 5 條。"},
    {"id": "pt-1043", "roles": {"doctor"}, "text": "病人 1043 用藥紀錄：每日一次，上次調整劑量為三月。"},
]

def score(query, text):
    """共同的字元 bigram 數量，當作簡化的相似度。"""
    grams = lambda s: {s[i:i + 2] for i in range(len(s) - 1)}
    return len(grams(query) & grams(text))

def retrieve(query, k=2, roles=None):
    # roles=None 代表不過濾；有給角色就只留使用者看得到的文件
    docs = DOCS if roles is None else [d for d in DOCS if d["roles"] & roles]
    return sorted(docs, key=lambda d: score(query, d["text"]), reverse=True)[:k]

def build_prompt(query, docs, extra_rule=""):
    context = "\n".join(f"[{d['id']}] {d['text']}" for d in docs)
    return f"{extra_rule}只根據以下資料回答，並引用編號。\n<資料>\n{context}\n</資料>\n問題：{query}"

query = "病人 1043 上次用藥調整是什麼時候？"
user_roles = {"staff", "nurse"}          # 提問的是一位護理師

print("=== 做法 A：全部檢索，靠提示詞要求「不得透露病歷」")
docs = retrieve(query)
print(build_prompt(query, docs, extra_rule="使用者不是醫師時，不得透露病歷內容。"))
print("→ 病歷已經在 prompt 裡：", any(d["id"] == "pt-1043" for d in docs))

print("\n=== 做法 B：檢索時先依角色過濾")
docs = retrieve(query, roles=user_roles)
print(build_prompt(query, docs))
print("→ 病歷已經在 prompt 裡：", any(d["id"] == "pt-1043" for d in docs))
```

做法 A 的 prompt 裡已經有病歷內容；模型這次可能守住，下次換個問法就不一定。做法 B 裡病歷從頭到尾沒有出現，模型想洩漏也沒有東西可以洩漏。

實作上的幾個要點：

- **權限跟著段落走**：每一段都帶上來源文件的權限（角色、部門、個案負責人）。文件權限改了，索引裡的段落要同步更新
- **身分來自登入系統，不是來自提問內容**：「我是醫師」這句話不能當成授權依據；角色要從驗證過的 session 或 token 取得（見 [RBAC 與 ABAC](#/skill/rbac-abac)）
- **資料存在 PostgreSQL 時**，可以考慮用 [Row Level Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) 讓資料庫本身依使用者過濾，應用程式少寫一層就少一個漏洞
- **wiki 頁的權限取最嚴格的來源**：一頁整合了公開 SOP 與限閱的檢討報告，這一頁就是限閱。比較單純的做法是不同權限等級分開成不同的 wiki
- **記錄誰查了什麼**：敏感資料的查詢要留存稽核紀錄

### 不要送到外部模型的資料

病歷、身分證號、病人聯絡方式這類資料，在送進任何外部模型之前，先確認組織政策與適用法規。預設的安全做法是：

- 敏感資料不進共用索引，也不送到外部服務
- 需要用 LLM 處理時，評估在組織可控的環境部署模型，或先去識別化
- 結構化資料（用藥紀錄、檢驗數值）直接用有權限控管的查詢回答，不需要經過 RAG

這部分的要求依組織與法規而異，上面是技術上的預設方向，不是法律意見。

## 常見錯誤

| 錯誤 | 後果 | 改法 |
|---|---|---|
| 所有文件放進同一個索引，權限寫在 prompt 裡 | 換個問法就問得出不該看的內容 | 檢索層依身分過濾；敏感資料分開索引或不進索引 |
| 每天變動的資料做成 wiki | wiki 永遠落後，回答過時 | 即時資料直接查資料庫；wiki 只放相對穩定的知識 |
| 幾千份長尾文件全部要整理成 wiki | 整理與審核成本失控，做不完 | wiki 只收高頻、高代價的主題；其他交給 RAG |
| 沒有評估集就開始調整 | 無法知道改動有沒有變好 | 先收集真實問題與標準答案，每次改動都重跑 |
| wiki 頁合併了不同權限的來源 | 低權限的人透過 wiki 讀到高權限的內容 | 頁面權限取最嚴格的來源，或分開 wiki |
| SOP 改版後只更新了原始文件 | wiki 和索引裡還是舊內容，兩邊說法不一 | 改版流程同時觸發 wiki ingest 與索引更新 |

## 動手

1. 按上面程式的「在 Playground 開啟」，把 `user_roles` 改成 `{"staff", "doctor"}`，確認醫師查得到病歷；再改成 `{"staff"}`，看針扎 SOP 是否也被過濾掉。
2. 拿一個自己熟悉的組織（社團、團隊），把它的文件分成「高頻穩定」「長尾」「敏感」三類，各自決定用 wiki、RAG 還是不處理。
3. 寫 10 題評估題，每題附標準答案與出處；之後無論選哪種做法，都用這組題目比較。
4. 讀 [原始資料下毒與間接提示注入](#/skill/knowledge-poisoning)：組合做法多了一條「原始資料 → wiki」的路徑，也多了一個被汙染的入口。
