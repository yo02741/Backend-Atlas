## 從一個具體問題開始：答案就在文件裡，系統卻說找不到

一間網路商店把退貨政策接上客服機器人。政策文件裡寫得很清楚：「退款會在收到退貨商品後十四個工作天內退回原付款方式。」使用者問「退款要幾天？」，機器人卻回答：

> 文件中沒有提到退款的處理時間，建議聯絡客服。

模型沒有壞，文件也有上傳。問題出在模型根本沒看到那句話：系統把文件切成好幾段，那句話剛好被切成兩半，「退款會在收到退貨商品後十四個」在一段，「工作天內退回原付款方式」在另一段。檢索只挑出前一段，模型看到的資訊不完整，只好說找不到。

換個問法，「客製化商品可以退貨嗎？」，結果更糟：檢索挑中的那一段寫著「商品到貨後七天內可以申請退貨」，而「客製化商品不接受退貨」被切到別段。模型照著看到的內容回答「可以」，語氣還很肯定。

這兩種錯誤都不是模型能力的問題，而是 **RAG（Retrieval-Augmented Generation，檢索增強生成）** 流程裡「把哪些文字交給模型」這一步出錯。要修，得先知道每一步在做什麼。

## 運作原理：從文件到回答

RAG 分成兩個階段：事先建好索引（離線），使用者提問時檢索並生成（線上）。

```text
離線：文件 ──切段──▶ 段落 ──embedding──▶ 向量 ──寫入──▶ 向量索引
                                                         │
線上：問題 ──embedding──▶ 查詢向量 ──相似度搜尋 top-k──────┘
                                   │
                                   ▼
                     候選段落 ──重新排序──▶ 前幾段 ──放進 prompt──▶ LLM 生成回答
```

| 步驟 | 做什麼 | 輸出 | 會出錯的地方 |
|---|---|---|---|
| 1. 切段（chunking） | 把長文件切成幾百字左右的段落 | 段落清單（附來源、標題等 metadata） | 一個事實被切到兩段 |
| 2. Embedding | 用 embedding 模型把每段變成一個固定長度的向量 | 每段一個向量（幾百到幾千維） | 換模型後新舊向量不能混用 |
| 3. 寫入向量索引 | 存起來，讓「找最接近的向量」變快 | 索引 | 近似索引可能漏掉真正最接近的幾段 |
| 4. 查詢 embedding | 用**同一個**模型把問題變成向量 | 查詢向量 | 問題用詞和文件差很多時，向量不夠接近 |
| 5. 相似度檢索 top-k | 找出與查詢向量最接近的 k 段 | k 個候選段落 | 一定會回傳 k 段，就算都不相關 |
| 6. 重新排序（rerank） | 用另一個模型把問題和每段一起讀，重新打分 | 排序後的前幾段 | 多一次模型呼叫，增加延遲與成本 |
| 7. 組 prompt 生成 | 把段落與問題放進 prompt，要求依據段落回答並標出來源 | 回答（附引用） | 模型忽略段落、自己補內容 |

### Embedding 與相似度

Embedding 模型把一段文字變成一個向量，訓練目標是讓意思相近的文字，向量也相近。比較兩個向量最常用 **cosine 相似度**：兩個向量夾角的餘弦值，越接近 1 越相似。

```text
cos(a, b) = (a · b) / (|a| × |b|)
```

cosine 只看方向、不看長度，所以一段長文和一段短文只要「講的東西比例一樣」，分數就會高。這一點下面會看到它的副作用。

### 向量索引

資料少時可以把查詢向量跟每一段都算一次（精確搜尋）。段落到幾十萬、幾百萬時，通常改用**近似最近鄰（ANN）**索引，例如 HNSW、IVF：用一點準確度換速度，偶爾會漏掉真正最接近的段落。PostgreSQL 可以用 pgvector 擴充存向量並建這類索引；也有專門的向量資料庫。選哪一種對 RAG 的流程沒有影響，影響的是規模、延遲與維運。

### 重新排序

向量檢索是「問題一個向量、段落一個向量，各自算好再比」，速度快但比較粗。常見做法是先用向量檢索撈 20～50 段候選，再用 reranker（把問題和段落**一起**讀進去打分的模型）挑出最相關的 3～5 段。前一步負責「別漏掉」，這一步負責「挑準」。

### 組 prompt

最後把段落和問題組成 prompt。幾個實際有用的寫法：

- 每段前面標編號與來源（例如 `[2] 退貨政策 §3`），要求回答時引用編號
- 明寫「只根據以下段落回答；段落裡沒有就說找不到」
- 段落放在明確的區塊裡，跟系統指令分開（這也是防間接提示注入的第一步，見 [原始資料下毒與間接提示注入](#/skill/knowledge-poisoning)）

## 切段：大小與重疊的取捨

切段是整個流程裡最常被忽略、影響卻最大的一步。

| | 小段（例如 100～200 字） | 大段（例如 1,000 字以上） |
|---|---|---|
| 檢索精準度 | 高：一段只講一件事，向量很集中 | 低：一段講很多事，向量被平均掉 |
| 上下文完整度 | 低：主詞、條件、例外常在別段 | 高：前因後果都在同一段 |
| 放進 prompt 的成本 | 低，可以多放幾段 | 高，放幾段就佔滿 context |
| 典型失敗 | 「十四個工作天」找到了，但不知道是在講什麼 | 答案在段落裡，但分數被稀釋，排不進 top-k |

**重疊（overlap）** 是讓相鄰兩段共用一小截文字，例如每段 500 字、重疊 100 字。一句話剛好落在切點上時，至少有一段會完整包含它。重疊不是越大越好：重疊越大，段數越多、索引越大，檢索結果也更容易出現幾段幾乎一樣的內容，佔掉 top-k 的名額。

固定字數切段最簡單，但它不知道文件結構。比較穩的做法：

- **依結構切**：先依標題、段落、條列切，太長的再依字數細分
- **每段附上 metadata**：文件名稱、章節標題、版本或更新日期。「退款會在…」這段如果前面帶著「退貨政策 › 退款」，檢索與生成都會更準
- **表格與程式碼不要從中間切**：半張表格比沒有還糟

## 實際程式：用詞頻向量做一個極小的檢索

下面不用真的 embedding 模型，改用「字元 bigram 的出現次數」當向量（中文沒有空白分詞，連續兩個字是最簡單的替代），再用 cosine 相似度檢索。流程和真實的 RAG 一樣，差別只在向量怎麼來。純標準函式庫，可以直接執行：

```python run
import math
from collections import Counter

# 虛構的退貨政策
DOC = (
    "退貨政策。商品到貨後七天內可以申請退貨，申請時要附上訂單編號。"
    "客製化商品不接受退貨。退款會在收到退貨商品後十四個工作天內"
    "退回原付款方式。退貨運費由買家負擔，商品有瑕疵時由公司負擔。"
)
FACT = "退款會在收到退貨商品後十四個工作天內退回原付款方式"   # 用來檢查答案是否完整

def chunk(text, size, overlap):
    """固定大小切段：每段 size 個字元，相鄰兩段重疊 overlap 個字元。"""
    step = size - overlap
    out, start = [], 0
    while True:
        out.append(text[start:start + size])
        if start + size >= len(text):
            return out
        start += step

def vec(text):
    """字元 bigram → 次數。真實系統這一步是呼叫 embedding 模型。"""
    s = "".join(ch for ch in text if ch not in "，。？、 ")
    return Counter(s[i:i + 2] for i in range(len(s) - 1))

def cosine(a, b):
    dot = sum(a[k] * b[k] for k in a if k in b)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0

def search(query, chunks, k=2):
    q = vec(query)
    return sorted(((cosine(q, vec(c)), c) for c in chunks), reverse=True)[:k]

# 1) 切段大小改變檢索結果
query = "退款要幾個工作天才會退回？"
for size, overlap in [(20, 0), (20, 8), (30, 10)]:
    chunks = chunk(DOC, size, overlap)
    top = search(query, chunks)
    print(f"--- size={size} overlap={overlap}（{len(chunks)} 段）top-1 含完整事實：{FACT in top[0][1]}")
    for score, c in top:
        print(f"  {score:.3f}  {c}")

# 2) 相似不等於相關：top-1 寫著「可以申請退貨」，真正的答案在第 2 名
print("\n--- 客製化商品可以退貨嗎？")
for score, c in search("客製化商品可以退貨嗎？", chunk(DOC, 40, 10)):
    print(f"  {score:.3f}  {c}")

# 3) 文件裡根本沒有答案，檢索照樣回傳 top-k
print("\n--- 退貨可以換成購物金嗎？")
for score, c in search("退貨可以換成購物金嗎？", chunk(DOC, 40, 10)):
    print(f"  {score:.3f}  {c}")
```

輸出重點：

- `size=20, overlap=0`：top-1 有「退款…十四個工作天內」，但「退回原付款方式」被切到下一段
- `size=20, overlap=8`：top-1 有「十四個工作天內退回原付款方式」，但主詞「退款」不見了
- `size=30, overlap=10`：top-1 包含完整的那句話
- 「客製化商品」那一題，第 1 名是寫著「可以申請退貨」、結尾的「客製化商品不接受退貨」還被切斷的段落，因為它跟問題共用「可以」「退貨」這些字；完整寫著「不接受退貨」的段落排第 2，兩者分數只差一點點
- 「購物金」那一題，文件根本沒提，檢索還是照樣回傳兩段，分數只是比較低

## 限制：相似不等於相關

### 相似度量的是「像不像」，不是「能不能回答」

上面的「可以申請退貨」vs.「不接受退貨」就是典型：否定、例外、條件句，在向量上和肯定句很接近。真的 embedding 模型比詞頻向量聰明很多，但「相似」與「回答得了這個問題」仍然是兩回事。reranker 能改善一部分，prompt 裡要求「找不到就說找不到」、並且附引用，讓錯誤至少看得出來。

### 檢索一定會回傳東西

top-k 的意思是「最接近的 k 段」，不是「相關的段落」。文件沒有答案時，它照樣交出 k 段最不離題的內容，模型就可能拿來硬湊。常見補法：設相似度門檻（低於門檻當作沒找到）、讓 reranker 的分數決定要不要回答、在評估集裡放「文件沒有答案」的問題。門檻值跟 embedding 模型有關，換模型要重新調。

### 每次提問都從零拼湊

RAG 不會記得上一次的整理結果。每一次提問，都是重新檢索幾段、重新拼湊。這對「某條規定是什麼」這種問題沒問題，對下面這些就吃力：

- **需要彙整很多文件**：「所有政策裡，哪些有例外條款？」答案分散在幾十份文件，top-k 只看得到其中幾段
- **需要比對**：「新舊兩版的退貨政策差在哪？」兩版都被索引時，檢索可能各撈一半
- **知識本身是零碎的**：一個概念散在十份會議紀錄裡，每份只講一點

把整理結果累積下來、而不是每次重做，是 [LLM Wiki](#/skill/llm-wiki) 的出發點。

### 其他常見的弱點

- **過時與矛盾**：舊版文件沒有下架，新舊版本都被檢索到。要靠 metadata（版本、生效日）過濾，不能靠模型自己判斷哪個新
- **代號、數字、專有名詞**：訂單編號、錯誤碼、產品型號在向量空間裡不一定靠得近。常見做法是**混合檢索**：關鍵字搜尋（例如 BM25）和向量檢索各撈一批再合併
- **換 embedding 模型要重建整個索引**：不同模型產生的向量不能互相比較，就算維度一樣也不行

## 評估：怎麼知道改了有沒有變好

改切段大小、換模型、加 reranker 之前，先準備一組固定的評估題，每次改動都跑同一組。

| 指標 | 怎麼量 | 看的是 |
|---|---|---|
| 檢索命中率（hit rate / recall@k） | 每題標出「答案在哪一段」，看 top-k 裡有沒有它 | 檢索這一步有沒有把對的段落找出來 |
| 引用是否存在 | 回答有沒有附段落編號或文件來源 | 讀者能不能回頭查證 |
| 引用是否支持答案 | 人工或另一個模型檢查：引用的段落真的寫了這件事嗎 | 模型有沒有「附了引用但內容是自己編的」 |
| 拒答是否正確 | 放幾題文件裡沒有答案的問題 | 找不到時會不會老實說找不到 |

評估題不用很多，幾十題、涵蓋常見問法和已知出過錯的問題就有用。重點是**固定下來**：同一組題目，改動前後的命中率一比就知道。檢索命中率低時，先修切段與檢索，不要先改 prompt；檢索對了、回答還是錯，才是 prompt 或模型的問題。

## 常見錯誤與症狀

| 症狀 | 常見原因 | 怎麼查、怎麼修 |
|---|---|---|
| 回答「文件中沒有提到」，但其實有 | 事實被切斷；top-k 太小；問題用詞和文件差很多 | 用評估題看 top-k 有沒有包含答案段落；加重疊或改依結構切；加關鍵字檢索 |
| 回答很肯定但是錯的 | 檢索到相似但不相關的段落（否定句、例外） | 加 reranker；prompt 要求引用；檢查引用段落是否真的支持答案 |
| 引用了舊版規定 | 舊文件還在索引裡 | 文件下架流程要同步刪索引；段落帶版本與生效日 metadata，檢索時過濾 |
| pgvector 寫入時報 `expected 1536 dimensions, not 768` 之類的錯誤 | 欄位宣告的維度和 embedding 模型輸出的維度不同（常見於換模型） | 欄位維度跟著模型；換模型要重新 embedding 全部段落，新舊向量不能混在同一個索引 |
| 模型呼叫報 context 太長 | 段落太大或放太多段 | 減少 k、縮小段落、先 rerank 再只放前幾段 |
| 同一題每次回答不一樣 | 檢索結果相近的段落分數接近、順序不穩；生成本身有隨機性 | 固定評估題觀察；分數接近的候選交給 reranker 決定 |

上表 pgvector 的錯誤訊息依版本可能略有不同，關鍵是「維度不符」。

## 動手

1. 按上面程式的「在 Playground 開啟」，把 `(30, 10)` 改成 `(30, 0)`、`(60, 15)`，觀察 top-1 是否還包含完整事實、分數怎麼變。
2. 在同一段程式加一個門檻：分數低於 0.2 就印「找不到」，看看「購物金」那題會不會被擋下、正常的題目會不會被誤擋。
3. 程式題 [固定大小＋重疊的切段](#/exercise/rag-basics-1)：自己實作 `chunk()`，處理重疊大於段落長度、最後一段不足長度這些邊界情況。
4. 接著讀 [LLM Wiki](#/skill/llm-wiki)：同樣的退貨政策，如果事先整理成一頁「退貨與退款」的 wiki 頁，上面三題會怎麼變。
