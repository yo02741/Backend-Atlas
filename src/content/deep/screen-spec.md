## 從一個具體問題開始：「我的掛號」改了三輪還在改

「我的掛號」頁的需求散在四個地方：設計稿只有一張有資料的畫面，API 文件是後端的 `/openapi.json`，取消規則在一段聊天紀錄裡，驗收是測試人員自己想的。交給 AI 實作後，三輪修改的內容是這些：

- 第一輪：沒有預約時畫面一片空白；載入失敗也是一片空白。
- 第二輪：取消超過期限時，畫面顯示英文的 `Cancel deadline passed`；手機上取消確認視窗超出畫面。
- 第三輪：設計稿上每筆預約顯示看診日期、時段與醫師姓名，但 `GET /appointments` 回傳的 `AppointmentOut` 只有 `session_id`，AI 自己寫了一個 `doctorName` 欄位，畫面上一整欄空白。同一輪還在爭論「取消後要不要提示退費」，沒有人負責回答。

每一輪改的都是「沒有人事先決定」的事。把一個畫面要決定的事集中寫成一頁，空著的地方在動工前就看得出來。

## 一頁規格的十節

| 節 | 寫什麼 | 用到的詞彙在哪一課 |
|---|---|---|
| 目的與入口 | 誰用、完成什麼事、從哪裡進來、網址參數 | [網址與瀏覽紀錄](#/skill/urls-history) |
| 版面 | 區域與排列，用文字線框或版面模式的名字 | [版面模式與斷點表](#/skill/layout-patterns) |

| 狀態表 | 區域 × 狀態，每格寫畫面上出現什麼 | [互動狀態](#/skill/ui-states)、[API 的四種狀態](#/skill/api-states) |
| 文案表 | 每段文字的位置、字串、變數、錯誤對應 | [回饋](#/skill/feedback) |

規格是索引，不是百科：設計稿、OpenAPI、元件庫文件都用連結指過去，規格只寫這個畫面做的決定。和 [把畫面描述成文字](#/skill/describe-ui) 的差別是用途：五段式描述是一次交給 AI 的一段話，規格是放在 repo 裡、會被審查、會跟著程式改版的文件，也是驗收時逐條對照的清單。

## 一份完整的範例

下面是「我的掛號」的規格。資料來源照 companion 的 clinic-api 實際產生的 OpenAPI 3.1 規格。

```markdown
# 我的掛號（/my/appointments）

更新：2026-11-19　設計稿：<連結>　API：clinic-api /openapi.json

## 目的與入口
- 病患查看自己的預約、取消還沒看診的預約。
- 入口：頁首「我的掛號」、掛號成功頁的「查看我的掛號」。
- 網址沒有參數；分頁用「載入更多」，不寫進網址。

## 版面
app shell 的主內容區：標題列（標題、筆數）→ 預約清單 → 「載入更多」。

## 元件清單
| 區域 | 元件 | 來源 | 備註 |
|---|---|---|---|
| 預約清單 | AppointmentCard | 新做 | props：appointment；emits：cancel |
| 狀態標籤 | ElTag | 元件庫 | 候診、已報到、已取消 |
| 取消確認 | CancelDialog | 新做 | 原生 dialog 的 showModal() |
| 成功提示 | Toast | src/components/ui/Toast.vue | role="status" |

## 狀態表
| 區域 | loading | empty | error | 送出中 | 其他 |
|---|---|---|---|---|---|
| 清單 | 3 張 Skeleton 卡片 | 「還沒有掛號」＋「去掛號」按鈕 | inline Alert＋「重試」 | — | 已有資料再抓：保留清單，標題旁小 spinner |
| 取消按鈕 | — | — | — | 停用、文字「取消中…」 | 已報到、已取消的不顯示按鈕 |
| 載入更多 | 按鈕停用＋spinner | next_cursor 為 null 時隱藏 | 按鈕下方錯誤文字＋可再按 | — | — |
| 取消確認 | — | — | 409、5xx 顯示在 Dialog 內 | 兩顆按鈕都停用 | — |

## 文案表
| 位置 | 字串 | 備註 |
|---|---|---|
| 標題 | 我的掛號（{count}） | count 是目前載入的筆數 |
| empty | 還沒有掛號 | 按鈕：去掛號 |
| 清單錯誤 | 預約清單暫時無法載入 | 按鈕：重試 |
| Dialog 標題 | 取消 {date} {period} 的掛號？ | |
| 409 cancel-deadline-passed | 已超過取消期限，請致電櫃台 | 不顯示後端的英文 title |
| 取消成功 | 已取消 {date} {period} 的掛號 | Toast，5 秒 |

## 斷點表
| 區域 | 390 | 768 | 1024 | 1280 |
|---|---|---|---|---|
| 清單 | 1 欄卡片 | 2 欄 | 2 欄 | 3 欄 |
| 取消確認 | 底部 Sheet | 置中 32rem | 同左 | 同左 |

## 資料來源
| 資料 | API | 欄位 | 格式 |
|---|---|---|---|
| 清單 | GET /appointments?cursor=&limit=20 | items[].id、number、status、created_at；next_cursor | status 對應：booked 候診、checked_in 已報到、cancelled 已取消 |
| 取消 | POST /appointments/{id}/cancel | 回傳更新後的 AppointmentOut | 成功後重抓清單 |
| 看診日期、時段、醫師 | （缺）AppointmentOut 只有 session_id | | 見待決事項 1 |

## 互動與焦點
- 按「取消」：開 CancelDialog，焦點在「保留掛號」；Esc 關閉，焦點回到該筆的「取消」。
- 確定取消成功：Dialog 關閉、該筆狀態變「已取消」、焦點移到清單標題、顯示 Toast。

## 驗收條件
1. 沒有任何預約時，顯示「還沒有掛號」與「去掛號」。檢查：mock 回 items: []。
2. 清單載入失敗時顯示 Alert 與「重試」，按重試多一筆請求。檢查：Network 的 Block request URL。
3. 超過期限取消時，Dialog 內顯示「已超過取消期限，請致電櫃台」。檢查：mock 回 409。
4. 只用鍵盤完成一次取消，Dialog 關閉後焦點在清單標題。檢查：Console 的 live expression document.activeElement。
5. 390px 沒有橫向捲軸。檢查：document.documentElement.scrollWidth > innerWidth 為 false。

## 不在範圍
- 改期、重新掛號、篩選與排序。

## 待決事項
1. 看診日期、時段、醫師姓名的來源：後端在 AppointmentOut 加欄位，或另開端點？（後端，11/22 前）
2. 取消後要不要提示退費？（櫃台主管）
```

## 每一節怎麼寫

### 狀態表：空格就是沒決定

列是區域，欄是狀態。欄位至少有 loading、empty、error；有送出的操作再加「送出中」，有權限差異再加「沒有權限」。每一格寫畫面上出現的東西（元件與文字），不寫「適當處理」。不適用的格子寫「—」，和「還沒想」分開。

範例裡「取消按鈕」那一列有一格寫「已報到、已取消的不顯示按鈕」。這種跟資料狀態有關的條件很容易漏，寫在表裡就會被看到。

### 文案表：字串照抄、錯誤對到原因

每段文字一列，寫實際的字串與變數。錯誤訊息依原因分列：網路錯誤、5xx、各種 4xx。後端回 Problem Details 時，用 `type` 對應前端的文案（範例的 `cancel-deadline-passed`），不直接把後端的英文 `title` 顯示在畫面上。

### 資料來源：寫到欄位，對不上就列成待決

每塊資料寫 API、欄位、格式。對照 OpenAPI 時常會發現缺口：範例的設計稿要顯示看診日期與醫師，但 `AppointmentOut` 的欄位是 `id`、`session_id`、`patient_id`、`number`、`status`、`created_at`。缺口寫進「待決事項」並指定誰回答，實作時就不會出現一個編出來的 `doctorName`。

`status` 在規格裡的型別是 `string`，沒有列出可能的值；文案對應寫在資料來源表裡，未知的值也要決定怎麼顯示。

### 驗收條件：每條附檢查方法

格式是「在什麼情況下、做什麼、看到什麼」，再加一句檢查方法。檢查方法讓條件可以被重複執行：手動驗收時照著做，之後也能直接改寫成 Playwright 測試。

寫不出檢查方法的條件要改寫。「載入時要有回饋」改成「按下『載入更多』後按鈕立刻停用並顯示 spinner，Network 只多一筆請求」，「Dialog 要好用」改成範例的第 4 條。

### 不在範圍與待決事項

「不在範圍」讓實作的人不用猜「篩選要不要順便做」。「待決事項」寫出問題、負責回答的人與期限；還沒回答的部分照「先不做」處理，並在交付時列出來。

## 把規格交給 AI

規格放在 repo 裡時，交給 AI 的指示可以很短：指出規格檔的路徑，要求每一節都對到程式、文案只用文案表的字串、資料只用資料來源表的欄位、待決事項先不做，完成後逐條回報驗收條件。

AI 的回報要能對回規格：哪一格狀態用了哪個元件、哪條驗收用什麼方法檢查、看到什麼。回報裡出現規格沒有的東西（新的文案、新的欄位、多做的篩選），先問來源。

## 常見錯誤

- **只有成功的畫面**：狀態表只填了 success 那一欄。實作出來的 empty 與 error 是一片空白，或是共用同一個「沒有資料」的畫面，網路斷掉時使用者以為自己沒有預約。
- **文案寫「適當的錯誤訊息」**：畫面上就會出現 `Something went wrong` 或後端的英文 `title`。
- **欄位用猜的**：資料來源沒有對照 OpenAPI，實作時才發現欄位不存在。型別檢查會報 `TS2339: Property 'doctorName' does not exist on type …`；沒有用產生的型別時，連這個錯誤都不會出現，只會看到空白的一欄。
- **斷點只寫「要 RWD」**：每個區域在哪個寬度變化，由實作自己決定。
- **驗收條件無法檢查**：「操作流暢」「符合設計稿」沒有工具可以判定通過與否。
- **規格和程式各走各的**：規格放在 repo 外的文件系統，畫面改了沒人回頭更新。放在 repo 裡，改畫面的 PR 一起改規格。

## 動手

1. 挑一個現有的畫面，照十節寫一頁規格。先填狀態表與資料來源，這兩節最常發現沒決定的事。
2. 打開那個畫面的 API 規格（FastAPI 的 `/openapi.json` 或 repo 裡的 YAML），把資料來源表的每個欄位都找到；找不到的寫進待決事項。
3. 用 [互動狀態實驗室](#/lab/UiStatesLab) 與 [API 的四種狀態實驗室](#/lab/ApiStatesLab) 對照，替自己的狀態表補上漏掉的狀態。
4. 把規格的驗收條件改寫成 Playwright 測試的標題清單，每條對到一個 `test()`，見 [驗收 AI 產出的前端](#/skill/ai-acceptance)。
