## 從一個具體問題開始：公告出來兩天後，才知道自己有沒有用到

週四下午，一個很多專案都會用到的檔案解析函式庫發布安全公告：處理特製的檔案時可能執行任意程式碼，嚴重度標示為最高一級，修正版已經釋出。某醫院資訊室接下來兩天是這樣過的：

- 週四 15:00：有人在群組貼公告，問「我們有用到嗎？」每個人各自搜尋自己負責的 repo，找到三個直接依賴它的服務。
- 週四 17:00：有人想到間接依賴與 base image 裡也可能有。正式環境現在跑的是哪一版映像、裡面裝了什麼，沒有人能馬上回答。
- 週五 10:00：影像上傳閘道是廠商提供的設備，裡面有沒有用到只能寫信問廠商。
- 週五 14:00：清查時發現一台兩年前建的報表主機，不在任何清單上，沒有負責人，而且有一個 port 對外開著。
- 週五 18:00：確認五個服務受影響，其中一個對外。升版、重建映像、部署，兩小時做完。

修補只花了兩小時，「搞清楚自己有沒有受影響」花了兩天，那個對外的服務在這兩天裡一直開著。慢的原因是平常沒有三樣東西：一份可以查詢的資產清冊、一套決定先修哪個的規則、一條走得快的修補流程。上線之後的資安工作，主要就是把這三樣東西維持在可用的狀態。

## 資產清冊：先知道有什麼

資產清冊要能回答的問題是：「這個元件的這個版本，我們哪裡有？誰負責？」每一筆資產至少記這些：

| 欄位 | 內容 | 用在哪裡 |
|---|---|---|
| 名稱與類型 | 主機、容器服務、資料庫、對外網域、廠商設備 | 查詢的單位 |
| 負責人 | 一個團隊或值班窗口，不是「大家」 | 弱點要派給誰 |
| 對外與否 | 網際網路可達、只有內網、只有管理網段 | 排優先序 |
| 重要性與資料等級 | 停擺的影響、有沒有個資或病歷 | 排優先序 |
| 軟體組成 | 作業系統與版本、映像的 digest、依賴清單 | 判斷受不受影響 |

清冊要**從實際狀態產生**，不靠人工填表；人工維護的試算表在第一次緊急加機器之後就開始過期。常見的資料來源：

- 雲端與虛擬化平台的 API、Kubernetes 的工作負載清單：實際在跑的主機與服務。
- DNS 區域檔、憑證清單、防火牆與負載平衡器的設定：對外有哪些網域、哪些 port 真的開著。
- 建置時產生的 SBOM：每個映像裡有哪些元件與版本。SBOM 的格式與產生方式見 [依賴與供應鏈安全](#/skill/supply-chain)，這裡只用它的結果。

另外要定期從外面看自己一次：列出組織名下的公開 IP 與網域，確認每一個開著的 port 都對得到清冊裡的一筆資產與負責人。對不到的，就是開頭那台報表主機。廠商設備看不到內部組成，清冊上至少記型號、韌體版本與廠商的安全公告管道。

## 弱點從哪裡來，各用什麼方式找

弱點有公開編號時叫 **CVE**（例如 `CVE-年份-流水號`），但不是所有問題都有編號：設定錯誤和自己程式裡的缺陷就沒有。來源不同，找的方式也不同：

| 來源 | 例子 | 找的方式 | 工具或基準舉例 | 什麼時候跑 |
|---|---|---|---|---|
| 程式的依賴 | 第三方套件有公開弱點 | 依賴掃描（SCA）：比對 lock 檔與弱點資料庫 | osv-scanner、pip-audit、npm audit | 每次建置，加上每日排程 |
| 容器映像 | base image 裡的系統套件過舊 | 映像掃描 | Trivy、Grype | 建置時；registry 與執行中的映像定期重掃 |
| 作業系統與主機 | 核心、OpenSSL、SSH 版本過舊 | 主機弱點掃描 | OpenVAS、Nessus、Qualys | 每週或每月排程 |
| 設定錯誤 | 預設密碼、儲存桶公開、管理介面對外 | 設定稽核：對照安全基準逐項檢查 | CIS Benchmarks、kube-bench、Lynis | 排程，加上基礎設施變更時 |
| 自己的程式 | 注入、存取控制缺漏 | 靜態分析（SAST）、動態掃描（DAST）、程式碼審查 | Semgrep、Bandit、OWASP ZAP | SAST 在 CI；DAST 對測試環境 |

依賴掃描的細節（資料庫、怎麼判讀結果）在 [依賴與供應鏈安全](#/skill/supply-chain)；自己程式的弱點類別在 [OWASP Top 10 地圖](#/skill/owasp-top10)。這裡補充幾個維運上的重點：

- **已經上線的也要重掃**。映像建置當天掃描是乾淨的，不代表三個月後還是：弱點是之後才公布的。掃描的對象是「現在正在跑的東西」。
- **主機掃描分登入式與非登入式**。非登入式從網路上觀察服務的回應推測版本；登入式讀主機上實際安裝的套件清單，結果比較準，代價是掃描器要有一個受控的唯讀帳號（保管方式見 [秘密管理](#/skill/secrets)）。
- **DAST 會真的送請求**。對測試環境跑；要掃正式環境時先取得同意、避開尖峰、通知值班人員。任何掃描都只針對自己擁有、或已取得書面授權的範圍。
- **掃描器的弱點資料庫要更新**。資料庫停在半年前的掃描器會一直回報「沒有問題」，斷網環境要另外安排同步。
- 掃描結果有誤判也有漏判。結果進同一個追蹤系統、去除重複、派給資產的負責人，才算開始處理。

## 嚴重度不等於優先序

掃描報告通常附一個 **CVSS** 分數（0 到 10，由 FIRST 維護的評分標準）。CVSS 的基本分數描述弱點本身的技術特性：能不能從網路觸發、需不需要先有權限、對機密性、完整性、可用性的影響多大。它不知道這個弱點在自己的環境裡是什麼處境，所以只照分數排會出兩種錯：把人力花在內網一般主機的 9.8 分上，同時讓對外服務上一個正被利用的 7.5 分排在後面。

排優先序時要一起看幾個問題，各有不同的資料來源：

| 問題 | 資料來源 | 說明 |
|---|---|---|
| 技術上多嚴重？ | CVSS | 與環境無關的基準；同一個弱點在不同版本的 CVSS 下分數可能不同 |
| 有沒有已知被實際利用？ | CISA KEV | 美國 CISA 維護的清單，收錄有證據顯示已被利用的弱點；不在清單上不代表沒被利用 |
| 近期被利用的可能性多高？ | EPSS | FIRST 維護的模型，對每個 CVE 估計一個機率，會隨時間更新 |
| 對外嗎？ | 資產清冊 | 網際網路可達的服務最先被碰到 |
| 這個資產多重要？ | 資產清冊 | 停擺的影響、資料的敏感度 |
| 有弱點的程式真的會被執行到嗎？ | 開發團隊的分析 | 有依據時可以降級，並把依據寫下來 |

怎麼把這些組合成等級由組織的政策決定，重點是**規則事先寫好、可以重算**。一個簡單的做法是計分：嚴重度給基本分，已知被利用、對外、重要資產各自加分，再依總分分級，後面的程式就是這樣做的。資產不在清冊裡時，對外與否和重要性都不知道，用最壞的情況算。

## 修補流程

一筆弱點從發現到結案：查清冊判定受不受影響 → 依規則得出等級與期限、派給資產負責人 → 修補（升級套件、重建映像、套用系統更新或改設定）→ 測試並依變更流程上線 → 重新掃描驗證 → 結案留紀錄。

修補期限依等級分級。下表只是示意，實際的天數依主管機關規範與組織政策訂定：

| 等級 | 典型情況 | 期限（示意） |
|---|---|---|
| P1 | 已知被利用，而且對外或在重要資產上 | 3 天內，必要時當天 |
| P2 | 高嚴重度，並有一項加重因素 | 14 天內 |
| P3 | 高嚴重度但在內網的一般資產，或中等嚴重度 | 30 天內 |
| P4 | 低嚴重度 | 90 天內或隨例行更新 |

幾個實務上的重點：

- **修補是變更**。每月的作業系統更新這類例行修補，可以登記成事先核准的標準變更；正被利用的弱點走緊急變更，先修、事後補齊紀錄。分類方式見 [受監管環境的變更管理](#/skill/change-management)。
- **修補也會弄壞東西**。先上測試環境、分批上線、準備好回復方式（見 [部署策略與資料庫遷移](#/skill/cd-strategies)）。
- **更新完要讓它生效**。套件更新後，執行中的程序仍然載入舊版的函式庫，要重啟服務；核心更新要重開機；映像重建後，用到它的服務都要重新部署。
- **以重新掃描的結果結案**，不是以「已部署」結案。逾期筆數與各等級的平均修補時間要定期檢視。

### 不能馬上修的時候：補償控制

沒有修正版、廠商設備要等韌體、停機時段還沒到，這些情況下弱點會多留一段時間。這時用**補償控制**（compensating control）降低它被碰到的機會或被利用後的影響：關閉受影響的功能、縮小能連到它的來源（只允許內網或 VPN）、在 WAF 加一條針對它的規則、降低服務的權限或移到獨立網段、加強相關的監控。

補償控制是暫時的，每一項都要記錄對應哪個弱點、負責人、到期日與移除條件。決定「暫時不修」是**風險接受**，要由有權責的人核准、有期限、到期重新評估；沒有到期日的例外會變成永久的。

## 邊界防護

### WAF

**WAF**（Web Application Firewall）放在網站前面，檢查每個 HTTP 請求，依規則決定放行、阻擋或記錄。常見的形式有 CDN 或雲端業者提供的 WAF 服務，以及自架的 ModSecurity 搭配 OWASP CRS 規則集。

| WAF 幫得上忙的 | WAF 幫不上忙的 |
|---|---|
| 符合已知樣式的惡意請求 | 授權邏輯的錯誤：請求本身完全合法，只是不該由這個人送出（見 [RBAC 與 ABAC 授權模型](#/skill/rbac-abac)） |
| 針對特定路徑或參數快速加一條規則 | 不經過 WAF 的流量：直接連到後端主機的、內網之間的、非 HTTP 的 |
| 速率限制、阻擋已知的惡意來源 | 規則沒有涵蓋到的請求：規則是依已知樣式寫的 |
| 留下請求紀錄供事後調查 | 已經在系統裡面的問題：有弱點的依賴、外洩的憑證 |

**虛擬修補**（virtual patching）是指程式還沒修好之前，先在 WAF 上擋掉針對那個弱點的請求。它爭取到的是時間，弱點還在：規則只涵蓋已知的樣式，也只保護經過 WAF 的那條路。所以加了規則之後工單不能關，仍然依原本的期限修補。

使用上：新規則先用只記錄不阻擋的模式觀察誤判，再切成阻擋；後端主機只接受來自 WAF 的連線；WAF 規則的異動也要走變更流程。

### 網路分段與最小開放

網路分段把系統分成幾個區，區與區之間預設不通，只開必要的連線：

```text
網際網路
   │  只開 443
[ WAF／負載平衡 ]     對外區
   │  只開應用程式的 port
[ 應用程式 ]          應用區 ──（出站只到允許清單上的目的地）──▶ proxy ──▶ 外部服務
   │  只開 5432，來源限應用區
[ 資料庫 ]            資料區

[ SSH、管理介面 ]     管理區：只能從跳板機或 VPN 進入
```

分段的目的是限制「一台主機出問題後，還能連到哪裡」：對外的 web 主機若能直接連到所有資料庫與管理介面，損害範圍就是整個內網。原則是**預設拒絕、逐條開放**，每條規則有用途、負責人與期限；申請規則要給哪些資訊、連不通時怎麼判斷是哪一段擋住，見 [網路通不通：從 DNS 到防火牆](#/skill/network-troubleshooting)。

Kubernetes 叢集裡，Pod 之間預設全部互通，要靠 NetworkPolicy 才能限制，而且叢集的網路外掛要支援它。

### 出站限制

多數防火牆規則管的是「誰能連進來」，「伺服器能連出去到哪裡」常常是全開的。把出站改成預設拒絕、需要的目的地列進允許清單（通常經由 proxy），服務出問題時較難把資料送到外部，SSRF 這類問題的影響範圍也變小（見 [OWASP Top 10 地圖](#/skill/owasp-top10) 的 A10），還順便得到一份「每個服務依賴哪些外部服務」的清單。代價是新增外部依賴要申請，流程要夠快。

### 零信任

零信任（zero trust）的核心想法是：不因為連線來自內網就信任它。每個請求都要確認身分（使用者、裝置或服務）、依最小權限授權、加密傳輸，並假設網路上任何一段都可能已經有不該在的人。它是一組設計原則，不是一個產品；網路分段仍然需要，只是不再是唯一的防線。服務之間怎麼互相驗證，見 [API key、服務間驗證、MFA 與 SSO](#/skill/api-keys-mfa)。

## 滲透測試、日誌集中與 SIEM

弱點掃描和滲透測試常被混為一談，兩者回答的問題不同：

| | 弱點掃描 | 滲透測試 |
|---|---|---|
| 怎麼做 | 工具自動比對已知弱點與設定 | 專業人員在約定範圍內實際檢驗，判斷多個問題組合後能造成什麼影響 |
| 擅長 | 已知、有特徵的問題；範圍廣 | 業務邏輯、授權、多個小問題串起來的路徑；範圍窄但深 |
| 產出 | 弱點清單 | 報告：實際影響、重現條件、修補建議 |
| 前提 | 清冊完整 | 書面授權、範圍、時段、聯絡窗口 |

兩者互補：掃描是持續做的，滲透測試是定期、重大改版前或依規範要求做的。滲透測試的發現同樣進弱點追蹤流程，有等級、負責人與期限。

**SIEM**（Security Information and Event Management）的定位是把各處的日誌集中起來：登入紀錄、WAF、防火牆、主機、雲端平台的稽核紀錄，轉成一致的格式，做跨來源的關聯與告警，並保存供調查。前提是日誌已經集中、各主機時間同步、內容不含不該出現的個資（見 [日誌與稽核紀錄裡的個資](#/skill/logs-pii)）。告警之後由誰處理、怎麼分級與通報，見 [事故處理、on-call 與 postmortem](#/skill/incident-response)。規則寧可少而準，每一條告警都要有對應的處理步驟。

## 實際程式：排修補優先序

下面用一份虛構的清冊與掃描結果，比較「只看 CVSS」與「依規則計分」兩種排法。計分規則與期限都是示意，可以直接執行：

```python run
from datetime import date, timedelta

TODAY = date(2026, 3, 16)

# 資產清冊（示意）：對外與否、重要性記在資產上，不是記在弱點上
ASSETS = {
    "portal-web":   {"exposure": "internet", "criticality": "high"},     # 對外掛號入口
    "vpn-gateway":  {"exposure": "internet", "criticality": "high"},
    "his-db":       {"exposure": "internal", "criticality": "high"},     # 病歷資料庫
    "report-batch": {"exposure": "internal", "criticality": "normal"},
    "wiki":         {"exposure": "internal", "criticality": "normal"},
}

# 掃描結果（虛構）：cvss 是技術嚴重度；known_exploited 是「有沒有已知被實際利用」
FINDINGS = [
    {"id": "F-101", "asset": "report-batch", "cvss": 9.8, "known_exploited": False, "found": date(2026, 3, 2)},
    {"id": "F-102", "asset": "portal-web",   "cvss": 7.5, "known_exploited": True,  "found": date(2026, 3, 10)},
    {"id": "F-103", "asset": "his-db",       "cvss": 9.0, "known_exploited": False, "found": date(2026, 3, 5)},
    {"id": "F-104", "asset": "portal-web",   "cvss": 5.3, "known_exploited": False, "found": date(2026, 1, 5)},
    {"id": "F-105", "asset": "wiki",         "cvss": 9.1, "known_exploited": True,  "found": date(2026, 3, 14)},
    {"id": "F-106", "asset": "vpn-gateway",  "cvss": 9.8, "known_exploited": False, "found": date(2026, 3, 14)},
    {"id": "F-107", "asset": "wiki",         "cvss": 4.3, "known_exploited": False, "found": date(2026, 2, 1)},
]

SLA_DAYS = {"P1": 3, "P2": 14, "P3": 30, "P4": 90}      # 示意；實際期限依組織政策


def severity_points(cvss):
    # CVSS 的定性等級：9.0 以上 Critical、7.0 以上 High、4.0 以上 Medium
    return 3 if cvss >= 9.0 else 2 if cvss >= 7.0 else 1 if cvss >= 4.0 else 0


def assess(finding):
    asset = ASSETS[finding["asset"]]
    points = severity_points(finding["cvss"])
    points += 2 if finding["known_exploited"] else 0          # 已知被利用：加最多
    points += 1 if asset["exposure"] == "internet" else 0     # 對外
    points += 1 if asset["criticality"] == "high" else 0      # 重要資產
    priority = "P1" if points >= 5 else "P2" if points == 4 else "P3" if points >= 2 else "P4"
    due = finding["found"] + timedelta(days=SLA_DAYS[priority])
    return {**finding, "points": points, "priority": priority, "due": due, "overdue": TODAY > due}


by_cvss = sorted(FINDINGS, key=lambda f: (-f["cvss"], f["id"]))
by_rule = sorted((assess(f) for f in FINDINGS), key=lambda f: (f["priority"], f["due"], f["id"]))
cvss_rank = {f["id"]: i + 1 for i, f in enumerate(by_cvss)}

print("只看 CVSS：", " > ".join(f"{f['id']}({f['cvss']})" for f in by_cvss))
print()
print(f"{'名次':<4}{'編號':<7}{'資產':<14}{'CVSS':<6}{'分數':<4}{'等級':<5}{'期限':<12}{'CVSS 名次':<9}備註")
for rank, f in enumerate(by_rule, 1):
    notes = []
    if f["overdue"]:
        notes.append(f"逾期 {(TODAY - f['due']).days} 天")
    if f["known_exploited"]:
        notes.append("已知被利用")
    print(f"{rank:<6}{f['id']:<9}{f['asset']:<16}{f['cvss']:<6}{f['points']:<6}{f['priority']:<7}"
          f"{f['due'].isoformat():<14}{cvss_rank[f['id']]:<12}{'、'.join(notes)}")
```

輸出裡有兩筆最值得看：`F-102` 的 CVSS 只有 7.5，只看分數時排第五，但它在對外的掛號入口上而且已知被利用，依規則是第一名並且已經逾期；`F-101` 是 9.8 分，只看分數時排第一，但它在內網的一般資產上，依規則排到 P3。兩種排法決定的是這一週的人力花在哪裡。

## 常見錯誤

| 現象 | 原因 | 處理 |
|---|---|---|
| 公告出來後要花幾天才知道受不受影響 | 沒有清冊，或清冊是人工維護、已經過期 | 清冊從平台 API、SBOM、DNS 自動產生；定期用對外盤點核對 |
| 掃描報告有幾千筆，沒有人處理 | 沒有排序規則、沒有負責人、同一個問題重複出現 | 結果進追蹤系統、去除重複、依規則分級、派給資產負責人 |
| 高分的弱點修了很多，對外正被利用的那個還在 | 只依 CVSS 排序 | 把已知被利用、對外、資產重要性納入規則 |
| 掃描器一直回報沒有弱點 | 弱點資料庫沒更新，或掃描範圍漏了一整個網段 | 監控資料庫的更新日期；掃描範圍和清冊比對 |
| repo 已經升版，掃描仍然報同一個弱點 | 映像沒重建、服務沒重新部署，或程序還載入舊的函式庫 | 重建並部署；重啟；以重新掃描的結果結案 |
| WAF 加了規則，工單就關了 | 把虛擬修補當成修好 | 工單維持開啟到程式修補並驗證；規則有到期日 |
| 例外清單越來越長 | 風險接受沒有到期日與負責人 | 每筆例外有核准人、期限、到期重評 |

## 動手

1. 執行排序那一段，把 `F-101` 的資產改成 `portal-web`，觀察它的等級與期限怎麼變；再把 `F-102` 的 `known_exploited` 改成 `False`，看它掉到第幾名。
2. 調整 `SLA_DAYS` 或加分的權重，看哪些弱點的等級會跨級。規則的每個數字都是政策決定，改之前先想清楚要怎麼向稽核說明。
3. 程式題：[依規則排修補優先序](#/exercise/security-operations-1)，加上到期日、逾期、清冊裡查不到的資產，以及需要補償控制的判斷。
4. 拿一個自己負責的服務，試著在十分鐘內回答：它跑的映像是哪一個 digest、裡面有哪些元件、對外開了哪些 port、負責人是誰。答不出來的那一項，就是清冊要補的地方。
