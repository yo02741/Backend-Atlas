> 本課以 2026 年 11 月的一般狀況為準。可自行部署的模型、推論軟體與硬體變動很快；這裡只講判斷方式與估算方法，所有數字都是示意，不代表任何特定模型或硬體的規格。

## 從一個具體問題開始：病歷摘要不能送到院外

一家虛構的醫院已經用雲端的模型 API 做了門診衛教問答：民眾問「抽血前要空腹多久」，系統依院內的衛教文件回答。問題與答案都不含可識別病人的資料，上線半年運作正常。

接下來要做第二個功能：醫師開出院病摘之前，系統先依這次住院的病歷紀錄產生一份摘要草稿。送審時法遵的回覆是：可識別病人的病歷內容，依主管機關規範與院方的契約，目前不能送到院外的服務。

團隊的第一個反應是「那就買一台 GPU 伺服器，把模型裝在院內」。接著問題一個一個出現：

- 要買多大的機器？一台能同時服務幾位醫師？
- 模型從哪裡來？可以商用嗎？下載回來的檔案怎麼確定沒被動過？
- 院內跑得動的模型，摘要品質和原本用的雲端模型差多少？
- 機器壞了怎麼辦？誰負責升級？
- 模型放在院內，資料就真的沒有出去嗎？

哪些資料能去哪裡，由法遵依主管機關規範與契約確認；工程這一側要做的，是讓每個選項的後果算得出來。

## 選項地圖

「雲端 API」和「地端自架」不是僅有的兩個選項：

| 選項 | 資料到哪裡 | 誰維運模型 | 成本形式 | 常見限制 |
|---|---|---|---|---|
| 雲端 API | 供應商的環境 | 供應商 | 按用量 | 資料離開機構；受供應商的速率限制與版本更替影響 |
| 雲端的專屬或區域部署 | 供應商的環境，但可指定區域或專屬容量 | 供應商 | 按用量或按保留的容量 | 資料仍在業者那裡；算不算「沒有出去」由法遵依契約判斷 |
| 地端自架 | 自己的機房 | 自己 | 一次性硬體 + 電力 + 人力 | 能用的模型大小受硬體限制；容量固定；全部自己維護 |
| 混合：依資料敏感度分流 | 敏感的留院內，其餘送雲端 | 兩邊都有 | 兩邊都付 | 兩條路徑都要維護；分流規則錯了就是資料外洩 |

選擇的順序是：**先分資料，再選位置**。先把每個功能會送進模型的資料分級（做法見 [地端、雲端與混合](#/skill/hosting-models) 的資料落地段落），不能出去的那一級只剩地端一個選項，其餘的才比較成本與能力。開頭的醫院就是混合：衛教問答繼續用雲端，病歷摘要在院內。

## 地端要自己處理的事

用雲端 API 時，下面每一項都是供應商的工作。搬到地端之後，全部變成自己的。

### 推論服務

模型本身是一組權重檔。要讓應用程式能呼叫它，需要一個**推論伺服器**：把權重載入 GPU 記憶體，對外提供 HTTP 介面，處理排隊、把多個請求併成一批計算、串流輸出。開源實作例如 vLLM、Ollama、llama.cpp，定位與適合的規模各不相同，這裡不比較。

多數推論伺服器提供和主流雲端 API 相容的介面，應用程式原則上換一個端點就能用。但相容的程度不一：結構化輸出、工具呼叫、串流時的用量回報都要逐項實測。[後端怎麼呼叫模型](#/skill/llm-api-integration) 裡的逾時、重試、驗證在地端一樣需要。

推論伺服器前面仍然放 [AI Gateway](#/skill/ai-gateway)：應用程式只認別名，由 gateway 決定送到地端還是雲端，金鑰、配額與紀錄也集中在那裡。

### GPU 記憶體怎麼估

模型要整個載入 GPU 記憶體才跑得快。記憶體分三塊：

| 項目 | 怎麼估 | 備註 |
|---|---|---|
| 權重 | 參數量 × 每個參數的位元數 ÷ 8 | 主要項。80 億參數、每參數 16 位元，約 16 GB |
| 每個併發請求的 context | 併發數 × context 長度 × 每 token 的佔用 | 推論時要保留每個 token 的中間狀態；每 token 佔多少依模型結構而定，要實測 |
| 固定開銷 | 推論伺服器與框架本身 | 另外留一成左右的餘裕，不要估到剛好 |

第二項容易被忽略：模型載得進去，不代表能同時服務很多人。

### 量化的取捨

**量化**是用比較少的位元表示每個參數，例如從 16 位元降到 8 或 4 位元。權重佔的記憶體大致等比例縮小（實際的量化格式有額外的資訊要存，會比純算術略大）。

- **好處**：同一張 GPU 放得下更大的模型，或留更多空間給併發。
- **代價**：品質可能下降。下降多少和模型、量化方法、位元數、任務都有關，沒有一個通用的數字。

所以量化後的模型要當成另一個模型：用自己的評測集，量化前後各跑一次比對，做法見 [Harness Engineering](#/skill/harness-engineering)。

### 併發與排隊

雲端 API 忙不過來時回 429。地端沒有 429，請求會在自己的推論伺服器前面排隊。

一張 GPU 的吞吐量有上限，可以用「所有請求合計每秒產生多少 token」來量。多個請求併成一批算時，合計的吞吐量上升，每個請求各自的速度下降。進來的比做完的快，佇列就變長：

- **容量依尖峰估，不依平均**。醫師集中在查房後寫病摘，那一小時的量可能是平均的數倍。估算方法（尖峰、Little's Law、留 headroom、N+1）見 [容量規劃](#/skill/capacity-planning)。
- **佇列要有長度上限與等待逾時**。無限長的佇列只會讓每個人都等到逾時。超過上限時明確回錯誤，讓呼叫端降級。
- **數字要自己壓測**。用接近真實的 prompt 長度與輸出長度分布去壓，看幾個併發時延遲開始惡化。做法見 [壓力測試](#/skill/load-testing)。
- **壞一台要還撐得住**。只有一張 GPU 時，它故障就是整個功能停擺，而且修復可能以天計。

### 模型與權重的來源

權重檔是幾 GB 到幾十 GB 的二進位檔案，通常從公開的模型倉庫下載，和程式套件一樣是供應鏈的一環：

- **來源**：是原始發布者，還是第三方轉檔、量化後重新上傳的版本？後者要當成不同的東西看待。
- **授權條款**：每個模型的條款不同，能否商用、有沒有使用範圍限制、微調後的模型怎麼算，都要由法務看過。可以下載不等於可以用在產品上。
- **雜湊驗證與鎖版本**：記下每個檔案的雜湊，部署時比對；用版本或提交編號指定，不要用「最新版」。
- **檔案格式**：有些權重檔格式在載入時可以執行任意程式碼。優先選只存數值資料的格式，來源不明的檔案不要在正式環境載入。
- **內部鏡像**：權重放進內部的儲存，正式環境只從內部拉。受限網路環境的搬運流程和容器映像相同。

治理方式（內部登錄、審查、變更重審）見 [行為層的供應鏈管理](#/skill/agent-supply-chain)。

### 更新、回滾與監控

- **換模型就是換行為**。新版本、不同的量化、推論伺服器升級，都可能改變輸出。上線前先跑評測集，保留上一版的權重與設定，壞了能切回去；流程見 [把 agent 當軟體交付](#/skill/agent-delivery)。
- **要更新的不只模型**：GPU 驅動、推論伺服器、作業系統都有安全修補，受限網路裡要有管道把更新帶進來。
- **監控**：GPU 記憶體與使用率、佇列長度與等待時間、第一個 token 的時間、每秒產生的 token 數、錯誤率。應用層的欄位見 [LLM 應用的可觀測性](#/skill/llm-observability)。

## 能力落差：用自己的任務評測

在自己的硬體上跑得動的模型，通常比雲端供應商最大的模型小。落差有多少，依任務而定：

- 分類、欄位抽取、格式轉換、有明確依據的摘要，較小的模型可能已經夠用。
- 很長的文件、多步驟的推理、複雜的工具呼叫，落差可能比較明顯。

公開的排行榜量的不是你的任務，也多半不是繁體中文的病歷用語。可靠的做法是自己量：

1. 從真實的工作裡取一批案例做成評測集（病歷摘要就請醫師標出每份摘要必須包含與不得出現的內容）。
2. 候選的模型與量化版本都用同一份評測集跑，逐案例比對，不只看總分。
3. 訂出可接受的門檻。達不到時，選項是縮小功能範圍（只摘要檢驗結果、不摘要病程）、加上人工確認，或不做。

評測集本身含有病歷時，評測也要在院內跑，不能為了比較而把它送到雲端模型。

## 成本結構：固定與變動

| | 雲端 API | 地端自架 |
|---|---|---|
| 一次性 | 幾乎沒有 | GPU 伺服器、機櫃、網路 |
| 每月固定 | 少（gateway、整合） | 硬體折舊、電力與冷卻、維護合約、維運人力 |
| 隨用量變動 | 按 token 計費 | 電力隨負載略增，其餘幾乎不變 |
| 閒置時 | 不用就不付 | 照付 |
| 尖峰時 | 受速率限制，付得起就有 | 容量固定，超過就排隊 |

比較方式是把地端的每月固定成本攤到請求上。假設（示意、無單位）地端每月固定成本是 300，雲端每千次請求 20，地端每千次的變動成本是 2，兩邊打平的用量是 300 ÷ (20 − 2) ≈ 每月 1.7 萬次。低於這個量，地端的機器大半時間閒置，每次請求比雲端貴；高於這個量且用量穩定，固定成本被攤薄。

常漏掉的項目：維運人力、備援用的那一台、依尖峰採購造成的離峰閒置、每次升級與重新評測的時間。成本模型見 [FinOps](#/skill/finops) 與 [地端、雲端與混合](#/skill/hosting-models)。資料依規定不能出去時，成本比較決定的是「值不值得做這個功能」，不是放哪裡。

## 「資料不出去」不只是模型放在哪裡

模型在院內，不等於資料沒有離開。逐項檢查：

| 路徑 | 要確認什麼 |
|---|---|
| 日誌 | prompt 與回應全文寫到哪裡？日誌平台是院內的嗎？規則見 [日誌與稽核紀錄裡的個資](#/skill/logs-pii) |
| 遙測 | 推論伺服器、框架、相依的函式庫有沒有預設回報使用統計或錯誤報告？查設定並關閉 |
| 更新管道 | 啟動時會不會連外檢查新版或下載模型？正式環境應該完全離線也能啟動 |
| gateway 的備援 | 地端滿載或故障時，會不會自動改送雲端？敏感請求的路由不能有雲端備援 |
| 開發與除錯 | 有沒有人把真實病歷貼到雲端的工具裡測 prompt？ |
| 備份與評測資料 | 評測集、對話紀錄的備份放在哪裡？ |

最可靠的一層在網路：推論主機的出站連線預設全部拒絕，只開放明確需要的內部位址。設定漏掉的地方，由網路擋下。

## 混合：依資料敏感度分流

分流的規則放在 gateway，原則有四條：

- **分級來自資料的來源，不是內容的猜測**。「這個請求來自病歷摘要功能」是可靠的標籤；用樣式比對猜內容裡有沒有個資，只能當第二道。
- **預設是敏感**。沒有標籤、標籤不認得的請求，一律當成敏感處理。
- **敏感請求絕不外送**。地端滿載時排隊，佇列也滿了就回錯誤，讓功能降級。這時候「為了可用性先送雲端」就是事故。
- **一般請求可以用地端的空位，但不佔敏感請求的佇列**。

本課的程式題就是實作這個路由函式。三種做法在同一天流量下的排隊、成本與故障時的行為，可以在 [模型放雲端、地端還是分流](#/scenario/model-hosting-choice) 的模擬器裡比較。

## 實際程式：GPU 記憶體與併發的粗估

下面的數字全部是示意。使用時換成候選模型的參數量、自己壓測得到的吞吐量與自己的尖峰流量。

```python run
import math

# ── 全部是示意數字：換成自己候選模型的參數量、實測的吞吐量與自己的流量 ──
PARAMS_B       = 8      # 模型參數量（十億）
CTX_TOKENS     = 6000   # 每個請求的 context 長度上限（輸入 + 輸出）
KV_MB_PER_1K   = 100    # 每 1,000 token 的 context 佔多少 MB（依模型結構而定，要實測）
OVERHEAD_GB    = 2.0    # 推論伺服器與框架本身
GPU_GB         = 24     # 一張 GPU 的記憶體
USABLE         = 0.9    # 只用到 90%，留餘裕

TOKENS_PER_SEC = 300    # 一張 GPU 在批次處理下「所有請求合計」每秒產生的 token（壓測得到）
OUT_TOKENS     = 600    # 每個請求平均輸出多少 token
PEAK_PER_MIN   = 40     # 尖峰每分鐘進來幾個請求
TARGET_UTIL    = 0.7    # 尖峰時只用到 70%

PER_REQ_GB = CTX_TOKENS / 1000 * KV_MB_PER_1K / 1024     # 一個併發請求的 context 佔多少 GB

print("一、記憶體 = 權重 + 併發 × 每個請求的 context + 固定開銷")
for bits in (16, 8, 4):                                   # 16：未量化的常見精度；8、4：量化
    weights = PARAMS_B * bits / 8                         # 十億參數 × 位元組數 = GB
    total = weights + 8 * PER_REQ_GB + OVERHEAD_GB        # 假設同時 8 個請求
    room = GPU_GB * USABLE - weights - OVERHEAD_GB        # 扣掉權重與開銷，剩多少給 context
    max_conc = max(0, math.floor(room / PER_REQ_GB))
    verdict = "放得下" if total <= GPU_GB * USABLE else "放不下"
    print(f"  {bits:>2} bit：權重 {weights:4.1f} GB + context {8 * PER_REQ_GB:.1f} GB + 開銷 {OVERHEAD_GB:.1f} GB"
          f" = {total:4.1f} GB → 併發 8 {verdict}（這張卡最多同時 {max_conc} 個）")

print("\n二、吞吐量：一張 GPU 每分鐘能完成幾個請求")
per_gpu = TOKENS_PER_SEC / OUT_TOKENS * 60
print(f"  {TOKENS_PER_SEC} token/s ÷ 每個請求 {OUT_TOKENS} token × 60 = {per_gpu:.0f} 個/分")
need = math.ceil(PEAK_PER_MIN / (per_gpu * TARGET_UTIL))
print(f"  尖峰 {PEAK_PER_MIN} 個/分、目標使用率 {TARGET_UTIL:.0%} → 需要 {need} 張；壞一張還要撐得住，所以是 {need + 1} 張")

print("\n三、少一張會怎樣：尖峰持續 30 分鐘")
for gpus in (need + 1, need, need - 1):
    cap = gpus * per_gpu
    if cap == 0:
        print(f"  {gpus} 張：沒有容量，全部請求失敗")
        continue
    backlog = max(0, (PEAK_PER_MIN - cap) * 30)           # 進來的比做完的多，差額累積成佇列
    wait = backlog / cap                                  # 尖峰結束時，佇列最後一個還要等幾分鐘
    print(f"  {gpus} 張：容量 {cap:.0f} 個/分，使用率 {PEAK_PER_MIN / cap:.0%}，"
          f"30 分鐘後佇列 {backlog:.0f} 個，最後一個約等 {wait:.1f} 分")
```

未量化時權重就佔了 16 GB，這張卡只能同時處理 6 個請求；量化到 4 位元可以同時 26 個，但品質要另外評測。第二段的張數依尖峰與目標使用率算，不依平均。第三段：只剩一張時使用率超過 100%，佇列每分鐘增加 10 個，半小時後最後一位醫師要等 10 分鐘。

## 常見錯誤

| 錯誤做法 | 會發生什麼 | 修正 |
|---|---|---|
| 只看權重大小就決定買哪張 GPU | 模型載得進去，三個人同時用就記憶體不足 | 把併發與 context 長度算進去，留餘裕 |
| 依平均流量估容量 | 尖峰時佇列暴增，每個請求都逾時 | 依尖峰估，並壓測找出飽和點 |
| 只有一張 GPU、沒有備援 | 故障時功能停擺，而且不能外送 | 至少 N+1；事先決定停擺時的人工流程 |
| 看排行榜選模型 | 上線後在自己的任務上表現不如預期 | 用自己的評測集並排比較 |
| 量化後沒有重新評測 | 品質下降沒人發現 | 量化版本當成新模型，重跑評測集 |
| 權重直接從公開倉庫拉最新版 | 內容變了不知道；來源被替換時直接中招 | 內部鏡像、鎖版本、比對雜湊 |
| 沒看授權條款就上線 | 事後發現不能商用或有使用限制 | 上架前由法務確認，紀錄在內部登錄裡 |
| gateway 的 fallback 沒有區分資料分級 | 地端滿載時病歷被送到雲端 | 敏感路由不設雲端備援；滿載時排隊或回錯誤 |
| 模型在院內，日誌送到雲端的日誌平台 | prompt 全文一樣離開了院內 | 逐項檢查日誌、遙測、更新管道；出站預設拒絕 |

2. 在 [Playground](#/playground?lang=python) 把 `PEAK_PER_MIN` 改成 90，看需要的張數；再把 `OUT_TOKENS` 減半（要求摘要更短），比較張數的變化。輸出長度是地端容量最直接的槓桿之一。
3. 做本課的程式題：實作依資料敏感度分流的路由函式。接著到 [模型放雲端、地端還是分流](#/scenario/model-hosting-choice) 調整敏感請求的比例與 GPU 台數，按「跑一天」，再注入一台 GPU 故障，看三種做法怎麼退化。
