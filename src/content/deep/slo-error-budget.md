## 從一個具體問題開始：「系統要 24 小時不能斷」

一家醫院的線上掛號系統上線前，需求單上寫著「系統必須 24 小時穩定運作」。這句話沒辦法驗收，也沒辦法拿來做決定：

- 上個月有兩次各 15 分鐘的錯誤高峰，算不算「不穩定」？
- 星期四晚上要上一個新功能，現在可以上嗎，還是要先修效能問題？
- 半夜 3 點有 5 個請求失敗，要不要把 on-call 的人叫醒？
- 要不要多花一筆預算做異地備援？

每個人心中的「穩定」都不一樣，所以每次都要重新爭論。SLO 的作用是把「穩定」變成一個**可以量、可以算、事先講好**的數字，接著用**錯誤預算**把它轉換成決策規則：預算還夠就照常上線，燒太快就叫人，燒完就先修穩定性。

## SLI、SLO、SLA：三個詞的差別

| | 是什麼 | 例子 | 誰在意 |
|---|---|---|---|
| **SLI**（Service Level Indicator，服務水準指標） | 量測值，通常是「好的事件 ÷ 有效事件」 | 過去 30 天，掛號 API 回應非 5xx 且在 1 秒內的請求比例 = 99.93% | 工程團隊 |
| **SLO**（Service Level Objective，服務水準目標） | SLI 的目標值與時間視窗 | 30 天滾動視窗內，上面的比例 ≥ 99.9% | 工程與業務一起訂 |
| **SLA**（Service Level Agreement，服務水準協議） | 對外的承諾，違反時有後果（賠償、罰款、退費） | 契約寫明月可用率低於某個值時，廠商要退部分費用 | 法務、採購、客戶 |

幾個要點：

- **SLA 通常比 SLO 寬**。內部目標要比對外承諾嚴，才有時間在違約之前發現並處理。很多內部系統根本沒有 SLA，但仍然應該有 SLO。
- **SLI 是比例，不是原始數字**。「錯誤數 = 30」沒有意義，要知道分母：30 / 100 和 30 / 1,000,000 是完全不同的狀況。
- **SLO 一定有時間視窗**。常見是 28 或 30 天的**滾動視窗**（rolling window）；也有用日曆月的，方便和報表對齊，但月初會「重置」，月底燒完的預算下個月一號又滿了。

### 怎麼定義 SLI

公式永遠是同一個：

```text
SLI = 好的事件數 / 有效事件數
```

難的是定義「好」與「有效」：

| 類型 | 好的事件 | 有效事件 | 注意 |
|---|---|---|---|
| 可用性 | 回應不是 5xx | 所有外部請求 | 健康檢查、內部探測不算；4xx 通常算「好」（是使用者的錯），但 429 限流要想清楚 |
| 延遲 | 回應時間 < 1 秒 | 所有成功的請求 | 用「比例」而不是平均值：平均 200 ms 可能藏著 5% 的請求超過 5 秒 |
| 資料新鮮度 | 每日批次在 06:00 前完成 | 每一天 | 適合數據中台、報表、資料同步 |
| 正確性 | 抽查結果與來源一致 | 所有抽查 | 適合資料管線，通常要另外寫檢查程式 |

**在哪裡量**也很重要。在應用程式裡量，看不到負載平衡器或網路層的失敗；在負載平衡器的存取日誌量，比較接近使用者看到的結果；從外部用合成探測（synthetic probe）定期打一次，可以量到「整條路徑都通」，但樣本數少。實務上常以負載平衡器或閘道的指標為主，合成探測為輔。

## 可用性目標換算成停機時間

可用性目標每多一個 9，允許的不可用時間就少十倍。以 30 天（43,200 分鐘）計算：

| SLO | 允許不可用的比例 | 每 30 天 | 每 365 天 |
|---|---|---|---|
| 99% | 1% | 432 分鐘（7.2 小時） | 87.6 小時（約 3.65 天） |
| 99.5% | 0.5% | 216 分鐘（3.6 小時） | 43.8 小時 |
| 99.9% | 0.1% | 43.2 分鐘 | 8.76 小時 |
| 99.95% | 0.05% | 21.6 分鐘 | 4.38 小時 |
| 99.99% | 0.01% | 約 4.3 分鐘 | 約 52.6 分鐘 |

這張表是以「時間」計算的。以「請求」計算時，意思是允許的失敗請求比例：一個月 200 萬個請求、SLO 99.9%，就允許 2,000 個失敗請求。兩種算法在流量平均時差不多；但半夜流量低時停機 30 分鐘，以請求計算的影響比以時間計算小。

選目標時要記得：

- **不要訂 100%**。沒有任何系統做得到，而且一個依賴外部網路、資料庫、身分驗證服務的系統，可用性不可能高於它所有關鍵依賴的乘積。
- **多一個 9，成本與限制往上跳**。99.99% 每月只剩 4 分多鐘，人工處理幾乎來不及，需要自動切換、多區部署，還要求每次部署都不能出錯。
- **從歷史資料開始**。先量過去幾個月的實際 SLI，把 SLO 訂在「略低於目前水準、使用者不會抱怨」的位置，之後再依實際狀況調整。

## 錯誤預算與燃燒率

### 錯誤預算

**錯誤預算**（error budget）= 1 − SLO。SLO 99.9% 的錯誤預算就是 0.1%：在 30 天的視窗裡，允許 0.1% 的事件是壞的。它把「可靠性」和「變更速度」放在同一個帳本上：

- 部署新版本、做資料庫遷移、更新基礎設施，都有機率造成錯誤，也就是在**花預算**。
- 預算還很多：可以照常部署，甚至可以嘗試風險較高的變更或做故障演練。
- 預算快用完：放慢變更，優先處理穩定性。

### 燃燒率

**燃燒率**（burn rate）是預算消耗的速度，相對於「剛好在視窗結束時用完」的速度：

```text
燃燒率 = 觀察到的錯誤率 / (1 − SLO)
```

- 燃燒率 1：照這個速度，30 天剛好用完預算。
- 燃燒率 2：15 天用完。
- 燃燒率 N：30 / N 天用完。

在長度 `w` 的時間裡，以燃燒率 `b` 消耗掉的預算比例是 `b × w / 30 天`。反過來，如果想在「1 小時內燒掉 2% 預算」時告警，門檻是 `0.02 × 720 小時 / 1 小時 = 14.4`；SLO 99.9% 時，這相當於錯誤率 1.44%。用這個公式，任何「多少時間燒掉多少預算要通知」的規則都可以換算成燃燒率門檻。

### 多視窗的燃燒率告警

直接對錯誤率設門檻（例如「錯誤率 > 1% 就告警」）有兩個問題：短暫的尖峰會誤報；長時間的小幅錯誤永遠不會觸發，卻默默燒光預算。燃燒率告警的思路是：**依「預算消耗多快」決定緊急程度**。

| 層級 | 條件（示意） | 處理 |
|---|---|---|
| 快速燃燒 | 短時間內燒掉明顯比例的預算 | 呼叫 on-call（page），立刻處理 |
| 緩慢燃燒 | 較長時間持續燒，照這個速度幾天內會用完 | 開工單，上班時間處理 |

每個條件通常搭配**一長一短兩個視窗**，兩個都超過門檻才告警：

- **長視窗**（例如 1 小時）：確定不是幾秒鐘的雜訊，消耗量真的值得在意。
- **短視窗**（例如 5 分鐘）：確定問題**現在還在發生**。只看長視窗時，問題修好後告警還會持續響到長視窗滑過去為止。

門檻與視窗長度要依自己的 SLO、流量與團隊能接受的回應時間來定，上線後再依誤報與漏報調整。Google 的 SRE Workbook 有一章 [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) 詳細比較了幾種告警策略的取捨，可以當作設計時的參考。

## 實際程式：換算表與燃燒率模擬

下面這段 Python 先算出停機時間換算表，再模擬一段流量：平常錯誤率 0.05%，中間有 40 分鐘錯誤率升到 3%。每 5 分鐘檢查一次燃燒率，觀察「長視窗 + 短視窗」的告警何時觸發、何時解除：

```python run
# 1. 可用性目標換算成每 30 天允許的不可用時間
MIN_PER_30D = 30 * 24 * 60
for slo in [0.99, 0.995, 0.999, 0.9995, 0.9999]:
    print(f"SLO {slo * 100:g}%：每 30 天 {MIN_PER_30D * (1 - slo):7.2f} 分鐘")

# 2. 模擬 4 小時的流量：每分鐘 1,000 個請求
SLO = 0.999
BUDGET = 1 - SLO
minutes = 240
total = [1000] * minutes
bad = [1 if m % 2 else 0 for m in range(minutes)]      # 平常約 0.05% 錯誤
for m in range(90, 130):                                # 第 90～129 分鐘：錯誤率 3%
    bad[m] = 30

def burn_rate(end, window):
    start = max(0, end - window)
    b, t = sum(bad[start:end]), sum(total[start:end])
    return (b / t) / BUDGET

# 快速燃燒告警：1 小時與 5 分鐘兩個視窗的燃燒率都 > 14.4 才發出
THRESHOLD = 14.4
firing = False
for now in range(5, minutes + 1, 5):
    long_br, short_br = burn_rate(now, 60), burn_rate(now, 5)
    should = long_br > THRESHOLD and short_br > THRESHOLD
    if should != firing:
        state = "觸發" if should else "解除"
        print(f"第 {now:3d} 分鐘 告警{state}：1h 燃燒率 {long_br:5.1f}，5m 燃燒率 {short_br:5.1f}")
        firing = should

# 只看 1 小時視窗會怎樣：問題在第 130 分鐘就結束了，告警卻還會響一陣子
still = [now for now in range(130, minutes + 1, 5) if burn_rate(now, 60) > THRESHOLD]
if still:
    print(f"只看 1h 視窗：問題結束後仍持續告警到第 {still[-1]} 分鐘")

# 這 40 分鐘燒掉多少 30 天預算（假設 30 天流量都是每分鐘 1,000）
budget_requests = MIN_PER_30D * 1000 * BUDGET
spent = sum(bad[90:130])
print(f"這次事件用掉 {spent} 個失敗請求，約占 30 天預算的 {spent / budget_requests:.1%}")
```

試著把事件期間的錯誤數 `30` 改成 `5`（錯誤率 0.5%，燃燒率 5），快速燃燒告警不會觸發，但照這個速度 6 天就會燒完預算——這正是緩慢燃燒告警要抓的情況。

在 Prometheus 裡，燃燒率通常先用 recording rule 算好，再寫告警規則。以下只是示意，**指標名稱與標籤依實際的 exporter 而定**：

```yaml
groups:
  - name: registration-api-slo
    rules:
      # 各視窗的錯誤率（5xx ÷ 全部）
      - record: job:request_error_ratio:rate1h
        expr: |
          sum(rate(http_requests_total{job="registration-api", code=~"5.."}[1h]))
          / sum(rate(http_requests_total{job="registration-api"}[1h]))
      - record: job:request_error_ratio:rate5m
        expr: |
          sum(rate(http_requests_total{job="registration-api", code=~"5.."}[5m]))
          / sum(rate(http_requests_total{job="registration-api"}[5m]))
      # 快速燃燒：兩個視窗都超過 14.4 倍（SLO 99.9% 的預算 = 0.001）
      - alert: RegistrationApiFastBurn
        expr: |
          job:request_error_ratio:rate1h > (14.4 * 0.001)
          and job:request_error_ratio:rate5m > (14.4 * 0.001)
        labels:
          severity: page
        annotations:
          summary: 掛號 API 錯誤預算快速燃燒
          runbook: 連到這個告警的 runbook
```

## 預算燒完時怎麼辦：錯誤預算政策

錯誤預算只有在「燒完時會發生什麼事」**事先講好**的情況下才有用。這份約定叫**錯誤預算政策**（error budget policy），由工程團隊與業務需求方一起簽核，常見的內容：

1. **預算用完**：暫停新功能上線，只允許修正錯誤、安全性修補與提升穩定性的變更，直到滾動視窗內的 SLI 回到目標以上。
2. **單一事件燒掉大量預算**（門檻自己定，例如四分之一）：必須寫 postmortem，行動項目排進下一個迭代。
3. **連續幾個視窗都燒完**：重新檢視 SLO 是否訂得太嚴，或系統是否需要架構層級的投資（備援、拆分、容量）。
4. **預算長期用不完**：SLO 可能太鬆，或團隊過度保守——可以加快部署頻率，或把資源轉去做功能。
5. **例外**：誰可以核准在預算用完時仍然上線（例如法規要求的變更），核准要留下紀錄。

政策的價值在於把爭論提前：事故發生後才討論「要不要停止上線」，每次都會變成部門之間的角力；事先寫好，就只是照規則執行。

## 常見錯誤

| 錯誤 | 後果 | 改法 |
|---|---|---|
| 用平均延遲當 SLI | 少數非常慢的請求被平均掉，使用者抱怨但指標正常 | 用「低於門檻的請求比例」，或看高百分位數 |
| SLI 在應用程式內量 | 負載平衡器、網路、TLS 的失敗完全看不到 | 以閘道／負載平衡器的指標為主，加合成探測 |
| 一個服務訂十幾個 SLO | 沒人記得、沒人在意 | 先挑使用者最在意的一兩條路徑（例如「掛號送出」「查詢報告」） |
| 對原因告警（CPU 80%、記憶體高） | 半夜被叫醒，但使用者根本沒受影響 | 呼叫人的告警只看症狀（SLO 燃燒）；原因類指標放儀表板或工單 |
| 低流量服務直接算比例 | 半夜 50 個請求錯 1 個就是 2%，燃燒率爆表 | 用較長的視窗、設最低請求數門檻，或用合成流量補足樣本 |
| 有 SLO 但沒有政策 | 預算燒完也沒人改變行為，SLO 變成報表數字 | 寫錯誤預算政策並由雙方簽核 |
| SLO 訂得比依賴還高 | 依賴的資料庫或外部服務一出事，目標就不可能達成 | 先列出關鍵依賴與它們的可用性，SLO 不高於它們的組合 |
