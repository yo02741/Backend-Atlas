## 從一個具體狀況開始：最後一個號

週一上午林醫師的家醫科診次名額 30，已經掛了 29 位。早上 8:00 開放掛號的瞬間，兩位病患同時按下「掛號」。API 照第 2 階段的規則寫成這樣：

```python
# 讀 → 判斷 → 寫：在並行下會出事
active = db.fetch_val(
    "SELECT count(*) FROM appointments"
    " WHERE session_id = %s AND status <> 'cancelled'", [sid])
if active >= capacity:
    raise SessionFull()
number = db.fetch_val(
    "SELECT coalesce(max(number), 0) + 1 FROM appointments"
    " WHERE session_id = %s", [sid])
db.execute(
    "INSERT INTO appointments (session_id, patient_id, number)"
    " VALUES (%s, %s, %s)", [sid, pid, number])
```

兩個請求交錯執行：

| 時間 | 請求 A（病患 101） | 請求 B（病患 102） |
|---|---|---|
| t1 | 數到 29 筆，29 < 30，通過 | |
| t2 | | 數到 29 筆，29 < 30，通過 |
| t3 | 算出號碼 30 | |
| t4 | | 算出號碼 30 |
| t5 | 插入 30 號，成功 | |
| t6 | | 插入 30 號：**唯一約束擋下**，`23505` |

第 1 階段的 `UNIQUE (session_id, number)` 在這裡救了一次：資料沒壞，但 B 收到的是一個資料庫錯誤，API 如果沒處理就變成 500。更糟的版本是號碼改用 sequence 產生：兩邊拿到不同號碼、都插入成功，診次變成 31 人——**超額掛號**，而且沒有任何約束擋得住，因為第 1 階段說過，CHECK 數不了別的列。

這一階段要做到：最後一個號只會給一個人，另一個人收到乾淨的 409 `session-full`；同時把第 1 階段留下的「取消後不能重掛」問題一起解決。交易與隔離等級的機制在 [交易與隔離等級](#/skill/transactions)，索引在 [索引](#/skill/indexes)。

## 這階段要做出什麼

1. `sessions` 加兩個欄位：`booked`（目前有效掛號數）與 `next_no`（下一個要發的號碼），並加上 `CHECK (booked <= capacity)`——有了計數欄位，「名額不能超過」終於寫得成約束。
2. 掛號改成呼叫一句原子的 SQL：名額檢查、扣名額、取號在同一個 `UPDATE` 裡完成。
3. 取消時把 `booked` 減回來；只有 `booked` 狀態能取消，取消兩次只算一次。
4. `UNIQUE (session_id, patient_id)` 換成部分唯一索引：同一病患在同一診次只能有一筆**未取消**的掛號。

## 運作原理：一句 UPDATE 怎麼擋住並行

```sql
UPDATE sessions SET booked = booked + 1, next_no = next_no + 1
WHERE id = $1 AND booked < capacity
RETURNING next_no - 1 AS number;
```

在 PostgreSQL 預設的 `READ COMMITTED` 下，兩個請求同時執行這一句：

| 時間 | 交易 A | 交易 B |
|---|---|---|
| t1 | 鎖住診次這一列，booked 29 → 30，拿到號碼 30 | |
| t2 | | 同一列被 A 鎖著，**等待** |
| t3 | 插入掛號，`COMMIT`，釋放鎖 | |
| t4 | | 拿到鎖，用**最新版本**重新檢查 `booked < capacity`：30 < 30 不成立，更新 0 列 |

B 的 `RETURNING` 是空的，應用程式就知道名額滿了，回 409。關鍵在 t4：被擋住的 `UPDATE` 拿到鎖之後，會用那一列最新提交的版本重新評估 `WHERE`，而不是用它一開始看到的舊值。這個行為和隔離等級的細節在交易那一課有完整的時間線。

`CHECK (booked <= capacity)` 是最後一道防線：哪天有人寫了一句忘了 `WHERE booked < capacity` 的 UPDATE，資料庫會直接報錯，而不是默默超額。

### 其他做法與取捨

| 做法 | 怎麼做 | 適合 | 代價 |
|---|---|---|---|
| 原子 UPDATE + 計數欄位（這裡的選擇） | 條件寫進 `WHERE` | 判斷能寫成一個條件時 | 多一個要維護一致的計數欄位 |
| `SELECT … FOR UPDATE` 鎖診次列 | 先鎖住診次，再數、再插入 | 判斷複雜、要在程式裡做時 | 交易較長，同診次的請求排隊時間較久 |
| `SERIALIZABLE` + 重試 | 照原本的讀 → 判斷 → 寫，衝突時資料庫讓一方失敗（`40001`） | 規則很多、難以一一上鎖時 | 要寫重試邏輯，衝突多時重試也多 |
| 名額放 Redis，用 `DECR` | 先在 Redis 扣，再寫資料庫 | 流量極高的搶購 | 兩個系統的一致性要自己處理（Redis 扣了、資料庫失敗怎麼辦） |

門診的流量規模（一個診次幾十個名額）用不到 Redis。所有掛號都會在同一個診次列上排隊，但每次只鎖住一句 UPDATE 加一句 INSERT 的時間，排隊很短——前提是交易裡**不要**做慢的事，例如呼叫簡訊服務。

### 計數欄位要和實際資料一致

`booked` 是從 `appointments` 推得出來的值（反正規化）。所有寫入都要經過 `book()` 與 `cancel()`，不能有人直接 `UPDATE appointments SET status = 'cancelled'`。定期跑一個對帳查詢，找出計數與實際不一致的診次，比假設它永遠一致可靠。下面的範例最後就有這個查詢。

### 每日上限在並行下呢？

「同一病患同一天最多 3 診」跨了好幾個診次，上面那句 UPDATE 只鎖住一個診次，擋不住同一位病患**同時**送出兩個不同診次的掛號（兩邊都數到 2 筆、都通過）。這種「各自讀、各自寫、合起來違規」的狀況叫 write skew。可以：

- 掛號交易一開始先鎖住病患那一列（`SELECT 1 FROM patients WHERE id = $1 FOR UPDATE`），同一病患的掛號就會排隊
- 或用 `SERIALIZABLE`，讓資料庫偵測並讓其中一方失敗重試

同一位病患同時送出多筆掛號的機率不高，但仍可能發生（重複點擊、腳本）。是否值得多鎖一列，是一個要明確做的決定；這裡建議鎖病患列，因為代價很小。

## 關鍵 SQL

建表、取號函式、取消函式，然後模擬五位病患搶名額 3 的診次。全部在瀏覽器裡的 PostgreSQL 執行（單一連線，無法真的並行，但可以看到每一步的結果）：

```sql run
-- 先清掉上一次執行（或第 1 階段範例）留下的表與函式
DROP TABLE IF EXISTS appointments, sessions, doctors, patients CASCADE;
DROP FUNCTION IF EXISTS book(bigint, bigint), cancel(bigint);

CREATE TABLE sessions (
  id BIGINT PRIMARY KEY,
  capacity INT NOT NULL CHECK (capacity > 0),
  booked INT NOT NULL DEFAULT 0 CHECK (booked >= 0),
  next_no INT NOT NULL DEFAULT 1,
  CHECK (booked <= capacity)                       -- 最後防線
);
CREATE TABLE appointments (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  session_id BIGINT NOT NULL REFERENCES sessions(id),
  patient_id BIGINT NOT NULL,
  number INT NOT NULL,
  status TEXT NOT NULL DEFAULT 'booked' CHECK (status IN ('booked', 'cancelled', 'checked_in')),
  UNIQUE (session_id, number)
);
-- 同一病患在同一診次只能有一筆「未取消」的掛號
CREATE UNIQUE INDEX one_active_per_patient
  ON appointments (session_id, patient_id) WHERE status <> 'cancelled';
INSERT INTO sessions (id, capacity) VALUES (1, 3);

CREATE FUNCTION book(p_session BIGINT, p_patient BIGINT) RETURNS INT
LANGUAGE sql AS $$
  WITH s AS (
    UPDATE sessions SET booked = booked + 1, next_no = next_no + 1
    WHERE id = p_session AND booked < capacity
    RETURNING next_no - 1 AS number
  )
  INSERT INTO appointments (session_id, patient_id, number)
  SELECT p_session, p_patient, number FROM s
  RETURNING number
$$;

CREATE FUNCTION cancel(p_id BIGINT) RETURNS BOOLEAN
LANGUAGE sql AS $$
  WITH a AS (
    UPDATE appointments SET status = 'cancelled'
    WHERE id = p_id AND status = 'booked'
    RETURNING session_id
  ), s AS (
    UPDATE sessions SET booked = booked - 1
    WHERE id IN (SELECT session_id FROM a)
    RETURNING id
  )
  SELECT EXISTS (SELECT 1 FROM s)
$$;

-- 五位病患依序搶名額 3 的診次：前三位拿到 1、2、3 號，後兩位拿到 NULL
SELECT p AS patient, book(1, p) AS number FROM generate_series(101, 105) AS p;

-- 101 取消，再取消一次（第二次回 false），然後 104 補上，拿到 4 號（號碼不回收）
SELECT cancel((SELECT id FROM appointments WHERE patient_id = 101)) AS first_cancel;
SELECT cancel((SELECT id FROM appointments WHERE patient_id = 101)) AS second_cancel;
SELECT book(1, 104) AS number_for_104;

-- 對帳：計數欄位與實際有效掛號數不一致的診次（應該沒有任何一列）
SELECT s.id, s.booked, count(a.id) AS actual
FROM sessions s
LEFT JOIN appointments a ON a.session_id = s.id AND a.status <> 'cancelled'
GROUP BY s.id, s.booked
HAVING s.booked <> count(a.id);

SELECT id, patient_id, number, status FROM appointments ORDER BY number;
```

應用程式這邊，`book()` 回 `NULL` 對應 `SessionFull`；部分唯一索引擋下的 `23505` 對應 `AlreadyBooked`。用 psycopg 3 時可以從例外的 `diag.constraint_name` 取得約束（或索引）名稱，依名稱轉換，不要只看錯誤代碼——同一個 `23505` 也可能來自號碼重複，那代表程式有 bug，應該是 500 而不是 409。

## 常見錯誤與錯誤訊息

**對聚合加 FOR UPDATE。** 想「鎖住這個診次的所有掛號再數」：

```
ERROR:  FOR UPDATE is not allowed with aggregate functions
```

`SELECT count(*) … FOR UPDATE` 不成立。要鎖的是診次那一列（`SELECT … FROM sessions WHERE id = $1 FOR UPDATE`），用它當作這個診次的「門」。

**忘了 WHERE 條件，撞上最後防線。** 寫成 `UPDATE sessions SET booked = booked + 1 WHERE id = $1`：

```
ERROR:  new row for relation "sessions" violates check constraint "sessions_check"
```

沒有自己命名的表層級 CHECK 會被命名成「表名_check」。看到這個錯誤代表有一條寫入路徑繞過了 `book()`。

**用 max(number) + 1 取號。** 在並行下兩個請求會算出同一個號碼，其中一個撞上 `appointments_session_id_number_key`。號碼要從被鎖住的那一列（`next_no`）拿。

**交易裡做慢的事。** 在掛號交易裡呼叫簡訊服務，簡訊服務慢 5 秒，同一個診次的所有掛號就排隊 5 秒。外部呼叫放到交易提交之後，或寫進一張待發送的表交給背景工作。

**取消的條件沒寫進 WHERE。** 先 `SELECT status`、判斷是 booked 再 `UPDATE`，兩個取消請求同時到時會減兩次 `booked`。把 `status = 'booked'` 寫進 UPDATE 的 WHERE，第二個請求自然更新到 0 列。

**單一連線的測試測不出競態。** 驗收題、這頁的範例都只有一個連線，請求是依序執行的。要真的驗證並行行為，需要兩個以上的連線，例如用兩個 `psql` 視窗手動交錯，或在整合測試裡用執行緒（需要真的 PostgreSQL，不能在瀏覽器裡跑）：

```python
from concurrent.futures import ThreadPoolExecutor
import psycopg

def try_book(patient_id):
    with psycopg.connect(DATABASE_URL, autocommit=True) as conn:
        return conn.execute("SELECT book(%s, %s)", [SESSION_ID, patient_id]).fetchone()[0]

with ThreadPoolExecutor(max_workers=20) as pool:
    numbers = list(pool.map(try_book, range(1000, 1050)))

issued = [n for n in numbers if n is not None]
assert len(issued) == CAPACITY and len(set(issued)) == CAPACITY
```

## 驗收題在測什麼

**一句 SQL 取號**：寫 `book()`。驗證查詢對名額 3 的診次依序掛 5 位，預期拿到 1、2、3、NULL、NULL；名額 1 的診次第二位拿到 NULL；不存在的診次回 NULL；最後檢查掛號筆數、號碼不重複、`booked` 與 `next_no` 的值。題目要求「同一句 UPDATE 完成」，但驗證只在單一連線上看行為，測不出先 SELECT 再 UPDATE 的寫法在並行下的問題——那是這頁上面解釋的部分。

**取消與重掛**：把全欄位的唯一約束換成部分唯一索引、寫 `cancel()`。驗證：有效掛號重複掛會得到 `23505`；取消回 true、再取消一次回 false 且 `booked` 只減一次；取消後可以重掛，拿到新號碼；已報到與不存在的掛號不能取消；資料表上確實有一個帶 `WHERE` 的唯一索引。
