## 這階段要做出什麼

整個系統的資料只有四種東西：病患、醫師、診次、掛號。這一階段把它們變成四張 PostgreSQL 資料表，並且把「什麼樣的資料不該存在」寫成約束，讓資料庫在寫入當下就拒絕。

```
doctors 1 ──── * sessions 1 ──── * appointments * ──── 1 patients
                (某醫師某天某時段，     (病患在某診次的號碼，
                 有名額上限 capacity)    狀態 booked / cancelled / checked_in)
```

| 表 | 一列代表 | 這一階段要守住的規則 |
|---|---|---|
| `patients` | 一位病患 | 姓名必填 |
| `doctors` | 一位醫師 | 姓名、科別必填 |
| `sessions` | 一個診次：某醫師、某天、某時段 | 醫師必須存在；時段只能是 morning／afternoon／evening；名額大於 0；同一醫師同一天同一時段只有一個診次 |
| `appointments` | 一筆掛號 | 診次與病患都必須存在；號碼大於 0；同一診次號碼不重複；同一病患在同一診次只有一筆；狀態只能是三種之一，預設 booked |

範例資料全部是虛構的。真實系統的病患表通常還有身分證字號、生日、電話，這裡刻意只留姓名：欄位越少，之後要遮罩、要控管存取的東西就越少（第 8 階段會處理日誌裡的身分證字號）。

建模的基本功（實體、關聯、正規化）在 [資料建模與正規化](#/skill/data-modeling)；語法在 [SQL 基礎](#/skill/sql-basics)；約束和交易的關係在 [交易與隔離等級](#/skill/transactions)。這裡只談把它們用在這個系統時要做的決定。

## 設計決策與取捨

### 規則為什麼放在資料庫，而不只放在程式裡

第 2 階段會把同樣的規則寫成 Python 函式，看起來重複。差別在於：程式裡的檢查只對「走這段程式的寫入」有效，而且在並行時會失效——兩個請求同時檢查「這個號碼還沒人用」，兩邊都通過，然後都寫入（第 5 階段會實際處理這種狀況）。資料庫的唯一約束是在寫入時由資料庫自己檢查，不管寫入來自 API、後台腳本、還是有人手動下 SQL，也不管同時有幾個交易。

所以分工是：**程式負責給出好懂的錯誤訊息，資料庫負責保證資料不會壞**。程式漏了一條檢查，最壞是使用者看到一個比較醜的錯誤；資料庫少了一條約束，就可能出現兩個人拿到同一個號碼。

### 哪些規則寫得成約束、哪些寫不成

| 規則 | 寫法 | 備註 |
|---|---|---|
| 同一診次號碼不重複 | `UNIQUE (session_id, number)` | 兩欄合起來唯一，不是各自唯一 |
| 同一病患同一診次只能一筆 | `UNIQUE (session_id, patient_id)` | 第 5 階段會改成「未取消的只能一筆」 |
| 名額大於 0、號碼大於 0 | `CHECK (capacity > 0)` | CHECK 只看同一列 |
| 狀態只能三種 | `CHECK (status IN (...))` | 也可以用 enum 型別，見下方 |
| 名額不能超過 | 這一階段**寫不成** | CHECK 不能數別的列；第 5 階段改用計數欄位 |
| 同一病患同一天最多 3 診 | 這一階段**寫不成** | 跨列又跨表（要看診次日期），留在程式裡，第 5 階段再談並行下的風險 |

「名額不能超過」是最重要、也最容易被誤以為可以用約束搞定的規則。`CHECK` 只能看正在寫入的那一列，沒辦法寫「這個診次的掛號數 ≤ capacity」。PostgreSQL 的 CHECK 裡也不能放子查詢。這條規則要等到第 5 階段，在 `sessions` 加一個 `booked` 計數欄位，才能用 `CHECK (booked <= capacity)` 守住。

### 列舉值：CHECK、enum 型別還是查找表

狀態和時段都是固定幾個值。三種常見寫法：

- `TEXT` + `CHECK (status IN (...))`：要改值時刪掉約束重建就好，這裡選這個。
- `CREATE TYPE appointment_status AS ENUM (...)`：型別本身就限制了值，儲存比較省；新增值用 `ALTER TYPE … ADD VALUE`，但移除或改名比較麻煩。
- 查找表（`periods(code, starts_at, ends_at)` 加外鍵）：值本身帶有屬性時最合適，例如每個時段的起訖時間。如果之後要顯示「上午診 08:30–12:00」，時段就值得升級成查找表。

### 主鍵：遞增整數還是 UUID

這裡用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`：小、有順序、索引友善。代價是 id 可以被猜：拿到 `/appointments/41` 的人會想試 `/appointments/42`。這不是資料表的問題，而是權限的問題——第 4 階段要確保「猜到 id 也看不到別人的掛號」。改用 UUID 可以讓 id 難猜，但不能取代權限檢查。

### 時間欄位

- `session_date` 用 `DATE`：診次的日期是「診所當地的哪一天」，不需要時區。
- `created_at` 用 `TIMESTAMPTZ`：記錄的是一個絕對的時間點，PostgreSQL 內部以 UTC 儲存、依連線的 `TimeZone` 設定顯示。用沒有時區的 `TIMESTAMP` 存「現在」，之後伺服器或連線的時區設定一變，就分不清那是哪個時間點。

### 外鍵與索引

PostgreSQL 會自動替主鍵和 `UNIQUE` 建索引，**但不會替外鍵的參照欄位建索引**。`UNIQUE (session_id, number)` 產生的索引以 `session_id` 開頭，「查某診次的掛號」用得到它；「查某病患的所有掛號」用的是 `patient_id`，沒有索引就得掃整張表。病患查自己的掛號是很常見的請求，所以要另外建：

```sql
CREATE INDEX appointments_patient_id_idx ON appointments (patient_id);
```

刪除行為維持預設（`NO ACTION`）：有掛號的病患不能直接刪除。醫療相關的紀錄通常不該因為刪了某一筆主資料就跟著消失，`ON DELETE CASCADE` 不要隨手加。

## 關鍵 SQL

下面這段在瀏覽器裡的 PostgreSQL 執行：建表、放入一筆合法資料，再用一個小函式逐一嘗試違規的寫入，印出每一項被擋下時的 SQLSTATE（錯誤代碼）。`try_sql` 執行成功時會刻意丟一個自訂錯誤把寫入撤銷，所以每一項嘗試互不影響。

```sql run
-- 先清掉上一次執行留下的表與函式，重複執行也不會出錯
DROP TABLE IF EXISTS appointments, sessions, doctors, patients CASCADE;
DROP FUNCTION IF EXISTS try_sql(text);

CREATE TABLE patients (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL
);
CREATE TABLE doctors (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name TEXT NOT NULL,
  dept TEXT NOT NULL
);
CREATE TABLE sessions (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  doctor_id BIGINT NOT NULL REFERENCES doctors(id),
  session_date DATE NOT NULL,
  period TEXT NOT NULL CHECK (period IN ('morning', 'afternoon', 'evening')),
  capacity INT NOT NULL CHECK (capacity > 0),
  UNIQUE (doctor_id, session_date, period)
);
CREATE TABLE appointments (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  session_id BIGINT NOT NULL REFERENCES sessions(id),
  patient_id BIGINT NOT NULL REFERENCES patients(id),
  number INT NOT NULL CHECK (number > 0),
  status TEXT NOT NULL DEFAULT 'booked'
    CHECK (status IN ('booked', 'cancelled', 'checked_in')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (session_id, number),
  UNIQUE (session_id, patient_id)
);

-- 執行一句 SQL：成功回 'ok' 並撤銷，失敗回 SQLSTATE
CREATE FUNCTION try_sql(q text) RETURNS text LANGUAGE plpgsql AS $$
BEGIN
  BEGIN
    EXECUTE q;
    RAISE EXCEPTION USING ERRCODE = 'ZX000';
  EXCEPTION WHEN OTHERS THEN
    IF SQLSTATE = 'ZX000' THEN RETURN 'ok'; END IF;
    RETURN SQLSTATE;
  END;
END $$;

-- 不指定 id，讓 identity 產生（依序是 1、2…）
INSERT INTO doctors (name, dept) VALUES ('林醫師', '家醫科');
INSERT INTO patients (name) VALUES ('王小明'), ('陳小華');
INSERT INTO sessions (doctor_id, session_date, period, capacity) VALUES (1, '2026-11-02', 'morning', 2);
INSERT INTO appointments (session_id, patient_id, number) VALUES (1, 1, 1);

SELECT probe, try_sql(q) AS sqlstate FROM (VALUES
  ('合法的第二筆',       $q$INSERT INTO appointments (session_id, patient_id, number) VALUES (1, 2, 2)$q$),
  ('號碼重複',           $q$INSERT INTO appointments (session_id, patient_id, number) VALUES (1, 2, 1)$q$),
  ('同病患同診次第二筆', $q$INSERT INTO appointments (session_id, patient_id, number) VALUES (1, 1, 2)$q$),
  ('診次不存在',         $q$INSERT INTO appointments (session_id, patient_id, number) VALUES (99, 2, 1)$q$),
  ('狀態不合法',         $q$INSERT INTO appointments (session_id, patient_id, number, status) VALUES (1, 2, 2, 'done')$q$),
  ('名額是 0',           $q$INSERT INTO sessions (doctor_id, session_date, period, capacity) VALUES (1, '2026-11-03', 'morning', 0)$q$)
) AS v(probe, q);
```

`23505` 是唯一鍵衝突、`23503` 是外鍵、`23514` 是 CHECK、`23502` 是 NOT NULL。第 3 階段的 API 會依這些代碼（和約束名稱）決定回哪個 HTTP 狀態碼。

## 常見錯誤與錯誤訊息

**唯一約束寫成兩個單欄。** `UNIQUE (session_id), UNIQUE (number)` 的意思是「整張表只能有一筆 1 號」，跟需求完全不同。違反時的訊息會指出是哪個約束與哪些值：

```
ERROR:  duplicate key value violates unique constraint "appointments_session_id_number_key"
DETAIL:  Key (session_id, number)=(1, 1) already exists.
```

約束名稱沒自己取時，PostgreSQL 會用「表名_欄位_key」這類規則產生。API 要依約束分辨「號碼重複」和「重複掛號」時，自己取名字（`CONSTRAINT one_per_patient UNIQUE (...)`）比依賴自動產生的名稱穩定。

**以為 CHECK 會擋 NULL。** CHECK 的運算式結果是 NULL 時算通過，`CHECK (capacity > 0)` 擋不住 `capacity` 是 NULL。必填欄位一定要另外加 `NOT NULL`。NOT NULL 違反時的訊息長這樣：

```
ERROR:  null value in column "patient_id" of relation "appointments" violates not-null constraint
```

**NOT NULL 卻沒有 DEFAULT。** `status` 和 `created_at` 都是必填，但 API 建立掛號時不會傳這兩個值。沒有 `DEFAULT 'booked'`、`DEFAULT now()`，每次插入都會撞到 not-null。

**外鍵指錯方向或少了外鍵。** `appointments.session_id` 沒有 `REFERENCES sessions(id)` 時，可以掛到不存在的診次，錯誤要到很久以後查報表才發現。有外鍵時的訊息：

```
ERROR:  insert or update on table "appointments" violates foreign key constraint "appointments_session_id_fkey"
DETAIL:  Key (session_id)=(99) is not present in table "sessions".
```

**手動指定 id 之後，identity 撞號。** `GENERATED BY DEFAULT AS IDENTITY` 允許插入時自己給 id，但背後的序列不會因此前進。先手動插入 `id = 1`，下一次讓資料庫產生 id 時序列給的還是 1：

```
ERROR:  duplicate key value violates unique constraint "appointments_pkey"
```

匯入舊資料後要把序列調到目前最大值之後（`SELECT setval(pg_get_serial_sequence('appointments', 'id'), max(id)) FROM appointments`）。不希望有人手動指定 id 時，改用 `GENERATED ALWAYS AS IDENTITY`，手動給值會直接被拒絕。

**用 TIMESTAMP 存現在時間。** 不會報錯，但之後換主機或改了連線時區，舊資料的意義就變了。存時間點一律用 `TIMESTAMPTZ`。

## 驗收題在測什麼

驗收題只給欄位名稱，約束要自己寫。驗證時先插入一位醫師、兩位病患、一個名額 2 的診次與一筆掛號，接著嘗試 12 種寫入：一種合法（沒給 `status` 與 `created_at`，用來確認預設值）、11 種違規（號碼重複、同病患重複、診次或病患不存在、病患為 NULL、號碼 0、狀態不合法、名額 0、時段不合法、同醫師同天同時段兩個診次、醫師不存在）。每一項都要得到預期的 SQLSTATE。

題目沒有檢查約束的名稱，也沒有檢查索引；`patient_id` 的索引是上面建議要加的，但不在驗收範圍內。下一階段把同樣的規則寫成 Python，並補上資料庫守不住的那兩條（名額上限與每日上限）。
